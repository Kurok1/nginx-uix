## H-1 🔴 SPA 无 history 回退，刷新/深链任何非根路由都 404

- **位置**：`internal/httpapi/server.go:45`（`spaFallback`）、`internal/httpapi/server.go:37`（`mux.Handle("/", ...)`）
- **相关**：`web/src/router.ts:48`（`createWebHistory()`）；路由 `/configuration`、`/login`

### 问题

`spaFallback` 直接 `return http.FileServer(http.FS(assets))`，没有把未命中的路径回退到 `index.html`。前端路由用的是 `createWebHistory()`（干净 URL，非 hash），存在 `/configuration`、`/login` 两条路由。

### 复现

1. 登录后进入配置页，URL 变为 `/configuration`。
2. 按 F5 刷新，或直接打开书签 / 深链 `/configuration`（`/login` 同理）。
3. Go 把 `GET /configuration` 交给 `http.FileServer`，它在 embedded dist 中找不到名为 `configuration` 的文件 → **返回 404，SPA 无法加载**。

所有非 `/` 路由一经刷新或深链即坏。

### 为什么测试没抓到

`web/playwright.config.ts` 的 e2e 跑在 `vite preview`（自带 SPA history 回退），而非真实 Go 二进制；`docs/release/v0.1.0-verification.md` 的路由审计把这个 `FileServer` 记作「SPA 静态资源 fallback」，但它并不是 history-mode 回退。**验收证据在此路径存在盲区。**

### 修复方向

把 `/` 处理器替换为自定义 handler：
- 命中真实存在的静态资源（`/assets/...`、`/favicon` 等）→ 返回该文件；
- 命中已有 API/health 前缀之外的其它 GET 路径且资源不存在 → 返回 `index.html`（HTTP 200）；
- 非 GET 或 API 路径保持原有 404/405 语义，不要吞掉 API 路由。
- 注意仍要保留 `requestBoundary` 注入的安全响应头与 `Cache-Control`（HTML 不应被强缓存）。

### 验证建议

- 新增 Go handler 测试：对真实 `NewHandler` 发起 `GET /configuration`，断言 `200` 且响应体为 `index.html` 内容；`GET /assets/<真实文件>` 仍返回该资源；`GET /api/v1/...` 未认证仍返回稳定错误码（回归保护，确认没误伤 API）。
- 新增一条跑在**真实 Go 二进制**（而非 `vite preview`）上的 e2e：深链 `/configuration` 刷新后页面正常渲染。

## M-1 🟠 `login_throttles` 只增不删，未认证请求可撑爆磁盘（慢速 DoS）

- **位置**：`internal/store/repository.go:147`（`RecordLoginFailure` 的 `INSERT ... ON CONFLICT`）
- **相关**：`internal/store/repository.go:174`（`ClearLoginFailures` 是唯一删除，且为 key 级）；`internal/auth/service.go:114-126`

### 问题

每次登录失败都会 upsert 一行 `(normalized_name, source_ip)`。唯一的删除发生在该 key 登录成功时（`ClearLoginFailures`）。不存在/格式非法的用户名各自生成独立哈希 key（`normalizeLoginName` 的 `invalid-<hash>`），**永远达不到 5 次封禁、也永不被清理**，且**没有任何 TTL 或后台清扫**。

会话表 `sessions` 同理只在访问时惰性删除过期项，无主动清扫。

### 复现（未认证即可触发）

脚本化客户端把 `Origin` 设成等于请求 `Host`（即可通过 `originMatches`），从单一 IP 反复 `POST /api/v1/auth/session`，每次换一个新用户名：
- 每次都进入 `RecordLoginFailure` 并 INSERT 一行新 key；
- 永不触发封禁、永不 `ClearLoginFailures`；
- `login_throttles` 单调增长，直至 `/var/lib/nginx-uix` 磁盘写满，拖垮整个服务。

### 修复方向

- 增加一个**受 owner 管理、可取消、带退避**的周期清扫任务（`AGENTS.md` §6.2：明确所有者、退出条件、回收路径），删除：
  - 已过封禁且窗口过期的 `login_throttles` 行（`blocked_until IS NULL OR blocked_until < now` 且 `window_started_at < now - window`）；
  - 已过绝对/空闲期的 `sessions` 行（可复用现有过期语义）。
- 或者在 `RecordLoginFailure` 写路径上顺带做有界清理（谨慎控制额外写放大）。
- 生命周期挂在 UI 进程（`internal/app`），随服务优雅停止一起退出。

### 验证建议

- store 测试：插入若干过期 throttle/session 行，运行一次清扫，断言过期行被删、活跃行保留、被封禁未到期行保留。
- 并发/取消测试：清扫任务在 context 取消后按期退出，无泄漏。

## M-2 🟠 `nginx -T` 标记解析可被配置注释伪造

- **位置**：`internal/runtime/effective_config.go:122`（`strings.HasPrefix(line, configurationMarkerPrefix)`）、`:23`（`configurationMarkerPrefix = "# configuration file "`）

### 问题

`parseEffectiveConfig` 把**任意**以 `# configuration file ` 开头、`:` 结尾的行都当成文件分界。但 `nginx -T` 会把每个文件正文原样回显，因此配置里一句注释就会被误判为新的文件条目。现有守卫只有「以 `:` 结尾、路径非空、无控制字符」，不足以区分真伪。

### 复现

在 `nginx.conf` 或任一被 include 的文件里加一行注释：

```nginx
# configuration file for the api:
```

或蓄意伪造：

```nginx
# configuration file /etc/passwd:
```

`nginx -T` 原样回显该行 → 解析器剥掉前缀、见到结尾 `:` → 生成一个 **Path 为注释文本的幽灵 `ConfigOccurrence`**，并把真实文件正文劈成两段分到两个面板。前端校验（顺序 `load_order`、唯一 `id`）仍通过（解析器是顺序赋值的），**没有任何环节拦截被污染的结果**。对一个以「忠实展示生效配置」为核心价值的工具，这直接损害可信度。

### 修复方向（务实收紧，非绝对可证）

- **至少**要求标记路径为绝对路径（以 `/` 开头），可滤掉绝大多数意外的散文式注释（如 `for the api:`）。
- 蓄意在注释里写 `/etc/passwd:` 这类仍无法纯文本区分；对此建议：
  - 结合 nginx 真实标记的结构特征进一步收紧（真实标记由 nginx 自身输出，通常前置空行、独占整行、路径为它实际打开的文件）；
  - 无法可靠证明时，宁可对可疑条目做显式标注/降级，也不要把推测当事实（符合 `PLAN.md` §6.2「不把推测包装成事实」的一贯原则）。
- 明确该解析限制并在测试中固化边界行为。

### 验证建议

- golden/单元测试：构造含 `# configuration file ...:` 形态注释的 `nginx -T` 输出样本，断言解析器不产生幽灵条目、真实文件正文不被劈开。
- 用 `tests/fixtures/nginx/` 下真实 fixture 跑集成测试，覆盖多文件/重复 include 与含此类注释的组合。

## 附录：其余审核项（本次不作为修复重点，留档备查）

### 低风险（受支持部署下影响有限）

- **logout 遇网络错误静默失败、仍停留在已登录态** — `web/src/session.ts:74` / `web/src/components/GlobalNav.vue:118` / `web/src/api/client.ts:105`。`kind:'network'` 错误不触发 `onError` 监听，`GlobalNav.logout` 无 `catch`，`setAnonymous()` 被跳过。建议 `logout` 加 `catch` 或客户端侧无条件 `setAnonymous()`。
- **`nginx-uix-agent` 缺 `finish` 脚本** — `deploy/docker/rootfs/etc/s6-overlay/s6-rc.d/nginx-uix-agent/`。缺少兄弟服务的 `sleep 1`（及 `s6-permafailon`）节流，快失败时紧凑重启风暴。建议补一个与 `nginx-uix/finish` 一致的 finish。
- **nginx 二进制被替换后运行中 master 被判 foreign** — `internal/runtime/status.go:238`。`/proc/<pid>/exe` 变为 `/usr/sbin/nginx (deleted)` 后严格等值失败。一体化镜像运行期通常不换二进制，影响低；可像 worker 路径那样容忍 `(deleted)` 后缀。

### 属「设计如此」——非缺陷，仅记录权衡

- **会话 Cookie 默认无 `Secure`** — `internal/httpapi/auth.go:175`。设计 §9.2 明确「仅当 `NGINX_UIX_PUBLIC_URL` 为 https 才设 Secure」，§7.1 官方暴露为回环明文 HTTP。真实风险仅在「TLS 反代但未设 `PUBLIC_URL`」这一未记录拓扑；建议在文档中更醒目提示。
- **限速按 `(用户名, 来源IP)` 键，IP 轮换可绕过** — `internal/auth/service.go:95`。设计 §9.1 明确此键。附带：每次登录尝试都跑完整 Argon2id（缺失用户走 dummyHash），IP 轮换可放大为 CPU/内存 DoS。建议未来版本加每账户/全局上限。
- **readiness 在 degraded/恢复窗口内返回 503** — `internal/httpapi/health.go:43`。设计 §11.2 + §14.1 明确规定，验证阶段驳回方正确引用设计。符合规范；仅需知悉外部编排器基于 health 重调度时的 5 分钟窗口影响。

### 清理项（不影响功能，防未来漂移）

- **构建元数据是死代码** — `internal/app/version.go:24`。Dockerfile 注入了 `-X Version/Commit/BuildTime`，但 `CurrentBuildInfo()` 仅测试引用，运行期无处暴露。接线到启动日志/状态，或删除。
- **`init-container` 是死路径** — `internal/app/agent.go:137`。容器实际用 `init-nginx-runtime` + `prepare-ui-data`，形成两套初始化路径，有漂移风险。
- **两个视图重复异步刷新状态机** — `web/src/views/EffectiveConfigView.vue:186` ↔ `web/src/views/DashboardView.vue`。建议抽 `useAsyncSnapshot` composable。
- **`AUTH_SESSION_EXPIRED` 是幽灵错误码 + 错误码命名不一致** — `web/src/session.ts:83`。后端只发 `unauthenticated`；且 auth 类错误用小写（`unauthenticated`/`invalid_credentials`/`csrf_rejected`/`rate_limited`），nginx/agent 类错误用大写下划线（`AGENT_UNAVAILABLE`…），二者都不完全匹配设计 §13.1 的稳定码定义。建议统一命名并对齐 `api/v1/openapi.yaml`。
