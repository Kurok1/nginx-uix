## 目标与边界

本计划只处理评审记录中的三项中高风险问题：

- H-1：真实 Go HTTP 服务缺少 SPA history fallback。
- M-1：过期登录限速与会话状态没有主动清理生命周期。
- M-2：`nginx -T` 正文中的伪造标记会污染生效配置条目。

不夹带附录中的低风险项、设计权衡或清理项；不修改 v0.2 worktree。所有行为变更先用失败测试复现，再做最小实现，并在 v0.1 分支验证后合并回 `main`。

## 已确认根因

### H-1

`internal/httpapi/server.go` 把 `/` 直接交给 `http.FileServer`。Vue Router 使用 history 模式，因此 `/configuration`、`/login` 等不存在同名静态文件的 GET 深链会由真实 Go 服务返回 404；当前 Playwright 运行在 Vite preview，未覆盖该路径。

初次修复的测试直接使用 `fstest.MapFS`，但生产 `uiassets.FS()` 是 `fs.Sub(embed.FS, "dist")` 返回的 `*fs.subFS`。修复后的 handler 对根路径计算出空 `assetPath` 并执行 `Stat("")`；`MapFS` 返回 `fs.ErrNotExist`，而 `subFS` 返回 `fs.ErrInvalid`，导致生产根路径错误进入 500 分支。根因是静态资源测试没有保留生产 FS 包装形态，同时 handler 没有在调用 FS 前排除空路径。

### M-1

`RecordLoginFailure` 只 upsert 当前 `(normalized_name, source_ip)`，成功登录只删除同一 key；过期 session 也只在持有该 token 的请求到来时惰性删除。UI 进程没有拥有、取消和等待任何认证清理任务。

### M-2

当前 parser 从头到尾扫描所有 `# configuration file ...:` 行。Nginx `-T` 会按“真实标记行、原文件字节、额外分隔换行”输出每个配置 occurrence；因此仅靠继续扫描文本无法区分正文中的同形注释。可靠边界必须从固定入口标记开始，并用 Nginx 实际读取文件的字节长度推进到下一条真实标记；读取必须限制在固定配置根目录内并设置大小上限。

## Task 1：修复 SPA history fallback（H-1）

**修改文件：**

- Modify: `internal/httpapi/server_test.go`
- Modify: `internal/httpapi/server.go`
- Modify: `tests/docker/smoke.sh`

### Step 1：添加失败的 Go HTTP 边界测试

在 `internal/httpapi/server_test.go` 使用 `fs.Sub(fstest.MapFS{"dist/...": ...}, "dist")` 构造与生产一致的 `*fs.subFS`，覆盖：

- `GET /` 返回 200 和 `index.html`，不对空路径执行 `Stat`。
- `GET /configuration` 与 `GET /login` 返回 200 和 `index.html`，HTML 为 `Cache-Control: no-store`。
- `GET /assets/app.js` 返回真实资源而不是 index。
- `GET /api/v1/unknown` 与缺失 asset 返回 404，不被 SPA 吞掉。
- `PUT /configuration` 返回 405。
- 响应仍包含 request boundary 的安全头。

运行并确认旧实现因深链 404 而失败：

```bash
go test ./internal/httpapi -run TestSPAFallback -count=1 -v
```

### Step 2：实现最小 GET-only SPA handler

把 catch-all 注册为 `GET /`，保留 ServeMux 对其它方法的 405 语义。handler 对空路径和 `.` 直接进入 index 回退，不调用 `Stat`；其它路径先检查并服务真实普通文件，`fs.ErrNotExist` 与 `fs.ErrInvalid` 均视为没有可服务静态文件，只有其它意外 I/O 错误返回 500。缺失 `/api`、`/health`、`/assets` 路径返回 404；其它缺失 GET/HEAD 路径改写到 `/index.html`，并给 HTML 设置 `Cache-Control: no-store`。不绕过现有 `requestBoundary`。

再次运行聚焦测试并确认通过：

```bash
go test ./internal/httpapi -run TestSPAFallback -count=1 -v
```

### Step 3：增加真实 Go 容器回归证据

在 `tests/docker/smoke.sh` 的主容器就绪后请求 `/` 与 `/configuration`，断言：

- HTTP 200；
- body 包含生产 `index.html` 的应用挂载点；
- `Cache-Control: no-store`；
- 缺失 API 路径仍为 404。

该检查直接命中镜像内 Go 二进制和 `uiassets.FS()` 的生产 embed/subFS，不依赖 Vite preview。

### Step 1：添加失败的 store 清理测试

插入以下组合后调用一次清理：

- idle 已过期 session、absolute 已过期 session；
- 活跃 session；
- 窗口已过期且未封禁 throttle；
- 窗口已过期且封禁也已结束 throttle；
- 窗口已过期但仍在封禁中的 throttle；
- 窗口仍活跃的 throttle。

断言仅前两类 session 和可安全遗忘的 throttle 被删除，并核对删除计数。先运行并确认接口/行为缺失：

```bash
go test ./internal/store -run TestCleanupExpiredAuthState -count=1 -v
```

### Step 2：实现领域策略与事务清理

在 `auth.Repository` 增加聚焦的清理方法与计数 DTO；由 `auth.Service.CleanupExpired` 使用其自身 clock 和既有五分钟 throttle window 调用 repository，避免 app/store 重复硬编码认证策略。

在 store 的 immediate transaction 中分别删除：

- `idle_expires_at <= now OR absolute_expires_at <= now` 的 session；
- `window_started_at <= now - throttleWindow` 且 `blocked_until IS NULL OR blocked_until <= now` 的 throttle。

SQLite 时间比较使用 `julianday` 解析 RFC 3339，而不是直接比较可变精度的 RFC3339Nano 文本。通过单调迁移为 session idle expiry 和 throttle window cutoff 补充索引，避免周期任务在大表上退化为全表扫描。返回两类删除计数，错误保留动作上下文。

运行：

```bash
go test ./internal/store ./internal/auth -run 'TestCleanupExpiredAuthState|TestServiceCleanupExpiredAuthState' -count=1 -v
```

### Step 3：添加失败的 worker 退避与取消测试

在 `internal/app/ui_test.go` 通过可注入 wait 函数验证：

- worker 启动后立即清理一次；
- 连续失败使用有上限的指数退避；
- 成功后恢复正常清理周期；
- context 取消能退出等待/执行路径，调用方可等待 worker 完成。

先运行并确认 worker 尚不存在：

```bash
go test ./internal/app -run 'TestAuthCleanupWorker' -count=1 -v
```

### Step 4：由 UI 生命周期拥有 worker

在 `RunUI` 完成 bootstrap 后启动一个清理 goroutine。worker 每次调用使用有界子 context，失败记录脱敏结构化日志并退避；`runHTTPServer` 返回后，无论正常取消还是监听失败，都先取消并等待 worker，再关闭 SQLite，避免 goroutine 使用已关闭数据库。

运行：

```bash
go test ./internal/app ./internal/store ./internal/auth -count=1
```

### Step 1：添加失败的 parser/golden 测试

把单元 fixture 调整为真实 Nginx dump 结构，并在某个正文中加入：

```nginx
# configuration file for the api:
# configuration file /etc/passwd:
```

给 parser 注入受控文件 reader，断言两行均保留在原 occurrence 正文中，不产生幽灵 path；同时添加缺失文件、越界 path、内容与 dump 不一致、缺少分隔换行等 fail-closed 用例。

先运行并确认旧扫描逻辑把 `/etc/passwd` 拆成条目：

```bash
go test ./internal/runtime -run 'TestParseEffectiveConfig' -count=1 -v
```

### Step 2：实现固定入口和文件验证边界

生产 Service 注入固定根文件 reader：

- 首标记必须是 `/etc/nginx/nginx.conf`；
- marker 原始 path 必须是绝对路径，规范化后的 path 必须仍在 `/etc/nginx` 内；安全的 `..` 折返路径规范化后读取和展示；
- 使用 `os.OpenRoot` 防止相对/符号链接逃逸；
- 只读取普通文件，单文件读取受总输出上限约束；
- parser 对比规范化后的真实文件字节，并按“正文长度 + Nginx 分隔换行”直接定位下一标记；
- 任意不一致都整体失败，不返回部分 occurrence。

这使正文中的同形注释不再参与边界识别，也避免为伪造 `/etc/passwd` 路径读取配置根之外的文件。

运行：

```bash
go test ./internal/runtime -count=1
```

### Step 3：用真实 Nginx fixture 固化行为

在现有 `tests/fixtures/nginx/effective/conf.d/repeated.conf` 加入两种同形注释；集成测试按同一“真实文件字节长度 + Nginx 分隔换行”边界验证真实 `nginx -T` stdout，断言 occurrence 数量、重复 include 顺序与正文完整性。生产 parser 本身由同形单元 fixture 覆盖。

运行：

```bash
NGINX_UIX_INTEGRATION=1 go test ./tests/integration -run TestEffectiveConfigWithRealIsolatedNginx -count=1 -v
```

同步修改 Docker smoke 的独立比对逻辑：不要再复制有缺陷的逐行 marker 扫描，而是从 API occurrence 的 path 读取容器内对应配置字节，验证顺序与内容；同时确认伪造注释没有形成 occurrence。
