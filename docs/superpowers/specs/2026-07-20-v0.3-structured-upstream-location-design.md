## 1. 文档目的

本文把 `PLAN.md` 中 v0.3.0“结构化 upstream 与 location 版”细化为可直接实施和验收的产品与技术设计。管理员在 v0.2.1 已有工作区草稿上读取、预览和应用结构化变更；结构化模型不是新的配置真源，也不能绕过 v0.2.2/v0.2.3 的候选校验、备份、发布、reload 和恢复事务。

本版本最重要的约束是 lossless：未修改的源文本必须按字节保持不变，修改一个目标时只替换能够由 source span 唯一证明的局部范围。解析器不认识的指令、参数、注释、引号、转义、空白和换行风格继续留在原文件中。解析或引用事实不完整时，结构化操作 fail closed，同时保留现有原始文本编辑入口。

Nginx 语义基线采用官方文档：[`upstream`/`server`](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)、[`location`](https://nginx.org/en/docs/http/ngx_http_core_module.html#location) 与 [`proxy_pass`](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)。本版本只实现计划明确列出的 HTTP 能力，不把版本相关或商业模块参数解释为可编辑字段。

## 2. 用户结果与完成标准

管理员能够在一个 `ready` 工作区中：

1. 查看跨文件展开后的 HTTP、server、upstream 与 location 结构及其相对文件位置。
2. 创建、重命名和删除 upstream，并管理其中常用的 `server` 参数。
3. 查看 server 下的 location 层级，创建、编辑和删除官方 location 类型。
4. 为 location 选择一个静态 upstream 并生成直接的 `proxy_pass`。
5. 在任何结构化写入前查看完整逐文件差异、诊断与警告。
6. 应用变更后回到普通工作区继续原始编辑、完整 diff、候选检查和安全发布。

版本只有同时满足以下条件才完成：

- parse → no-op render 对每个有效输入逐字节相等。
- parse → 局部修改 → render → reparse 对目标结构一致，目标 span 之外逐字节相等。
- include 展开能够继承 `main`、`http`、`server`、`upstream` 和 `location` 上下文，并对循环、外部、缺失或多上下文包含给出确定结论。
- upstream 删除在存在静态引用时被阻止并列出相对文件、行、列；引用分析不完整时同样 fail closed。
- upstream 重命名与其可证明的静态 `proxy_pass` 引用作为一个可恢复的多文件草稿事务提交。
- location 嵌套限制、重复规则、明显不可达规则、正则顺序敏感和悬空 upstream 引用都有稳定诊断码和测试。
- UI 明确区分“结构化静态检查”“尚未执行完整 Nginx 校验”和“发布检查通过”，不把解析成功当作配置有效。

## 3. 范围

### 3.1 包含

- UTF-8 Nginx 配置 tokenizer、通用 directive/block AST、1-based 行列和 byte source span。
- 注释、空白、引号、转义和未知语法的 lossless 原文保留。
- 基于现有 workspace manifest/include dependency 的跨文件上下文展开。
- `http`、`server`、`upstream`、`location` 和直接 `proxy_pass` 的结构投影。
- upstream 创建、重命名、删除和引用检查。
- upstream `server` 的地址、端口、`weight`、`backup`、`down`、`max_fails`、`fail_timeout`。
- upstream 内未知 directive 和 `server` 未识别参数的原样保留。
- location 的 exact、普通 prefix、`^~`、`~`、`~*` 和 named 类型。
- location 嵌套读取、创建、编辑、删除和可证明的合法性检查。
- location 中单个直接字面量 `proxy_pass` 的 upstream 选择、替换和删除。
- 重复、不可达、正则顺序、动态引用、悬空引用和解析不完整诊断。
- 绑定 workspace ETag 的结构化变更预览、确定性 preview ID 和可恢复批量应用。
- `/api/v1` 显式 DTO、类型化前端 client、Upstream 与 Server/Location 页面。
- 原始文本编辑回退、响应式、键盘操作和 WCAG 2.2 AA 验收。

### 3.2 不包含

- Nginx 全语义解释器、全局自动格式化、LSP、自动补全或任意模块 schema。
- 修改生产配置、直接运行 reload/restart 或跳过现有发布流程。
- 路径真实命中测试、Route ID 注入或沙箱 Nginx；属于 v0.4.0。
- stream/mail upstream、Nginx Plus 动态 API、主动健康检查平台或服务发现管理。
- 自动编辑变量型 `proxy_pass`、Unix Socket `proxy_pass`、带用户信息的 URL 或无法唯一证明 authority 的表达式。
- 自动重写 `fastcgi_pass`、`uwsgi_pass`、`scgi_pass`、`grpc_pass`、`memcached_pass`、rewrite、try_files 或 error_page 引用。
- 自动移动整个 block 到另一文件、目录 CRUD、include 自动修复或跨工作区复制结构。
- 用 SQLite 保存 AST、配置正文、生成后的文件或可反向覆盖草稿的模型。
- Docker 构建、容器运行、卷、容器升级和多架构验证；统一留到 v0.7.0。

## 4. 不可违反的安全与数据不变量

1. `/etc/nginx` 仍是生产真源；workspace `draft` 是唯一可编辑候选文件集合；AST 只是一次读取的派生视图。
2. 结构化读取和预览不写 draft、SQLite 或浏览器持久化；结构化应用只调用 workspace 的受控草稿事务。
3. 所有写入要求认证、Origin、CSRF、单个强 `If-Match` 和匹配的 preview ID。
4. preview ID 绑定 workspace ID、draft ETag、规范化操作、目标文件集合和生成内容摘要；应用时必须重新解析和重新生成，不能信任客户端返回的 patch。
5. 任何 parse error、include 上下文歧义、source span 重叠、diff 不完整或 ETag 变化都禁止结构化应用；引用分析不完整只禁止依赖全局引用完备性的 upstream rename/delete。
6. 局部渲染不得改变目标 span 之外的任何字节；多文件变更不得留下被报告为成功的部分结果。
7. upstream 删除不能留下可证明的直接悬空引用；重命名必须同步更新所有可证明的直接静态引用。
8. 动态或无法分类的 `proxy_pass` 使 upstream rename/delete 的全局引用分析不完整，操作 fail closed；管理员仍可使用原始文本编辑并经过完整发布校验。
9. API、日志和审计不返回绝对路径、完整配置、生成后的完整文件、请求正文或 preview 原始操作；公开 patch 只存在于显式预览响应且禁止缓存。
10. 结构化解析成功不是 `nginx -t` 证据；UI 和 API 不使用 `valid` 描述单纯 AST 成功。

## 5. 总体架构

```text
Browser
  │ GET structured projection
  │ POST change preview
  │ POST change application + CSRF + If-Match
  ▼
nginx-uix Web/API
  ├── upstream service
  │   ├── upstream model / server parameter validation
  │   ├── direct proxy_pass reference analysis
  │   └── upstream change planner
  ├── location service
  │   ├── server/location hierarchy
  │   ├── matcher legality / diagnostics
  │   └── location change planner
  ├── nginxast
  │   ├── tokenizer / generic parser / source span
  │   ├── include-context project builder
  │   └── non-overlapping local renderer
  └── config workspace service
      ├── verified draft snapshot
      └── recoverable multi-file draft replacement
          │
          ▼
  /var/lib/nginx-uix/workspaces/<id>/{base,draft,control}

生产 /etc/nginx 与 Nginx 进程：结构化读取、预览和应用阶段均不接触
```

组件边界：

| 单元 | 负责 | 不负责 |
| --- | --- | --- |
| `nginxast` | 通用词法/语法、source span、include 上下文、局部拼接 | upstream/location 业务校验、HTTP、SQLite、文件写入 |
| `upstream` | upstream/server 模型、引用、规划和诊断 | 工作区持久化、生产发布、路径匹配 |
| `location` | server/location 模型、嵌套、proxy_pass 选择和诊断 | 真实请求、发布、upstream 生命周期 |
| `config` | 一致性工作区快照、ETag、可恢复批量草稿写入 | 解释 AST 或 location 匹配优先级 |
| `httpapi` | 严格 DTO、安全边界、错误映射 | 直接读写 draft 或拼接配置文本 |
| Vue | 结构列表、表单、预览、警告和原始编辑入口 | 推断配置有效、自动提交或持久化正文 |

`upstream` 和 `location` 在消费方定义小型 workspace 接口；`config.Service` 提供具体实现。`config` 不反向依赖领域包，避免工作区层理解 Nginx 语义。

## 6. Lossless tokenizer 与 AST

### 6.1 Token

tokenizer 保留每个输入字节并输出以下类型：

- `whitespace`：空格、tab、LF、CRLF 等原样保留。
- `comment`：未转义且位于引号外的 `#` 到行尾。
- `word`：普通参数、变量、正则片段和转义序列的原始字节。
- `quoted`：单引号或双引号及其完整原始内容。
- `semicolon`、`left_brace`、`right_brace`。
- `eof`：零长度终止 token。

每个 token 包含 `[start_byte,end_byte)`、起止 1-based 行列、raw 和按 Nginx 词法规则做最小解码后的 value。raw 是渲染事实；value 只用于结构判断。tokenizer 不展开变量、不解释正则、不规范化换行，也不把注释内容识别为指令。

以下情况返回带 span 的稳定 parse error：未闭合引号、悬空转义、缺失 `;`/`}`、多余 `}`、block 头为空、参数/token/嵌套上限超出。错误文件继续可以原始编辑，但其中节点不参加可写结构投影。

### 6.2 通用 AST

AST 只有两类语句：

- `Directive{Name, Arguments, Span, TerminatorSpan}`。
- `Block{Name, Arguments, Children, Span, OpenBraceSpan, CloseBraceSpan}`。

Document 持有不可变 source、完整 token 列表和顶层 statement。trivia 不被丢弃或重建；它仍由 source 拥有。`Document.Render()` 在没有 edit 时直接返回原 source。

局部渲染器只接受经 parser 产生、互不重叠的 span edit。edit 按 byte offset 逆序拼接，验证每个 span 位于同一 source 且未重叠。新片段使用目标文件已检测到的 LF/CRLF 和父 block 的实际缩进；无法唯一推导缩进时使用同级第一个 statement 的缩进，再回退为父缩进加四个空格。

不做 whole-file pretty print。修改 block header、单个 `server`/`proxy_pass` directive、插入或删除 block 都只触及各自 span 和必要的相邻空白；注释不会因“看起来属于目标”而被猜测性搬移。删除默认保留目标前方独立注释，只有与目标处于同一行的尾随空白进入删除 span。

### 6.3 解析上限

解析沿用 workspace 的 2 MiB 单文件、4096 条目和 32 MiB 受管文本上限，并增加：

- 单文件最多 200,000 token、50,000 statement、128 层 block。
- 一个 directive/block 最多 1024 个参数。
- include 展开最多 64 层、每个物理文件最多 64 个上下文实例。
- 一个结构投影最多 10,000 upstream/server/location 节点和 20,000 条诊断。

达到上限返回 `STRUCTURED_LIMIT_EXCEEDED`，不返回部分结构并伪装为完整。

## 7. 跨文件项目与身份

`config.Service` 在共享锁下返回一个已验证的 `DraftSnapshot`：workspace 身份、draft ETag、稳定排序的受管文件内容、entry 摘要和已有 include dependency。snapshot 只驻留当前请求内，不写 SQLite 或长期缓存。

project builder 从 `nginx.conf` 开始，按 AST 中 include 的 source path + line + column 与 workspace dependency 对齐，并把被包含文件的顶层 statement 视为出现在 include 所在上下文。它不自行访问磁盘、不重新展开 glob，也不读取 external/sensitive 条目。

- 同一物理节点只生成一个 physical ID；ID 由 schema、相对 path、source span、节点种类和 header 摘要计算为不透明 lowercase hex。
- 节点可记录多个 include context path。全部上下文一致时只展示一次并列出来源计数。
- 同一节点在不同语义上下文出现时标记 `ambiguous_context` 并只读。
- include 缺失、external、循环、无法绑定或解析失败产生 project diagnostic；影响目标语义完整性时禁止相应变更。
- 未被入口 include 图加载的受管文件可在原始编辑器中读取，但不作为“有效 HTTP 结构”展示。

API 公开相对 path、起始/结束行列和 opaque ID，不公开 byte offset、内部工作区路径或 include 的绝对解析路径。ID 只在对应 draft ETag 下有效；ETag 改变后客户端必须刷新投影。

## 8. Upstream 模型与操作

### 8.1 读取模型

只把 `http` 上下文直接子级的 `upstream <name> {}` 识别为 HTTP upstream。模型包含：

- opaque ID、名称、相对文件/source location、只读原因。
- 稳定排序的 `server` 行。
- 其他 directive/block 的数量和原始名称列表，不返回其正文。
- direct references、dynamic/unknown reference analysis 状态和诊断。

`server` 第一参数识别 domain/IP + 可选端口、方括号 IPv6 + 可选端口或 `unix:` socket。端口缺省在模型中保持 `null`，不擅自写入默认 80。可编辑字段为：

- `address`、可选 `port`。
- 可选正整数 `weight`。
- `backup`、`down`。
- 可选非负整数 `max_fails`；0 保留“禁用失败计数”语义。
- 可选有界 Nginx time literal `fail_timeout`。

其余参数按原始 token 顺序进入 `preserved_parameters`。更新一条 server 时必须原样带回这些参数；重复的已识别参数、互相冲突的 `backup`/`down` 或无法无歧义解析的 server 行标记为 raw-only，不能用结构表单覆盖。

upstream 名称和新地址采用保守正向校验：有效 UTF-8、无控制字符/空白/引号/`;{}`/变量，名称 1–255 bytes。地址接受合法 hostname、IPv4、IPv6 或非空 `unix:` path；端口为 1–65535。超出该正向集合的已有配置仍可读取并 raw-edit，不被自动“修正”。

### 8.2 引用分析

只把参数数量为 1、scheme 为 `http`/`https`、不含变量/用户信息且 authority 可唯一分离的 `proxy_pass` 识别为 direct reference。authority 的 host 与 upstream 名称精确匹配时建立引用；可选端口和 URI 保持原样。

含变量、无法分离 authority、Unix Socket URL 或多个参数的 `proxy_pass` 标记为 reference analysis incomplete。由于变量可能在运行时形成任意 upstream 名称，只要项目内存在这种表达式，upstream rename/delete 就 fail closed 并返回相关位置。普通 create 和 server 行编辑不受该全局限制。

重命名更新 upstream header 和所有 direct reference 的 authority，仅替换 host 名称，保留 scheme、端口、URI、引号和目标 directive 之外内容。删除在 direct reference 非空时返回 `UPSTREAM_REFERENCED`，并列出有界相对位置。

### 8.3 操作

- `upstream.create`：在选定、可写且上下文唯一的 `http` block 关闭花括号前插入 block；至少包含一条 server。
- `upstream.rename`：名称唯一、引用分析完整，并以一个批量草稿事务更新 header 和 direct references。
- `upstream.delete`：名称具名确认、无 direct reference、引用分析完整；删除目标 block。
- `upstream_server.create/update/delete`：只修改目标 upstream 内的单个 server directive；删除最后一个可用 server 时拒绝。

存在重复 upstream 名称时两者都保持可读但相关 rename/delete/create 被阻止；系统不猜测 `proxy_pass` 指向哪一个。

## 9. Server、Location 与 proxy_pass

### 9.1 读取模型

只把 `http` 上下文直接子级的 `server {}` 识别为 HTTP server。展示 opaque ID、相对位置、`listen`/`server_name` 的有界摘要和 location 树。v0.3 不结构化编辑 listen/server_name；原始编辑入口继续可用。

location 类型映射：

| source | 类型 |
| --- | --- |
| `location = <uri>` | `exact` |
| `location <uri>` | `prefix` |
| `location ^~ <uri>` | `prefix_priority` |
| `location ~ <regex>` | `regex` |
| `location ~* <regex>` | `regex_insensitive` |
| `location @<name>` | `named` |

参数数量或组合不符合上述形式时节点 raw-only。matcher 保留解码值和原始 token；未修改时不重写引号或转义。

每个 location 展示其直接子 location、直接 `proxy_pass` 投影、unknown directive 数量、source location 和 diagnostics。继承的 `proxy_pass` 不伪装为本 block 自有值；同一 block 多个直接 `proxy_pass` 标记 raw-only。

### 9.2 合法性与诊断

结构化写入至少执行以下可证明规则：

- named location 只能是 server 直接子级，且不能包含 location。
- exact location 不能包含 location。
- nested location 不能是 named。
- plain/exact/`^~` 子 URI 必须位于可证明的父 prefix URI 范围内；否则拒绝。
- regex matcher 非空且能由 Go regexp 做基础语法检查；Go 与 PCRE 不等价，因此通过只表示基础静态检查，最终仍以 Nginx 校验为准。
- 同一 parent 下相同类型和 matcher 产生 `LOCATION_DUPLICATE`。
- exact/named 下已有子级、父前缀之外的 literal child 等产生 `LOCATION_UNREACHABLE` 或 blocking diagnostic。
- 同一 parent 有多个 regex/regex-insensitive 时按源顺序产生 `LOCATION_REGEX_ORDER_SENSITIVE`，不声称哪一条一定命中。
- direct proxy_pass host 没有对应唯一 upstream 时产生 `UPSTREAM_REFERENCE_DANGLING`。
- variable/unknown proxy_pass 产生 `UPSTREAM_REFERENCE_DYNAMIC`，只读展示而不猜测。

warning 不自动改写用户配置。blocking diagnostic 阻止会触及相关节点的结构化变更；不相关、上下文完整的节点仍可操作。

### 9.3 操作

- `location.create`：parent 为 server 或允许嵌套的 location；插入一个带可选 direct proxy_pass 的 block。
- `location.update`：修改 matcher，并选择 `preserve`、`set` 或 `remove` direct proxy_pass；其他 children/directive 原样保留。
- `location.delete`：要求完整可见 matcher 具名确认，删除该 block 及其 children。

`set` proxy_pass 只接受 upstream opaque ID、`http|https` scheme、可选端口和可选 URI。服务端从当前 project 取真实 upstream 名称并安全编码；浏览器不能提交任意 URL。`remove` 只在当前 block 恰有一个可证明的 direct proxy_pass 时可用。

## 10. 结构化预览与草稿事务

### 10.1 预览

预览是纯计算资源：读取 verified snapshot，解析 project，校验显式 tagged operation，生成 non-overlapping edits，重新解析全部变更文件并重新建立 project。只有前后结构满足目标不变量才返回成功。

响应包含：

- `preview_id`、workspace ID、draft ETag、operation kind。
- 稳定排序的 changed files：相对 path、before/after digest、完整 unified patch。
- 目标摘要、诊断和结构化检查说明。
- `complete`；patch 达到现有 4 MiB 响应上限时为 false，并禁止应用。

preview 不持久化、无过期计时；它只在绑定 ETag 与规范操作仍相同时可重现。preview ID 使用带长度前缀的 canonical binary 编码计算 SHA-256，不依赖 JSON map 顺序。

### 10.2 应用

应用请求重新提交同一个显式 operation 和 `preview_id`，并携带强 `If-Match`。服务端在当前 snapshot 上完整重算；preview ID、ETag、changed files 或生成摘要任一不同均拒绝。客户端 patch 和生成文件从不作为输入。

单文件和多文件统一调用 `config.Service.ReplaceFiles`。该事务：

1. 在 workspace 独占锁下复核状态、attention、production digest 和 ETag。
2. 验证所有 path 已受管、互异，内容符合 UTF-8/NUL/容量策略。
3. 持久化 before contents、before/after manifest 和 batch journal。
4. 按相对 path 稳定顺序逐文件原子 replace，并验证完整 after digest。
5. 原子提交 SQLite workspace revision 与一条结构化 audit summary。
6. 提交 control manifest/state 后清理 recovery。

崩溃发生在 SQLite 提交前时，启动对账用逐文件 before contents 恢复整个 batch 并验证 before digest；提交后只接受完整 after digest。无法证明任一端时进入现有 `needs_attention`。不把部分文件状态报告为成功。

审计 action 使用稳定 operation kind、path count、before/after digest、preview ID 和目标 opaque ID；不记录 patch、完整操作字段、地址、URI 或配置正文。

## 11. REST API

### 11.1 资源

| 方法与路径 | 语义 |
| --- | --- |
| `GET /api/v1/config/workspaces/{id}/structured-config` | 读取当前 ETag 下的 HTTP/upstream/server/location 投影与诊断 |
| `POST /api/v1/config/workspaces/{id}/structured-change-previews` | 纯计算结构化变更预览 |
| `POST /api/v1/config/workspaces/{id}/structured-changes` | 复核 preview 并应用草稿事务 |

GET 与 preview 需要认证；preview 因接收非幂等意图描述仍要求同源 Origin 和 CSRF，确保接口不能被跨站滥用为配置内容 oracle。application 还必须携带单个强 `If-Match`。全部响应 `Cache-Control: no-store`。

application 成功返回 200、更新后的 workspace DTO、draft ETag、changed path 摘要和刷新后的相关 opaque IDs。它只表示草稿已更新，不返回“配置有效”或自动启动 publish check。

### 11.2 DTO 约束

- 所有请求 `DisallowUnknownFields`、拒绝 duplicate JSON key、body 有界。
- operation 使用 `kind` discriminator 和每种操作独立 DTO；未知 kind 返回 `invalid_request`。
- 数值、bool 和 null 不做字符串宽松转换。
- source location 只含 `path`、`start_line`、`start_column`、`end_line`、`end_column`。
- list 始终非 null、按 source path/offset 或显式父子顺序稳定排序。
- preserved unknown 只返回名称、参数数量和 `editable:false`，不通过目录 API复制其完整正文。

### 11.3 稳定错误

| HTTP | code | 场景 |
| --- | --- | --- |
| 422 | `STRUCTURED_PARSE_FAILED` | 目标项目存在影响操作的词法/语法错误 |
| 413 | `STRUCTURED_LIMIT_EXCEEDED` | token/node/context/diff 上限 |
| 409 | `STRUCTURED_PREVIEW_STALE` | preview ID、operation 或 ETag 不匹配 |
| 409 | `STRUCTURED_CONTEXT_AMBIGUOUS` | include 使目标上下文不唯一 |
| 409 | `STRUCTURED_EDIT_CONFLICT` | span 重叠、目标身份变化或 reparse 不一致 |
| 422 | `UPSTREAM_INVALID` | 名称、server 地址或参数非法 |
| 409 | `UPSTREAM_DUPLICATE` | 名称不唯一 |
| 409 | `UPSTREAM_REFERENCED` | 删除目标仍有 direct reference |
| 409 | `UPSTREAM_REFERENCE_INCOMPLETE` | dynamic/unknown proxy_pass 使 rename/delete 无法安全判定 |
| 422 | `LOCATION_INVALID` | matcher、parent 或嵌套组合非法 |
| 409 | `LOCATION_DUPLICATE` | 同 parent 相同规则 |
| 422 | `PROXY_PASS_INVALID` | upstream/scheme/port/URI 选择非法 |

继续复用 workspace conflict/stale/published/needs-attention、attention unresolved、Agent unavailable 和 timeout 错误。details 白名单只允许 opaque ID、相对 source location、当前 ETag、diagnostic code、limit name/value 和引用计数。

## 12. 前端信息架构与交互

新增两个工作区子路由：

- `/config/workspaces/:workspaceId/upstreams`
- `/config/workspaces/:workspaceId/servers`

页面共享当前 workspace identity，但不把 AST 写入全局持久 store。路由切换或 ETag 变化取消旧读取、清除 preview，并重新取得完整投影。

Upstream 页面使用 master-detail：左侧 bounded upstream 列表，右侧显示 server 表单、保留项提示、引用和诊断。Server/Location 页面先选择 server，再显示可键盘导航的 location tree 与详情表单。两页都持续显示：

- 工作区名称/state 与“Draft only — full Nginx validation has not run”。
- 当前结构诊断、raw-only 原因和“Open raw editor”入口。
- dirty 表单状态；切换目标前需要明确丢弃，不自动保存。

每个 mutation 先打开 `structured-change-review`：展示 changed file summary、完整 unified diff、warning 和“仅更新工作区草稿”的明确文案。`complete:false`、blocking diagnostic、ETag 变化或未确认风险时 Apply 不可用并有可见原因。成功后刷新 workspace/catalog；冲突保留表单值和 preview 内容供复制，但不能自动重放。

删除 upstream/location 和 upstream rename 使用具名确认；删除 upstream 还持续展示所有引用位置。toast 只用于非关键成功，parse/conflict/stale/needs-attention 和引用阻止保持 inline。

## 14. 日志、审计与敏感信息

HTTP 边界记录 `request_id`、workspace ID、operation kind、target opaque ID、path count、result 和 duration。领域包不重复记录错误。日志和审计禁止包含：

- 配置正文、完整 patch、unknown raw 参数或生成后的文件。
- upstream 地址、proxy URI、Header 值、变量展开或用户确认输入。
- 绝对生产/workspace 路径、byte span、临时 recovery 路径。
- Cookie、Authorization、CSRF 或原始请求 body。

结构化投影和 preview 不写普通审计；只有成功 application、被安全边界拒绝的关键 mutation 和 workspace needs-attention 转换记录审计元数据。

## 15. 测试策略

所有新行为先有失败测试。parser 和 renderer 以 package unit/golden/fuzz 为主，领域服务使用真实 workspace fixture，最终配置有效性由真实 Nginx 集成测试证明。

### 15.1 tokenizer、AST 与 project

- whitespace、CRLF、注释、单/双引号、转义、变量、regex、空 block、深层 block。
- 未闭合 token、缺失 terminator、额外 brace、上限和精确 source location。
- no-op byte equality、单 directive/block 插入/替换/删除、非目标字节 equality。
- render 后 reparse 结构相等；golden 覆盖不同缩进、行尾和未知模块指令。
- include glob dependency 对齐、嵌套 include、循环、missing/external、同文件多上下文和歧义。
- fuzz 断言不 panic、成功 parse 的 token raw 拼接等于输入、edit 不越界。

### 15.2 upstream 与 location

- upstream IPv4/IPv6/domain/Unix Socket、端口、六个计划参数、unknown 参数保留。
- create/rename/delete/server CRUD、duplicate、direct/dynamic/dangling references。
- rename 跨文件更新只改变 upstream name 与 direct proxy_pass host。
- exact/prefix/`^~`/`~`/`~*`/named 正反例，nested legality 和全部 warning code。
- proxy_pass 带/不带 URI、端口、变量、external host、重复 directive 和 raw-only。
- 任何 preview 应用后重新 parse/catalog，目标外 source 保持不变。

### 15.3 workspace、API 与故障

- `ReplaceFiles` before/after digest、ETag、容量、stable order、重复 path 和审计。
- 每个 batch journal checkpoint 崩溃后得到完整 before、完整 after 或 needs-attention，不出现部分成功。
- API auth/Origin/CSRF/If-Match、strict JSON、no-store、错误 details 白名单。
- preview deterministic、stale、tampered operation、incomplete diff 和并发 mutation。
- 应用前后生产摘要、Nginx master/worker 和服务响应不变。

### 15.4 前端与浏览器

- Upstream/server/location browse、表单、preview、apply、conflict 和 raw fallback。
- 具名 delete/rename、引用阻止、dynamic/raw-only、parse error 和 stale/needs-attention。
- tree/list/drawer/modal/task tabs 全键盘操作、焦点恢复和 local live region。
- 1068/833/734/640/480/320px、200% zoom、400% reflow、无页面横向溢出。
- localStorage/IndexedDB/Cache/URL/日志中不存在配置或表单正文。
- 真实 Nginx fixture 经结构化变更、publish check 和安全发布链路通过；Docker 仍不执行。

## 17. 实施切片

实施按以下可独立验证的顺序推进：

1. **版本与 lossless 基础**：同步 0.3.0 版本，交付 tokenizer、AST、span、renderer、golden/fuzz。
2. **跨文件只读投影**：verified draft snapshot、include context、upstream/server/location catalog 与 diagnostics。
3. **可恢复结构化事务**：`ReplaceFiles` batch journal、preview identity、API preview/application。
4. **Upstream 闭环**：upstream/server CRUD、direct reference、跨文件 rename 和删除保护。
5. **Location 闭环**：六类 matcher、nested legality、proxy_pass selection 和 warnings。
6. **前端与验收**：先扩展 `DESIGN.md`，再实现双页面、API client、组件/浏览器测试和发布链路复验。

每个切片都保持工作树可测试；不得为等待 UI 而跳过领域测试，也不得用临时 whole-file formatter 代替 span renderer。
