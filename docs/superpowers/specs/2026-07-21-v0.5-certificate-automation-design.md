## 1. 文档目的

本文是 v0.5.0 的唯一设计规格，定义 ACME 账户、HTTP-01、Cloudflare API Token DNS-01、证书签发与续期、Nginx server 绑定、失败恢复、SQLite、REST/SSE 和前端交互边界。实现和验收记录必须引用本文；若范围或安全边界改变，先更新本文与 `PLAN.md`。

本版本沿用 v0.2.1–v0.2.3 的配置工作区、完整候选校验、不可变备份、原子发布、reload、健康确认和恢复能力。证书领域不得另造绕过该闭环的生产配置写路径。

## 2. 用户结果与完成标准

管理员能够：

1. 查看固定的 Let's Encrypt staging/production 目录与当前服务条款。
2. 创建、导入和停用环境隔离的 ACME 账户。
3. 保存只具备目标 Zone 权限的 Cloudflare API Token；Token 提交后不再回显。
4. 使用 HTTP-01 申请单域名或 SAN 证书。
5. 使用 Cloudflare DNS-01 申请单域名、SAN 或通配符证书。
6. 在执行前查看会写入 Nginx 的逐文件差异，并明确确认目标 server。
7. 完成签发、严格校验证书、版本化保存、完整 `nginx -t`、备份、原子配置发布、reload 和运行确认。
8. 查看到期时间、绑定、任务阶段、清理证据、续期历史和下一次自动续期时间。
9. 手工续期、启停自动续期、解绑、受控导出，以及在无引用后删除证书。

完成标准不是“ACME 返回成功”，而是证书文件、配置引用、运行时状态、清理结果和持久化元数据能够一致判定。任何不能安全判定的结果进入 `needs_attention`，不得报告成功。

## 3. 范围

### 3.1 包含

- RFC 8555 ACME v2。
- 固定的 Let's Encrypt staging 与 production directory URL。
- ECDSA P-256 ACME 账户密钥和默认 ECDSA P-256 证书密钥；导入兼容受支持的 RSA/ECDSA PKCS#8、EC 或 PKCS#1 PEM 私钥。
- ACME 账户创建、导入、服务条款确认、联系邮箱和停用。
- HTTP-01 临时精确 location、事务化发布和事务化清理。
- Cloudflare user API Token；Zone Read + DNS Write 最小权限提示、Token active 验证、最长 Zone 后缀解析、TXT 创建、权威 DNS 传播检查与精确记录 ID 删除。
- DNS-01 通配符证书。
- 单域名与最多 100 个唯一 SAN；域名规范化、IDNA ASCII、长度与 wildcard 约束。
- staging 预检；production 计划默认要求相同标识符和挑战方式在 24 小时内有成功 staging 证据。
- 版本化证书文件、绑定、发布、续期、抖动、退避、取消、重启对账和审计。
- 本地 ACME 测试服务与 fake Cloudflare API，不访问 production 配额。

### 3.2 不包含

- Cloudflare Global API Key、API Email + Key、Origin CA Key 或任意自定义 Header。
- Cloudflare 之外的 DNS 服务商、通用 provider 接口注册表、插件、脚本、webhook 或任意命令。
- TLS-ALPN-01、external account binding、ARI、OCSP 管理、私有 CA、自签名证书生成或证书购买。
- 多节点证书分发、集群锁、Kubernetes Secret、宿主机证书扫描或 Docker Socket。
- 自动改变 DNS A/AAAA/CNAME、Cloudflare proxy 状态或 Nginx HTTP→HTTPS 跳转策略。
- 自动撤销尚未过期的证书；v0.5 删除只删除本地无引用材料和元数据。
- Docker 构建、卷升级与多架构运行验证；这些仍由 v0.7.0 统一完成。

## 4. 不可违反的安全与数据不变量

1. 账户私钥、证书私钥、Cloudflare Token、HTTP key authorization 和 DNS TXT value 不进入普通日志、审计详情、SQLite JSON、SSE、URL、浏览器持久化、配置 diff 或 API 错误。
2. Secret 请求 Body 只在认证、Origin、CSRF、Content-Type、长度和 strict JSON 校验之后解析；禁止记录 Body。
3. Cloudflare Token 只接受 `Authorization: Bearer` 出站，固定到 `https://api.cloudflare.com/client/v4`；不跟随 redirect、不使用环境代理、不发送 Cookie。
4. Token 以 AES-256-GCM 密文持久化；独立 32-byte master key 使用 `0600`，凭据 ID 与 schema version 作为 AAD。API 只返回 SHA-256 指纹前缀和验证时间。
5. ACME 账户密钥和证书私钥只以 `0600` 原子写入；目录无 symlink 且为 `0700`。证书链也默认 `0600`，不扩大权限。
6. 所有路径由固定 certificate root 与服务端生成的 32 位 opaque ID 推导；API 不接受绝对路径、相对路径、文件名或命令参数。
7. HTTP-01 只发布 exact `/.well-known/acme-challenge/<token>` location；token 和 key authorization 必须满足 ACME base64url 约束，生成内容不得被解释为 Nginx 语法。
8. DNS-01 只删除任务持久化的 `zone_id + record_id`；不得按名称批量删除，不得删除用户已有同名 TXT。
9. wildcard 只允许最左单标签 `*.`，且必须使用 DNS-01；HTTP-01 请求含 wildcard 时 fail closed。
10. production 证书部署前必须验证 SAN 精确集合、有效期、密钥匹配、签名链编码和当前时间；任何偏差不写活动引用。
11. 新版本使用不可变版本目录。配置发布成功前旧证书文件与旧配置引用不变；失败或回滚继续使用旧版本。
12. Nginx 绑定只通过现有工作区、完整候选 `nginx -t`、备份、原子发布、reload 与健康确认链路；证书包不直接写 `/etc/nginx`。
13. HTTP challenge 临时配置和 Cloudflare TXT 无论成功、失败、超时、取消或 UI 重启都必须尝试清理。不能确认清理时为 `needs_attention` 并保留精确处置证据。
14. production 签发默认需要 staging 预检证据；只有显式、审计的精确确认可以重跑 production，不能静默消耗配额。
15. 一个证书任务有唯一 owner、取消路径、阶段上限和总超时；浏览器断开或 SSE 重连没有取消语义。

## 5. 总体架构

```text
Vue Certificate UI
        |
        v
httpapi certificate boundary
        |
        v
internal/certificate
  account service ─── ACME client adapter ─── Let's Encrypt / local ACME
  credential vault ─ Cloudflare client ────── Cloudflare / fake API
  order service ───── challenge provisioners
        |             ├── HTTP workspace + release transaction
        |             └── DNS exact-record lifecycle
        ├── certificate filesystem vault
        ├── binding planner + config workspace/release
        └── scheduler + durable task state
                     |
                     v
                  store/SQLite
```

`internal/certificate` 按消费方定义小接口：

- `Repository`：账户、凭据元数据、计划、证书、版本、绑定、任务、阶段和 challenge artifact。
- `WorkspaceManager`：创建/读取/批量替换/创建或删除受管文件/删除内部工作区。
- `Publisher`：完整候选检查、排队、同步执行和读取最终 release。
- `ProductionInspector`：配置摘要与结构化 `nginx -T` 快照。
- `ACMEClient`：目录、账户、order、authorization、challenge、finalize 的窄适配面。
- `DNSProvider`：v0.5 只有一个具体 `CloudflareClient`；不公开注册机制。
- `SecretVault`：固定根、原子文件和 Token AEAD。

接口定义在 `certificate` 消费方；构造函数返回具体 `*Service`。不使用可变包级状态、Service Locator 或带副作用的 `init()`。

## 6. 固定目录、权限与原子写

固定 root 为 `/var/lib/nginx-uix/certs`，应用配置和 API 均不能覆盖。布局：

```text
certs/                                      0700
  master.key                               0600
  accounts/<account_id>/account.key        0600
  credentials/<credential_id>.token        0600 (AES-GCM envelope)
  certificates/<certificate_id>/
    versions/<version_id>/
      fullchain.pem                         0600
      privkey.pem                           0600
      leaf.pem                              0600
  staging/<task_id>/                        0700
    privkey.pem                             0600
    issued-chain.pem                        0600
```

每次写入使用目标同目录的随机临时文件，`O_CREATE|O_EXCL|O_NOFOLLOW`、精确 mode、写入、`fsync(file)`、close、再次 `lstat`、rename、`fsync(directory)`。不得覆盖非 regular、symlink、link count 异常、owner/mode 异常或不属于预期 ID 的路径。

证书版本目录只有在内容全部写入并重新解析验证后才可进入 `ready`。未被配置引用的失败 staging 目录可清理；发布结果不确定时必须保留新旧版本，避免删掉真实运行时可能引用的材料。

## 7. 领域模型

### 7.1 ACME Account

- `id`、`environment`、`directory_url`、`account_uri`、contact email、status。
- `terms_url`、`terms_agreed_at`、`terms_agreed_by`。
- `key_path` 只在领域内部持有，DTO 不含路径。
- staging 与 production 账户严格分离；同一 key 不跨环境复用。

### 7.2 DNS Credential

- `id`、固定 provider=`cloudflare`、display name、token fingerprint、状态、verified_at、last_used_at。
- 密文文件路径由 ID 推导，不入 API。
- 删除前检查证书续期配置和活动 task 引用。

### 7.3 Certificate

- stable certificate ID、规范化标识符集合、challenge type、目标 account、可选 staging account/Cloudflare credential。
- lifecycle：`pending`、`active`、`expiring`、`expired`、`unbound`、`needs_attention`、`deleted`。
- active version、not_before/not_after、serial fingerprint、issuer summary、自动续期开关、renew_before、next_renewal_at、retry_count/retry_at。
- 不保存 PEM、私钥、Token、完整 ACME problem detail。

### 7.4 Binding

Binding 保存服务端生成的 `server_ref`：相对配置路径、server block 起始位置、规范化 server_name/listen 摘要和稳定指纹。每次发布前在最新生产快照重新解析，必须精确匹配唯一 HTTP server；不存在或歧义则拒绝，不能猜测或按数组下标绑定。

### 7.5 Plan 与 Task

计划在任何网络签发或生产变更之前持久化：标识符、环境、挑战方式、账户/凭据引用、server refs、目标证书/version ID、生产摘要、完整绑定 diff 和十分钟 expiry。执行要求精确确认 primary identifier；production 还要求 staging 证据或明确的补充确认。

任务状态：`queued`、`running`、`cancelling`、`succeeded`、`failed`、`cancelled`、`needs_attention`。每个状态变化与 stage 在一个 SQLite 事务中写入，stage 最多 512 条。

## 8. ACME 账户生命周期

固定目录：

- staging：`https://acme-staging-v02.api.letsencrypt.org/directory`
- production：`https://acme-v02.api.letsencrypt.org/directory`

创建流程：Discover → 展示/比对 Terms URL → 要求显式 `terms_of_service_agreed=true` → 生成 P-256 key → Register → 验证 account URI/status → 原子保存 key → 同事务保存元数据与审计。任何一步失败均删除未注册到本地元数据的临时 key；远端已创建而本地落盘失败时返回可操作的导入说明，不伪报成功。

导入流程只接受有界 PEM private key，请求内存解析后调用 `GetReg`，确认 environment、account URI 和 status，再原子保存。导入 Body、key、JWK、thumbprint 不进入日志。

停用先在 SQLite 事务中把 `valid` 原子转换为 `deactivating` 并审计，因此新签发和续期立即 fail closed；随后调用 ACME `DeactivateReg`，成功后使用脱离请求取消的有界提交把状态转换为 `deactivated`。远端调用或本地完成提交失败时保留 `deactivating`，API 返回 `needs_attention`，由管理员重试或修复，绝不退回 `valid`。有活动 task 时拒绝；已有证书继续展示，但自动续期暂停并说明需更换账户。`deactivated` 使用独立稳定错误码，不能与未知或损坏账户混为一类。

## 9. Cloudflare API Token

创建凭据时：

1. strict JSON 接受 display name 与 `api_token`，最大 512 bytes，拒绝 CR/LF/NUL/前后空白。
2. 使用固定 client 调用 `/user/tokens/verify`，要求 active。
3. 调用 `GET /zones?status=active&per_page=50` 验证 Zone Read，并确认至少一个 active Zone。
4. UI 明确提示 Token 应限制为目标 Zone，权限只需要 Zone Read 与 DNS Write。
5. 生成 fingerprint、AEAD 加密并原子写密文；SQLite 只保存非秘密元数据。

Cloudflare client 只实现：verify token、按 exact name 列 Zone、创建 TXT、读取 TXT、删除 exact record。API response 有 1 MiB 上限、10 秒 header timeout、30 秒操作 timeout，严格检查 HTTP 状态、`success`、errors 数量、ID 长度和 exact echo。错误转换为稳定 code，不回显 Cloudflare 原始请求、Token、TXT value 或不受限 message。

Zone 解析从去除 wildcard 的完整域名开始逐标签向上，选择 Token 可见且 active 的最长 exact Zone；不使用公共后缀猜测。TXT name 为 `_acme-challenge.<authorization identifier>`。记录 TTL 使用 Cloudflare automatic (`1`)，`proxied=false`，并带不含 secret 的 task comment。

创建后保存 exact `zone_id + record_id + record_name` artifact，再等待 Cloudflare 返回记录且至少一个该 Zone 的权威 nameserver 查询到目标 TXT。传播超时不 Accept challenge；清理只按 record ID。

## 10. HTTP-01 challenge 事务

HTTP-01 计划要求每个非 wildcard identifier 至少匹配一个已选 server ref。匹配只用于预检；真实 ACME 仍由 CA 从公网验证。

收到所有 pending authorization 后，服务生成一个受管 fragment：

```nginx
location = /.well-known/acme-challenge/<validated-token> {
    default_type text/plain;
    return 200 "<validated-key-authorization>";
}
```

fragment 使用任务 ID 命名并位于受管 Nginx 根内。系统工作区把固定 absolute include 追加到每个目标 server，随后执行完整候选检查、备份、发布、reload 与健康确认。只有 release `succeeded` 才 Accept ACME challenges。

验证结束后，无论结果如何，创建最新生产快照的第二个系统工作区，按 exact include path 删除所有任务 include 并删除 fragment，再执行同样的发布闭环。清理不得恢复整份旧配置，因此可以保留 challenge 期间出现的其他合法生产变更。清理 release 失败、回滚或无法判定时 task 为 `needs_attention`。

系统工作区名称以 `ACME HTTP challenge <task-id-prefix>` 开头，普通工作区 API 标记为 system-owned 且不可由用户编辑；终态后删除其工作树和元数据，审计与 release 证据保留。

## 11. DNS-01 challenge 事务

DNS-01 对每个 pending authorization：计算 TXT value → 最长 Zone 解析 → create TXT → 持久化 exact artifact → 权威传播等待。所有记录均 ready 后才逐个 Accept；任一失败先清理所有已创建记录。

同一 SAN order 可能对 apex 与 wildcard 产生同名 `_acme-challenge` 多值 TXT。每个 challenge 使用独立 record ID，允许同名多记录；清理逐 ID，不覆盖或合并用户记录。

取消、超时和重启对账使用不含 TXT value 的 durable artifact 找到记录；解密对应 credential 后删除。若 Token 已被撤销、权限丢失或记录状态不可判定，保留 artifact 并进入 `needs_attention`。

## 12. 签发、证书验证与文件提交

order ready 后生成证书 private key 和 CSR。CSR SAN 必须与计划规范化集合完全一致，不使用 Common Name 作为替代。`CreateOrderCert` 返回 DER chain 后：

- 每张 DER 都必须可解析，数量和总大小有界。
- leaf public key 与 staging private key 匹配。
- leaf DNSNames 经规范化后与计划集合精确相等，不允许 CA 返回额外 SAN。
- 当前时间位于 NotBefore/NotAfter 容忍窗口内，NotAfter 晚于 NotBefore。
- leaf 允许 server authentication；基础约束不能为 CA。
- fullchain PEM 只包含 CERTIFICATE blocks，private key 只包含一个 PRIVATE KEY block。

验证后写入预分配 version 目录并重新从磁盘解析。staging 预检证书只记录成功证据后删除，不部署。production 证书进入 `ready`，等待绑定发布成功后成为 `active`。

## 13. Nginx 绑定与部署

绑定 planner 从结构化 production snapshot 解析目标 server：

1. 替换 direct `ssl_certificate` 与 `ssl_certificate_key`；多条或动态参数视为 blocking。
2. 不存在时追加两条指令，路径只使用服务端生成的 active version absolute path。
3. 若没有 TLS listen：已有 plain `listen 443` 时在同一 directive 增加 `ssl`；否则追加 `listen 443 ssl`。不改变重定向、HTTP/2、cipher 或其他 TLS 策略。
4. 只修改目标 block 的 source span，其他注释、空白、未知指令和文件字节保持不变。
5. 计划响应提供完整、受限的逐文件 unified diff；diff 包含证书路径但绝不包含 PEM/key 内容。

执行时重新验证 production digest、server refs、计划 expiry 和 diff identity，再以内部工作区应用同一确定性 edits。发布必须复用 ReleaseService。成功后一个 SQLite 事务切换 active version/bindings/renewal schedule；失败、rolled_back 或 needs_attention 不停用旧 version。

续期使用新 immutable version 目录并把现有 binding 指向新路径。没有 binding 的证书可续期并保持 unbound。解绑只移除确切属于该 certificate ID 的 direct cert/key 指令，不删除 listen 或用户 TLS 设置；引用不明确时拒绝。删除前同时检查数据库 binding 和最新 production AST 的路径引用。

## 14. 续期、抖动与退避

默认 `renew_before=30d`。首次成功后把 `next_renewal_at` 持久化为 `not_after - renew_before + jitter`，jitter 在 `[-12h,+12h]`，从 crypto/rand 取得并在创建时固定，重启不重算。

调度器启动时立即查询一次，之后每小时查询 `next_renewal_at <= now` 或 `retry_at <= now` 的有界集合；按时间、certificate ID 稳定排序，一次最多启动 4 个网络 task，但 production 配置发布仍由现有 lease 串行化。

失败退避为 1h、2h、4h、8h、16h、24h 上限并加 ±10% jitter；ACME `Retry-After` 更晚时采用更晚值。旧证书不被替换。剩余有效期小于 7 天时 UI 为 warning，小于 24 小时且续期失败为 error，但状态仍带文本与图标。

手工续期不能绕过同一账户、challenge、staging policy、文件验证和绑定事务。一个证书最多一个 active task。

## 15. 取消、超时与重启对账

总任务默认 15 分钟；ACME、DNS 传播、配置发布和清理各有更小 timeout。取消是持久化请求：task owner 取消 context，执行器进入 cleanup，只有服务端写入 `cancelled` 才是取消完成。清理失败覆盖普通取消并成为 `needs_attention`。

应用启动时：

- `planned` 且未过期仍可执行；过期转 `failed/plan_expired`。
- `queued/running/cancelling` 不猜测 ACME 成功。先按 durable artifact 清理 DNS 或 HTTP 临时资源，再标记 `failed/interrupted`；清理不确定则 `needs_attention`。
- 已提交且验证的 certificate version 重新从固定路径解析；缺失、symlink、mode 或摘要异常转 `needs_attention`。
- 自动续期计划直接从 SQLite 恢复，不能依赖内存 timer。

## 16. SQLite 与审计

新增单调 migration `0007_certificates.sql`，至少包含：

- `certificate_accounts`
- `certificate_dns_credentials`
- `certificate_order_plans`
- `certificates`
- `certificate_versions`
- `certificate_bindings`
- `certificate_tasks`
- `certificate_task_stages`
- `certificate_challenge_artifacts`

所有 ID 为 32 位 lowercase hex；时间为 UTC RFC 3339 Nano；JSON 有大小上限且只包含安全 DTO。active task、active certificate version、同一 binding 和 task stage sequence 由约束/索引保证唯一。Repository 的复合状态变化使用 `BEGIN IMMEDIATE`，不把文件系统与 SQLite 假装成同一事务；通过 staging/ready/active 状态和启动对账恢复。

通用 `audit_events` 记录 account create/import/deactivate、credential create/delete/verify failure、plan/create/execute/cancel、issue/renew/bind/unbind/export/delete，以及所有 cleanup 结果。详情只含 opaque ID、environment、challenge type、identifier count、server ref count、result/error code、证书有效期和 request ID。

## 17. REST API 与 SSE

所有资源位于 `/api/v1`，经过认证；非幂等请求还经过 Origin、CSRF、strict JSON 和大小限制。

```text
GET    /acme/directories
GET    /acme/accounts
POST   /acme/accounts
POST   /acme/account-imports
POST   /acme/accounts/{account_id}/deactivations

GET    /certificate-dns-credentials
POST   /certificate-dns-credentials
DELETE /certificate-dns-credentials/{credential_id}

GET    /certificate-server-candidates
POST   /certificate-order-plans
GET    /certificate-order-plans/{plan_id}
POST   /certificate-order-plans/{plan_id}/executions

GET    /certificate-tasks
GET    /certificate-tasks/{task_id}
GET    /certificate-tasks/{task_id}/events
POST   /certificate-tasks/{task_id}/cancellations

GET    /certificates
GET    /certificates/{certificate_id}
POST   /certificates/{certificate_id}/renewals
PUT    /certificates/{certificate_id}/renewal-policy
POST   /certificates/{certificate_id}/binding-plans
POST   /certificate-binding-plans/{plan_id}/executions
POST   /certificates/{certificate_id}/unbindings
POST   /certificates/{certificate_id}/exports
DELETE /certificates/{certificate_id}
```

列表使用稳定 `created_at DESC, id DESC` 或 `next_renewal_at ASC, id ASC`，有明确 limit/cursor，不返回无界历史。所有响应 `Cache-Control: no-store`。SSE 支持 `Last-Event-ID`、心跳、stage 序号和重连；心跳不成为 UI live announcement。

私钥导出使用 POST、精确证书 ID 确认和短生命周期流式 `application/x-pem-file`；响应不经过 JSON、压缩或缓存。默认只导出 fullchain；包含 private key 需要第二个明确 boolean 与确认短语，审计只记录 `included_private_key=true`，不记录内容。

## 18. 稳定错误码

至少定义：

- `ACME_TERMS_REQUIRED`、`ACME_ACCOUNT_INVALID`、`ACME_ACCOUNT_DEACTIVATED`
- `ACME_STAGING_PREFLIGHT_REQUIRED`、`ACME_RATE_LIMITED`、`ACME_ORDER_FAILED`
- `CERTIFICATE_IDENTIFIER_INVALID`、`CERTIFICATE_WILDCARD_REQUIRES_DNS`
- `CLOUDFLARE_TOKEN_INVALID`、`CLOUDFLARE_PERMISSION_DENIED`、`CLOUDFLARE_ZONE_NOT_FOUND`、`CLOUDFLARE_UNAVAILABLE`
- `DNS_PROPAGATION_TIMEOUT`、`CHALLENGE_CLEANUP_FAILED`
- `CERTIFICATE_KEY_MISMATCH`、`CERTIFICATE_SAN_MISMATCH`、`CERTIFICATE_FILE_INVALID`
- `CERTIFICATE_SERVER_NOT_FOUND`、`CERTIFICATE_SERVER_AMBIGUOUS`、`CERTIFICATE_BINDING_CONFLICT`
- `CERTIFICATE_REFERENCED`、`CERTIFICATE_TASK_ACTIVE`、`CERTIFICATE_PLAN_EXPIRED`
- `CERTIFICATE_NEEDS_ATTENTION`、`CERTIFICATE_PRIVATE_KEY_CONFIRMATION_REQUIRED`
- `CERTIFICATE_RENEWAL_POLICY_INVALID`、`CERTIFICATE_OPERATION_TIMEOUT`
- `CERTIFICATE_RESOURCE_NOT_FOUND`、`CERTIFICATE_SERVICE_UNAVAILABLE`、`CERTIFICATE_LIMIT_EXCEEDED`、`CERTIFICATE_REQUEST_INVALID`

用户消息可操作且脱敏；内部 ACME/Cloudflare error type、URL path、绝对本地路径、raw response 和 secret 不返回浏览器。

## 19. 前端信息架构与交互

新增 `/certificates` 页面，桌面为证书列表/详情双栏，任务与账户/凭据管理为同页明确 task tabs；手机使用 Overview、Request、Accounts、History task tabs。页面不把 Token、private key、HTTP response 或确认短语写入 URL、`localStorage`、IndexedDB、Cache Storage 或 Service Worker。

申请向导顺序：Identifiers → Challenge → Account/Cloudflare credential → Server bindings → Review diff → Exact confirmation。production 未有 staging 证据时，review 明确阻止并提供 staging preflight 动作。Cloudflare Token 字段使用 password input，提交成功立即清空；凭据列表只显示 display name、fingerprint 和 verified time。

任务页面展示持久化 stage timeline、当前安全消息、取消、challenge cleanup、issued certificate validation、配置 release ID 和最终运行确认。终态结果保持 inline，不用 toast 代替。SSE 断开只显示“正在重新连接”，不取消 task。

所有状态含可见文字和图标/形状；所有控件至少 44×44px；Modal 使用现有 focus trap、Escape、inert background 和 trigger focus restoration。320px/400% reflow 无页面级横向滚动，diff/PEM 只在标记的内部 pane 滚动。

## 20. 日志与敏感信息

结构化日志仅包含 `request_id`/`task_id`、动作、对象 ID、environment、challenge type、阶段、结果、耗时和稳定 error code。禁止记录：

- account key、certificate key、CSR DER/PEM、certificate PEM 正文；
- Cloudflare Token、Authorization、token fingerprint 全值；
- ACME challenge token、key authorization、DNS TXT value；
- secret-bearing request body、export body、Cloudflare raw response；
- 完整 Nginx diff、绝对私有路径或未经脱敏的 ACME problem detail。

## 21. 测试策略

### 21.1 领域与密码材料

- domain/SAN/wildcard/IDNA 规范化表驱动测试。
- account key import、unsupported key、PEM trailing data、key mode/symlink/path traversal。
- AES-GCM round trip、AAD mismatch、ciphertext tamper、master key mode、原子写 fault injection。
- certificate SAN/key/validity/chain 校验正反例。
- jitter、退避、Retry-After、due ordering 和重启后不重算。

### 21.2 Cloudflare

- `httptest.Server` 覆盖 Bearer、无 proxy/redirect/cookie、response limit、token verify、zone longest suffix、pagination bound。
- 同名 TXT 多记录、精确 record ID 清理、部分创建失败、权限撤销、传播超时、取消和重启 cleanup。
- 任何错误和日志断言不含 Token/TXT。

### 21.3 HTTP challenge 与配置发布

- lossless server ref 和 TLS binding edits；目标块外 bytes 不变。
- fragment exact location 与 escaping；无 wildcard。
- challenge publish/cleanup 均走完整 release；清理基于最新 production，不覆盖并发合法变更。
- invalid candidate、reload failure、rolled_back、needs_attention、取消和进程崩溃。
- 真实 Nginx 请求命中 challenge、证书部署后 HTTPS/SNI，前后生产隔离与旧证书回滚。

### 21.4 ACME 集成

- 使用本地 Pebble 或等价 RFC 8555 测试服务，HTTP-01 和 DNS-01 覆盖 create account、order、authorization、finalize、renew。
- 测试 directory 由构造依赖注入，不通过公开环境变量/API 开放任意 CA URL。
- 不读取或消耗 Let's Encrypt staging/production 配额；没有固定测试私钥进入仓库。

### 21.5 Store、API、App

- migration 0.4.0→0.5.0、fresh DB、checksum、重开持久化。
- repository CAS、唯一 active task/version、分页、stage 顺序和 audit 脱敏。
- auth/CSRF/strict JSON/content type/body limit/no-store/SSE reconnect/error mapping/export headers。
- task owner cancellation、scheduler stop、startup reconciliation 和 bounded graceful shutdown。

### 21.6 前端与浏览器

- typed parser/client、向导字段错误、secret 清空、diff review、exact confirmation。
- staging gate、Cloudflare credential flow、task SSE reconnect/cancel、manual renewal、unbind/delete reference block。
- 1069/833/734/640/480/320px、200% zoom、400% reflow、键盘、focus restoration、44px targets、axe。
