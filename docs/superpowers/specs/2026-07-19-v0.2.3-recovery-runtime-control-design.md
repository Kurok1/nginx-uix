## 1. 文档目的

本文把 `PLAN.md` 中 v0.2.3“恢复与运行控制版”细化为可直接实施和验收的产品与技术设计。v0.2.3 在 v0.2.2 已交付的不可变备份、发布 journal、自动回滚和 `needs_attention` 证据之上增加：人工恢复、备份保护与确定性保留、固定类型化 restart、完整配置历史与审计查询，以及人工处置闭环。

本版本不把“管理员操作”降级为任意命令或任意文件访问。浏览器只能提交不透明 ID、受限原因和具名确认；生产根、备份根、可执行文件、命令参数、PID、信号、健康目标和绝对路径仍由 Agent 固定。

## 2. 用户结果与完成标准

管理员能够在新的“恢复与历史”页面完成以下闭环：

```text
查看发布 / 恢复 / restart / 审计历史
  -> 查看备份完整性、来源和保护原因
  -> 选择已验证且仍存在的备份
  -> 具名确认人工恢复
  -> 校验目标备份并创建恢复前安全备份
  -> 持久化恢复意图并替换生产配置
  -> 校验生产配置、reload 并确认运行健康
  -> 成功，或恢复安全备份，或进入 needs_attention

固定 restart
  -> 校验当前生产配置与运行前事实
  -> 请求监督器重启 Nginx
  -> 确认新 master、worker 和回环 HTTP 健康
  -> 成功，或明确失败 / needs_attention

备份保留
  -> 计算稳定、可审阅的保留计划
  -> 跳过所有受保护恢复点
  -> 逐项持久化删除意图并由 Agent 删除正文
  -> 保留 tombstone 与审计证据
```

版本只有同时满足以下条件才完成：

1. 人工恢复只接受 SQLite 中存在、Agent 完整复核通过且正文仍存在的 `complete` 备份。
2. 目标备份在任何生产写入前完成隔离 `nginx -t`；恢复前当前生产树被保存为独立、已验证的安全备份。
3. 恢复使用 durable journal 和逐文件原子替换；失败时从安全备份恢复，无法唯一证明结果时进入 `needs_attention`。
4. restart 只调用固定监督器操作，不接受浏览器提供的命令、路径、PID、signal 或 Nginx 参数。
5. restart 成功要求 master 已更换、worker 稳定、生产配置有效且固定回环 HTTP 健康；命令退出 0 不是成功证据。
6. release、restore、restart 和 retention 共享一个持久化生产变更租约，同一时刻最多执行一个会改变生产或恢复点的任务。
7. 保留计划按稳定顺序运行，不删除当前受保护恢复点、活动任务引用、开放 `needs_attention` 引用、人工保护或最小安全集合。
8. 备份删除保留索引 tombstone、决策原因和审计；数据库失败不能先删除正文，Agent 删除失败不能标记成功。
9. `needs_attention` 工作区与任务保持只读；只有带健康证据的恢复、restart 或固定复核可以关闭 attention case。
10. 历史、备份和审计列表稳定排序、有界分页，不返回配置正文、diff、私有 manifest、绝对路径或敏感摘要。
11. 应用、Agent 或 Nginx 在任务任一阶段退出后，重启对账得到幂等且可解释的终态。
12. UI 在桌面、平板和手机上均可审阅历史、执行具名确认和读取终态，并满足 WCAG 2.2 AA。

## 3. 范围

### 3.1 包含

- 完整 release、restore、restart、retention run 与 audit event 历史查询。
- 备份列表、详情、完整性复核、来源、保护原因、正文存在状态和删除 tombstone。
- 人工保护/解除保护；解除保护要求具名确认并留下审计。
- 基于固定策略的保留计划、dry-run 预览、具名确认执行和逐项结果。
- 从不可变备份执行人工恢复；恢复前目标隔离校验与当前生产安全备份。
- 人工恢复的 Agent journal、进度、崩溃恢复、回滚和 SSE。
- 由 s6 监督器执行的固定 restart、生产校验、超时、取消、进度、健康确认和 SSE。
- `needs_attention` case、证据投影、阻断状态、允许动作和处置结果。
- 固定生产健康复核；只有完整配置、runtime identity 和 loopback probe 全部通过才可解决 case。

- Agent/UI/Nginx 进程终止、备份损坏、端口冲突、持久化失败和原生真实 Nginx 验收。

- 跳过目标校验、跳过安全备份、强制删除受保护备份或“仍然继续”开关。
- 自动修复 Nginx 配置、结构化 AST 编辑、路径实验室或证书生命周期。
- Docker 构建、容器运行、卷、容器升级、Docker 浏览器流程、镜像内容和多架构验证；全部仍由 v0.7.0 统一执行。

## 4. 不可违反的安全不变量

1. `/etc/nginx` 始终是配置真源；SQLite 只保存身份、状态、摘要、索引、阶段和审计。
2. Web/API 进程不能直接读取或写入生产配置、备份正文、Agent journal 或 supervisor 控制目录。
3. restore、restart、backup verify/delete 只通过 Agent 的独立类型化协议操作执行。
4. Agent 请求只含协议版本、request ID、不透明对象 ID、精确摘要与固定枚举；不含根路径、命令或健康目标。
5. 所有生产写入前必须已有可用回退来源；目标备份和安全备份任一不完整都禁止写入。
6. restore 不复用 release 的 workspace/check 授权；它有自己的 ID、journal、阶段、目标和安全备份绑定。
7. restart 不扩展 reload 参数，也不直接向浏览器暴露 s6；固定调用 `/command/s6-svc -r /run/service/nginx`。
8. restart 前真实生产路径必须通过固定 `nginx -t`，失败时不触发 supervisor。
9. 只有当前唯一 master、worker、配置校验和固定回环健康证据一致时才报告运行健康。
10. 所有持久化任务在执行外部副作用前先记录意图，在报告成功前先记录完整阶段证据。
11. 生产变更租约在崩溃后不能被新任务静默窃取；启动对账先恢复/判定原任务，再释放租约。
12. 保留计算使用数据库快照和稳定排序；执行前逐项重新检查保护条件和 Agent 完整性。
13. 删除采用“数据库 deleting 意图 → Agent 删除 → 数据库 deleted tombstone”顺序；中断可重放。
14. `needs_attention` 不是可手工清空的布尔值；处置必须引用一个带终态证据的操作。
15. API、SSE、审计和日志不包含配置正文、diff patch、原始 stderr、绝对路径、命令行、Cookie、CSRF、凭据或私有摘要。

## 5. 总体架构

```text
Browser
  │ session + Origin + CSRF + named confirmation
  │ history / backups / attention / restore / restart / retention
  ▼
nginx-uix Web/API (non-root)
  ├── recovery service
  │   ├── production mutation lease
  │   ├── restore/restart/retention state machines
  │   ├── attention case resolution
  │   └── startup reconciliation
  ├── history repository ── SQLite
  └── typed Agent client
          │ Unix Socket + peer credentials
          ▼
nginx-uix-agent (root)
  ├── backup verifier/deleter
  ├── restore target materializer + isolated validator
  ├── restore journal + production applier + safety rollback
  ├── fixed s6 restart adapter
  └── status + loopback HTTP health verifier
          │
          ├── /etc/nginx
          ├── /var/lib/nginx-uix/backups
          ├── /var/lib/nginx-uix/restores
          └── /run/service/nginx
```

### 5.1 组件边界

| 单元 | 负责 | 不负责 |
| --- | --- | --- |
| `config` recovery service | 授权、租约、状态机、Agent 编排、case 处置、启动对账 | 直接访问生产/备份或执行命令 |
| `runtime` restore | 固定根备份复核、目标校验、安全备份、journal、恢复/回滚 | SQLite、HTTP DTO、用户确认 |
| `runtime` restart | 固定生产校验、s6 restart、master/worker/HTTP 确认 | 任意 supervisor 操作或配置修改 |
| `runtime` retention | 仅按已授权 backup ID 验证并删除固定根对象 | 决定保护策略或数据库状态 |
| `store` | 历史分页、任务/阶段、租约、保护、保留决策、case、审计 | 配置或备份正文 |
| `httpapi` | 认证、Origin、CSRF、严格 DTO、分页、SSE、稳定错误 | 直接调用文件系统或推断成功 |
| Vue operations | 历史投影、具名确认、进度和终态 | 自动重试变更、强制恢复或隐藏风险 |

不创建通用命令执行器、通用 task manager、`utils` 或插件层。release、restore、restart 和 retention 保留独立领域类型，共用的只有小型持久化租约和只读阶段展示语义。

## 6. 持久化布局与权限

```text
/var/lib/nginx-uix/
├── nginx-uix.db
├── backups/<backup-id>/
│   ├── tree/
│   └── control/{manifest.bin,complete.json}
├── releases/<release-id>/control/
└── restores/<restore-id>/
    ├── validation/                 # 临时目标校验副本，终态清理
    └── control/{state.json,events.ndjson}
```

- restore/restart/retention ID 继续使用服务端生成的 128-bit lowercase hex。
- `restores` 由 Agent 建立并验证根身份；目录/文件不高于 `0700`/`0600`。
- 安全备份进入现有 `backups` 根并使用完整不可变格式，来源类型为 `restore`。
- backup complete metadata 升级为兼容读取 v1、写入 v2；v2 使用 `origin_type` + `origin_id`，不再把新备份强绑为 release。
- 旧 v1 备份仍按其中 `release_id` 验证，迁移只扩展索引，不改写正文。
- 删除后的备份目录必须不存在，但 SQLite 索引保留 `deleted`、删除任务、原因、时间、释放字节数和原始来源。

## 7. 生产变更租约

新增单例 `config_production_lease`，持久化 `owner_type`、`owner_id`、`acquired_at`。owner 只允许 `release`、`restore`、`restart`、`retention`。

- 创建任务与获取租约处于同一 SQLite immediate transaction。
- v0.2.2 release 创建也改为获取该租约；原 active unique index 继续作为 release 内部防线。
- 终态与释放租约处于同一事务；租约 owner 必须精确匹配。
- 启动发现租约时先读取对应任务与 Agent journal。只有任务达到可证明终态后才能释放。
- 查询历史不需要租约；候选 publish check 和 backup 只读完整性复核可并行但保持现有上限。

## 8. 备份索引与保护模型

### 8.1 备份状态

```text
creating -> complete -> deleting -> deleted
                  \-> invalid
deleting 可在重放后进入 complete（正文仍完整）或 deleted（正文已确认不存在）
```

普通列表默认展示 `complete`、`invalid` 和 `deleted`；`creating`/`deleting` 只在活动任务或对账证据中展示。任何 `invalid` 备份都不能恢复或解除系统保护。

### 8.2 保护来源

备份在任一条件成立时不可删除：

- 被 active release/restore/restart/retention 引用。
- 是开放 `needs_attention` case 的目标、自动回滚或安全备份。
- 是最近一次成功发布/恢复所需的最后一个可验证恢复点。
- 属于固定最小安全集合：至少保留最近 3 个完整备份。
- 管理员设置人工保护；保护记录含 actor、原因和时间。
- 保留策略 dry-run 已选中但执行时事实变化；该项转 `skipped_protected`。

人工保护不是文件权限替代品。设置或解除只修改索引与审计；备份正文始终保持不可变。解除保护要求输入完整 backup ID，不能解除系统派生保护。

## 9. 确定性保留策略

默认策略固定并由 API 只读展示：

- `minimum_complete = 3`
- `maximum_complete = 20`
- `maximum_total_bytes = 4 GiB`
- `minimum_age = 24h`

v0.2.3 不允许浏览器自定义这些上限。测试通过注入 policy 覆盖空间边界。

候选按 `(created_at ASC, id ASC)` 稳定排序，只从超过 minimum/maximum 且年龄满足的未保护 `complete` 备份中选择。先满足 count，再满足 bytes；同一输入总产生相同计划。dry-run 持久化每项 `keep/delete` 决策与原因，默认 10 分钟过期。

执行要求输入完整 retention run ID。每项删除前重新读取索引、保护引用并调用 Agent `VerifyBackup`；随后按 `deleting -> Agent DeleteBackup -> deleted` 推进。任何单项不确定都停止后续删除并使 run 进入 `needs_attention`，已完成 tombstone 不回滚或伪装未发生。

## 10. 人工恢复事务

### 10.1 请求与前置条件

人工恢复请求包含：target backup ID、可选 attention case ID、受限原因（1–256 个可打印字符）和必须精确匹配完整 backup ID 的 `confirm_backup_id`。

服务在获取生产租约前后分别复核：

- backup 索引为 `complete`、正文存在且未进入删除。
- Agent 完整性证据与索引的来源、生产摘要、条目数、总字节数和验证时间一致。
- attention case（若提供）仍为 open 且允许 restore。
- 没有活动生产租约。
- 当前生产摘要可读取；无法读取时拒绝普通恢复并保留 needs-attention，不猜测覆盖。

### 10.2 目标隔离校验

Agent 将备份 tree 复制到 restore 专用 validation 目录，不使用 hardlink。对固定生产根内的绝对 include 使用与 candidate validator 相同的有界词法重写；变量 include、越界依赖、特殊文件或 build 不一致 fail closed。

目标树通过固定 `nginx -t` 后才继续。诊断只返回稳定 code、备份内相对路径、行号和脱敏摘要。validation 目录在成功、错误、取消和恢复对账后清理。

### 10.3 安全备份与 journal

目标校验后，Agent 为当前生产创建新 safety backup。它必须完成双清单、fsync、freeze、complete marker 和二次摘要检查。服务持久化 safety backup 索引后，Agent 才建立 restore journal 并写生产。

restore journal 至少包含：schema、restore/target/safety backup ID、目标/当前摘要、当前 stage、durable operation、baseline master/workers 和更新时间。

阶段单调推进：

```text
queued
  -> target_verifying
  -> target_validated
  -> safety_backup_creating
  -> safety_backup_verified
  -> files_restoring
  -> files_restored
  -> production_validated
  -> reload_requested
  -> runtime_confirmed
  -> succeeded

任一已写生产后的可恢复失败
  -> rollback_applying
  -> rollback_files_restored
  -> rollback_validated
  -> rollback_reload_requested
  -> rolled_back

证据不唯一
  -> needs_attention
```

文件恢复继续使用同目录临时文件、`fsync`、atomic rename、目录 `fsync` 和稳定操作顺序。目标成功摘要必须等于 target backup 的 production/tree identity；回滚成功摘要必须等于 safety backup identity。

### 10.4 成功和失败判定

恢复成功要求：生产完整摘要等于目标、真实生产 `nginx -t` 通过、reload 成功、原 master 不变、worker 替换且稳定、固定 loopback HTTP 健康。

目标校验或安全备份失败时生产不变，restore 为 `failed`。生产写入后失败则恢复 safety backup；只有摘要、生产校验、必要 reload 和运行健康全部确认后才为 `rolled_back`。任何缺失证据进入 `needs_attention`。

## 11. 固定 restart

restart 请求包含可选 attention case ID、受限原因和固定确认文本 `RESTART NGINX`。请求不接受 PID、signal、command、path、timeout 或 health target。

Agent 固定流程：

1. 获取共享 release lock，读取当前 production digest。
2. 对真实生产路径执行固定 `nginx -t`；失败时不调用 supervisor。
3. 采样当前状态；允许 `running`、`degraded` 或可证明 `stopped`，拒绝 `unknown`/多 master/身份冲突。
4. 持久化 restart stage intent。
5. 固定执行 `/command/s6-svc -r /run/service/nginx`，15 秒命令期限和 1 MiB 输出上限。
6. 最多 45 秒轮询：新 master PID 与旧 master 不同（旧状态为 stopped 时只要求唯一新 master）、至少一个稳定 worker、生产摘要未变化、生产校验通过、固定 loopback HTTP 健康。
7. 记录 new master、worker count、HTTP status 和终态。

阶段为 `queued -> production_validating -> runtime_sampling -> restart_requested -> runtime_confirming -> succeeded`，错误进入 `failed`；命令是否已被 supervisor 接受但运行事实不唯一时进入 `needs_attention`。客户端取消或断开不代表任务取消。

## 12. needs_attention case

case subject 只允许 workspace、release、restore、restart。迁移/启动对账为已有 `needs_attention` workspace/release 创建 open case；未来任务在进入该状态时原子创建 case。

case 展示：case ID、subject 类型/ID、workspace/release/backup 关联、安全 reason code、开放时间、允许动作和引用阶段。证据不包含正文、绝对路径或原始命令输出。

允许的处置：

- 从已验证备份恢复，并把 restore ID 记录为 resolution。
- 固定 restart，并把 restart ID 记录为 resolution。
- 固定“复核当前状态”：production `nginx -t`、唯一 master/worker、固定 loopback HTTP 全部通过后记录 verification ID。

不提供普通 acknowledge、强制关闭或把 workspace 改回 ready。case 解决后原 workspace 仍是只读历史；管理员从当前生产创建新 workspace。每次处置尝试和结果都写审计。

## 13. 历史、SQLite 与迁移

新增 `0004_config_recovery_control.sql`，只新增/重建受影响表，不修改已发布迁移。

### 13.1 持久化概念

| 概念 | 持久化内容 |
| --- | --- |
| production lease | 单例 owner 类型/ID、获取时间 |
| backups v2 | 来源、摘要、状态、大小、人工保护、删除 tombstone |
| restores / stages | target/safety backup、attention、状态、阶段、摘要、actor、原因、时间 |
| restarts / stages | production digest、before/after runtime evidence、状态、actor、原因、时间 |
| retention runs/items | policy、计划过期、稳定 ordinal、决策、执行结果、释放字节 |
| attention cases | subject、关联对象、安全原因、open/resolved、resolution 引用和时间 |
| audit views | 现有 audit event 的 cursor 查询，不复制一份审计事实 |

### 13.2 稳定分页

所有列表使用 keyset cursor，不使用无界 offset：

- 新到旧资源：`(created_at DESC, id DESC)`。
- audit：`(occurred_at DESC, id DESC)`。
- 默认 limit 50，最小 1，最大 100。
- 响应含 `items` 和可选 `next_cursor`；cursor 是版本化、带类型的 URL-safe 编码，不暴露 SQL。

历史 details 只解码白名单 JSON 字段。数据库中旧的安全 details 可以原样用于内部查询，但 API 必须构造显式 DTO，不能直接透传字符串。

| `PUT /api/v1/config/backups/{id}/protection` | 设置/解除人工保护 |

SSE 与 release 保持相同语义：单调 sequence，首次 snapshot，`Last-Event-ID` 续传，`snapshot/stage/terminal/heartbeat` 四种 event；heartbeat 不持久化。浏览器断开不取消生产任务。

### 14.3 稳定错误

| HTTP | code | 场景 |
| --- | --- | --- |
| 409 | `CONFIG_OPERATION_IN_PROGRESS` | 已有生产变更租约 |
| 409 | `CONFIG_BACKUP_PROTECTED` | 备份存在系统或人工保护 |
| 409 | `CONFIG_RETENTION_PLAN_EXPIRED` | dry-run 过期或事实变化 |
| 409 | `CONFIG_ATTENTION_UNRESOLVED` | 普通操作试图绕过 open case |
| 422 | `CONFIG_BACKUP_TARGET_INVALID` | 目标备份损坏或隔离校验失败 |
| 500 | `CONFIG_RESTORE_NEEDS_ATTENTION` | 恢复或安全回滚事实不唯一 |
| 422 | `NGINX_RESTART_CONFIG_INVALID` | restart 前生产配置无效 |
| 503 | `NGINX_RESTART_FAILED` | supervisor 明确失败且运行事实可判定 |
| 500 | `NGINX_RESTART_NEEDS_ATTENTION` | supervisor 结果或 runtime identity 不唯一 |

错误 details 白名单只允许 stage、state、reason_code、current_etag、limit、HTTP status 和不透明 object ID。绝对路径、命令、PID 列表和 raw output 不进入公开错误。

## 15. 前端信息架构与交互

新增 `/config/operations` 路由和导航项“Recovery & History”。页面使用一个主标题和任务 tab：Overview、Backups、History、Audit。tab 是 URL query 驱动的展示状态，不持久化敏感内容。

### 15.1 attention 与运行控制

页面顶部先展示 open attention case；它是持久 blocking panel，不使用 toast。每个 case 同时显示文字状态、shape/icon、reason、关联 ID 和允许动作。restore/restart/verify 之外没有关闭按钮。

runtime control panel 展示最新 Nginx 状态、生产校验时间和最近 restart。Restart 按钮打开具名 modal，说明 master 会更换、短暂中断和生产配置不会被修改。输入必须精确为 `RESTART NGINX`。

### 15.2 备份与保留

backup table 每行显示 abbreviated ID、来源、状态、创建/验证时间、大小、保护标签和可用动作。表格在窄屏转为语义卡片列表，不通过整页横向滚动容纳列。

restore modal 显示目标备份、来源、生产 identity、完整性时间、当前 protection 和风险说明。确认输入必须为完整 backup ID。任务开始后 modal 可关闭，但关闭/离页不取消任务；终态持久显示。

retention panel 展示固定 policy、总数/总字节、protected 数量和 dry-run 结果。执行前逐项展示将删除的 ID、时间和大小；输入完整 run ID 才能执行。被重新保护的项显示 `Skipped — protected`，不当作删除成功。

### 15.3 历史与审计

history timeline 合并 release/restore/restart 顶层记录，按服务端稳定时间排序；筛选只使用固定 kind/state 枚举。详情使用现有 stage timeline。

audit table 显示时间、actor display name、action label、object kind/ID、result 和安全 details 摘要。request ID 可复制；配置正文、路径列表和 raw JSON 不展示。分页“Load more”保留当前内容与焦点。

## 16. DESIGN.md 扩展与可访问性

实现 UI 前在 `DESIGN.md` 增加：`operations-task-tabs`、`attention-case-panel`、`runtime-control-panel`、`backup-table/card`、`backup-protection-badge`、`restore-confirmation-modal`、`retention-plan-panel`、`operations-history-list` 和 `audit-table/card`。

- 表格使用原生 table/thead/th scope；窄屏切换为有 label/value 关系的卡片，不用 CSS 把 table role 伪装成 div。
- destructive retention 与 restore 主按钮仍使用 Action Blue 交互语言，风险由明确文案、确认输入和 danger status token 表达，不引入第二品牌色。
- open attention 和 needs-attention 终态使用一次 blocking alert；后续证据是普通可读内容。
- stage timeline 的 live region 只播报当前阶段，heartbeat 和历史不播报。
- modal 继续遵循 focus trap、Escape、background inert 和 trigger focus restore；提交中的任务不会因 modal 关闭而取消。
- 320 CSS px 时页面无横向溢出；ID/code 自身可内部滚动或换行。44×44px target、200% zoom、400% reflow 和键盘顺序必须人工/浏览器验证。

## 17. 日志、审计与脱敏

每个 restore/restart/retention/verification 阶段记录 `request_id`、对象 ID、stage、result 和 `duration_ms`。只有 Agent 边界记录固定命令类别；不记录命令行或 stdout/stderr。

审计至少记录：backup protect/unprotect、retention plan/create/item/result、restore queue/stage/result、restart queue/stage/result、attention open/attempt/resolved 和 health verification。details 只包含稳定枚举、计数、大小、公开 identity abbreviation 和关联不透明 ID。

严禁记录：配置正文、diff、备份正文、私有 manifest、文件摘要列表、绝对路径、临时路径、命令行、完整 stderr、Cookie、Authorization、CSRF、确认输入或用户填写的原始原因全文。原因只在专用列中经长度/字符校验保存，审计 details 记录 reason category，不复制全文。

## 18. 崩溃恢复与生命周期

Web 在绑定管理端口前按顺序：

1. 对账 v0.2.2 release 和 production lease。
2. 对账非终态 restore 与 Agent journal；按 target/safety/current digest 唯一判定继续、回滚或 needs-attention。
3. 对账 restart；重新采样 runtime，只有能够证明新 runtime healthy 才补记成功，否则按阶段记 failed/needs-attention。
4. 对账 retention deleting 项；正文完整则退回 complete，正文不存在则补记 deleted，部分/不可读进入 needs-attention。
5. 为所有 needs-attention workspace/task 幂等创建 case。
6. 补记终态审计并释放精确匹配的 production lease。
7. 完成上述步骤后才接受新的生产变更。

关闭时先停止接收新任务，再等待已拥有任务的有界收尾。超时取消只停止当前进程继续工作，不抹去 journal 或报告取消成功；下次启动重放。

## 19. 测试策略

所有新行为先写失败测试，再实现最小修改。

### 19.1 Go 单元与组件

- migration：v0.2.2 数据升级、旧 backup v1 索引、needs-attention case backfill、lease 约束和重复打开。
- history：keyset cursor、稳定 tie-break、limit、筛选、safe DTO 和 malformed row fail closed。
- protection/retention：动态保护、人工保护、最小集合、count/bytes/age、稳定计划、过期、事实变化和 tombstone。
- restore：目标损坏、隔离 validation、当前生产变化、安全备份失败、每个 journal 点、reload/health 失败、回滚和 needs-attention。
- restart：固定 command、生产无效、running/degraded/stopped/unknown、超时、取消、master replacement、worker/HTTP 失败。
- attention：backfill、只读阻断、错误处置不关闭、成功 action 绑定和幂等 resolution。
- HTTP/SSE：认证、Origin、CSRF、strict JSON、确认、202/Location、cursor、Last-Event-ID、no-store 和脱敏。

### 19.2 真实 Nginx 与文件系统

- 用固定备份 fixture 验证相对/绝对 include、敏感文件、损坏 manifest 和目标错误位置。
- 在隔离 Nginx + 监督器适配测试中验证 restart 更换 master/worker 并保持 HTTP 可达。
- restore 每个 durable 文件点杀 Agent，重启后只得到目标成功、安全备份回滚成功或 needs-attention。
- 注入只读目录、空间不足、rename/fsync、backup delete、端口冲突、PID 不可读和进程崩溃。
- retention 在相同输入上重复运行产生相同计划，不删除任何受保护项。

### 19.3 前端与浏览器

- open/resolved attention、可用动作和普通操作阻断。
- backup empty/loading/error/complete/invalid/deleted/protected 状态。
- restore/restart/retention 具名确认、重复提交 single-flight、焦点 trap/Escape/restore。
- SSE snapshot/reconnect/terminal、刷新恢复和 session 过期。
- history/audit 分页、筛选、窄屏 card、键盘和复制 request ID。
- 1068/833/734/640/480/320 响应式、无页面横向溢出、44px target 和 axe/键盘流程。

### 19.4 原生升级与持久化

- v0.2.2 SQLite、备份和 release 数据升级后历史与恢复可用。
- 任务成功后重启应用与 Agent，配置、数据库、备份、tombstone、case 和审计保持一致。
- Agent/UI/Nginx 在 restore/restart/retention 任一阶段退出后恢复判定正确。
- 本版本不运行 Docker 脚本、不构建验收镜像、不验证 volume/container lifecycle，也不执行 multiarch；这些门禁全部属于 v0.7.0。
