## 1. 文档目的

本文把原 v0.2 配置管理范围拆分后的第一个可独立安装、升级和验收的版本细化为产品与技术设计。v0.2.1 只交付“安全配置工作区”：管理员可以从生产配置建立稳定快照，在持久化草稿中编辑、搜索和查看差异，但任何工作区操作都不能修改 `/etc/nginx`、触发候选配置 `nginx -t`、reload 或 restart。v0.1.0 已有的容器启动校验和只读 `nginx -T` 浏览保持不变。

这种拆分先验证最容易造成数据损坏的文件边界、并发控制和崩溃恢复，再在后续版本逐步授予生产变更权限。根级 `AGENTS.md` 继续约束工程、安全和质量活动，`PLAN.md` 继续定义版本顺序，`DESIGN.md` 继续作为前端视觉与交互基线。三者发生冲突时停止相关实现并请求确认。

## 2. 背景与版本拆分

v0.1.0 已交付一体化 Docker 镜像、认证与安全会话、非特权 Web/API、Unix Socket Agent、真实 Nginx 状态以及基于 `nginx -T` 的只读生效配置浏览。v0.2 不重建这些能力，而是在现有边界上增量扩展。

原 v0.2.0 被拆为三个连续版本：

| 版本 | 用户结果 | 新增生产权限 | 前置版本 |
| --- | --- | --- | --- |
| v0.2.1 | 创建、编辑、搜索和审阅持久化配置工作区 | 无；生产配置与 Nginx 运行状态严格只读 | v0.1.0 |
| v0.2.2 | 校验候选配置，备份、原子发布、reload、确认并自动回滚 | 固定的 validate、publish、reload、rollback | v0.2.1 |
| v0.2.3 | 人工恢复、备份保留、restart、完整历史与人工处置 | 固定的 restore、restart、retention | v0.2.2 |

三个版本分别更新应用版本、数据库迁移、API 契约、UI、升级测试和发布记录。v0.2.2 不能与 v0.2.1 合并交付，v0.2.3 也不能作为 v0.2.2 的隐藏功能提前实现。

## 3. v0.2.1 目标与完成标准

v0.2.1 的用户结果是：管理员从当前 `/etc/nginx` 创建一个有生产摘要的工作区，在浏览器中组织和编辑受管文本文件，并始终能够看出草稿与初始快照的差异、并发冲突和生产过期状态。

版本必须同时满足以下目标：

1. 生产配置快照具有稳定边界；快照期间生产内容变化会使创建失败，而不是生成混合版本。
2. 每个工作区具有不可变 `base`、可编辑 `draft` 和不参与 Nginx 配置的 `control` 数据。
3. 所有工作区文件操作都受配置根、条目类型、UTF-8、NUL、大小、数量和容量限制约束。
4. 每次文件变更都要求强 ETag；并发或进程外篡改不能静默覆盖内容。
5. 文件系统写入、SQLite 元数据和审计之间具有可恢复的一致性协议；崩溃后不能把半成品报告为可用。
6. 生产摘要发生变化时，旧工作区进入只读 `stale`；系统不自动 rebase、三方合并或覆盖外部修改。
7. UI 在桌面、平板和手机上都能完成文件选择、编辑、搜索、差异审阅和冲突恢复，且满足 WCAG 2.2 AA。
8. 从 v0.1.0 升级和容器重建不会丢失已有应用数据或新建工作区。
9. Docker 验收复用可验证的构建缓存，同一源码指纹的测试镜像只构建一次，并记录缓存与镜像证据。

## 4. 范围

### 4.1 包含

- 从固定生产配置根 `/etc/nginx` 建立受限快照并计算确定性摘要。
- 工作区列表、创建、读取和删除。
- 物理文件树、include 依赖图和基于相对路径的逻辑分组。
- 受管常规 UTF-8 文本文件的创建、复制、重命名、编辑和删除。
- 当前文件与全部工作区的 unified diff。
- 当前文件编辑器搜索和工作区字面量搜索。
- 工作区级强 ETag、`If-Match`、冲突响应和 stale 检测。
- `preparing`、`ready`、`stale`、`needs_attention` 状态机。
- 工作区有界操作日志、失败回退、启动重放和文件系统/SQLite 对账。
- 工作区、文件、差异和逻辑分组的 `/api/v1` DTO 与 UI。
- 必要的结构化日志和审计元数据。
- v0.1.0 → v0.2.1 数据迁移、持久化、故障注入和 Docker 验收。
- Dockerfile 与验收脚本的缓存正确性、复用和可观测性改进。

### 4.2 不包含

- 修改、删除、重命名、chmod 或 chown `/etc/nginx` 中的任何条目。
- 由工作区对候选或运行中的生产配置发起 `nginx -t`；这属于 v0.2.2。v0.1.0 的容器启动校验继续保留。
- 发布、备份、reload、自动回滚或任何生产写入；这属于 v0.2.2。
- 人工恢复、备份保留、restart 或完整历史中心；这属于 v0.2.3。
- Nginx AST、语义校验、自动格式化、自动补全、LSP 或结构化配置编辑。
- 自动修复 include、在重命名后重写引用、自动 rebase 或三方合并。
- symlink 创建、编辑、复制、重命名或删除。
- 特殊文件读取或写入。
- 目录 CRUD、递归复制、批量重命名或批量删除；新文件只能写入工作区内已存在的受管目录。
- 协作光标、实时共同编辑、离线编辑或把配置正文写入浏览器持久化存储。
- 分页型无限工作区或全文索引服务；v0.2.1 使用严格上限后的有界列表和字面量搜索。

## 5. 不可违反的安全不变量

1. `/etc/nginx` 始终是配置真源，SQLite 不能保存可反向覆盖生产文件的配置正文。
2. 非 root Web/API 进程只写 `/var/lib/nginx-uix`，不能直接读取或写入特权生产路径，也不能执行 Nginx 命令。
3. Agent 只监听现有 Unix Socket，继续校验对端凭据，只接受版本化、类型化、白名单化操作。
4. Agent 不接受可执行文件、Shell 文本、绝对路径、配置根、Nginx 参数或用户提供的目标目录。
5. v0.2.1 Agent 新操作全部只读生产配置；协议中不存在 publish、reload、restart、restore 等能力。
6. 所有相对路径先做词法校验，再在受管根内 canonicalize；任何穿越、越界、symlink 竞态或根外解析都 fail closed。
7. 遍历使用 `lstat` 语义，不能通过跟随 symlink 扩大扫描边界。
8. 工作区 `base` 不可由 API 修改；其内容摘要在读取和后续状态判断前重新验证。
9. 草稿写入只发生在同一工作区文件系统内，使用同目录临时文件、正确权限、`fsync` 和原子 rename。
10. 任何无法确认文件系统与 SQLite 一致性的工作区都进入 `needs_attention`，绝不报告 `ready`。
11. API 错误、日志、审计和指标都不能包含配置正文、完整差异、绝对生产路径、临时路径或敏感指令参数。
12. 工作区操作不得改变 `/etc/nginx` 摘要、Nginx master PID、worker 集合或服务健康状态。

## 6. 总体架构

```text
Browser
  │ HTTPS/HTTP :9000, session + Origin + CSRF + If-Match
  ▼
nginx-uix Web/API (non-root)
  ├── httpapi/config DTO、认证边界、错误映射
  ├── config workspace service
  │   ├── path guard / inventory / include scanner / diff
  │   ├── manifest / ETag / operation journal / reconciliation
  │   └── /var/lib/nginx-uix/workspaces
  ├── store metadata + audit ── SQLite
  └── typed Agent client
          │ Unix Socket + peer credentials
          ▼
nginx-uix-agent (root)
  ├── config snapshot
  └── production digest
          │ fixed root, read-only
          ▼
       /etc/nginx

nginx master/worker：v0.2.1 不调用、不 reload、不 restart
```

### 6.1 组件边界

| 单元 | 负责 | 依赖 | 不负责 |
| --- | --- | --- | --- |
| `runtime` Agent 适配 | 固定根快照、生产摘要、边界检查、输出限制 | 文件系统、现有 Agent 协议 | 工作区编辑、SQLite、diff、Nginx 控制 |
| `config/path` | 相对路径语法、canonicalization、entry 分类 | 标准库文件系统抽象 | HTTP、数据库、业务状态 |
| `config/inventory` | 确定性遍历、manifest、摘要、容量统计 | path guard | include 语义、数据库 |
| `config/include` | 有界词法扫描、glob 展开、依赖边 | inventory | 完整 Nginx 语法或路径匹配语义 |
| `config/workspace` | 生命周期、状态机、锁、文件操作、journal、对账 | inventory、store、Agent client | HTTP DTO、视觉状态 |
| `config/diff` | base 与 draft 的逐文件摘要和 unified diff | manifest、受管文本 | 将 diff 持久化到数据库 |
| `store` | 工作区索引、逻辑分组、修订、审计元数据、迁移 | SQLite | 配置正文、base/draft 内容、完整 diff |
| `httpapi` | 认证、Origin/CSRF、DTO、ETag、状态码、错误脱敏 | workspace service | 拼接路径或直接读写文件 |
| Vue 配置工作区 | 文件导航、编辑、搜索、差异、状态恢复 | 类型化 API client | 解释内部错误或持久化配置正文 |

每个包继续遵循小包、显式依赖注入和消费方小接口原则。不得建立 `utils`、`helpers` 或提前为 v0.2.2 创建发布抽象。

## 7. 持久化工作区模型

### 7.1 路径布局

工作区只位于现有持久化卷内：

```text
/var/lib/nginx-uix/
├── nginx-uix.db
└── workspaces/
    └── <opaque-workspace-id>/
        ├── base/       # 创建时的可管理配置快照；应用级不可变
        ├── draft/      # 可管理配置的完整可编辑副本；不使用 hardlink
        └── control/    # manifest、状态、锁、journal、恢复暂存；不是 Nginx 配置
```

工作区 ID 由服务端生成，固定后不可修改。客户端只能把它作为不透明标识使用。所有内部路径都由服务端用工作区 ID 和固定根组合，Agent 与浏览器都不能指定工作区根。

`base` 和 `draft` 位于同一个文件系统，确保恢复暂存和 rename 不跨文件系统。工作区目录与 `control` 默认不高于 `0700`，工作区常规文件不高于 `0600`；manifest 单独保留原生产模式，v0.2.1 不提供 chmod。`base` 文件采用只读权限并由应用协议禁止写入；每次关键读取仍校验 manifest，不能只依赖权限。`draft` 是逐文件复制，禁止 hardlink，避免编辑草稿时改变 `base`。新建文件的未来目标模式固定记录为 `0640`。`control` 至少包含原子写入的 manifest、状态记录和有界 journal；其中任何文件都不会出现在文件树、搜索、diff、下载或未来 Nginx 候选配置中。

### 7.2 条目分类

快照与工作区清单对每个条目记录相对路径和类型，但只有一类条目可编辑：

| 条目 | 清单/UI | 快照内容 | v0.2.1 操作 |
| --- | --- | --- | --- |
| 根内常规 UTF-8 文本文件 | 展示 | 复制到 `base` 和 `draft` | 创建、复制、重命名、编辑、删除 |
| 敏感材料或不符合文本策略的常规文件 | 只展示类型和稳定安全原因，不展示正文或逐文件摘要 | 不复制正文 | 禁止读取与全部变更 |
| 目录 | 展示 | 创建对应目录 | 只读导航；不提供 CRUD |
| symlink，解析目标仍在根内 | 展示目标与只读原因 | 只记录 link 元数据，不创建可跟随的活动 link | 禁止全部变更；目标常规文件按其物理路径单独管理 |
| symlink，目标越界、断裂或成环 | 展示为 external/unavailable | 不复制目标，不创建 link | 禁止读取与全部变更 |
| FIFO、Socket、设备等特殊文件 | 只展示类型和不可管理状态 | 不读取、不复制 | 禁止读取与全部变更 |
| include 指向根外常规文件 | 依赖图展示为 external read-only | 不复制 | 禁止读取正文与全部变更 |

常规文件只有满足以下正向规则之一才进入“可管理配置”候选集：入口 `nginx.conf`；basename 为 `mime.types`、`fastcgi_params`、`fastcgi.conf`、`uwsgi_params`、`scgi_params`、`koi-win`、`koi-utf` 或 `win-utf`；文件名以 `.conf` 结尾；或者它被入口配置的有界、根内、传递 include 图直接匹配。新建、复制或重命名后的目标也必须满足同一规则，且只能位于已有受管目录。

候选文件随后执行敏感策略。以下任一条件命中即分类为 `sensitive_material`：内容具有 PEM private key、OpenSSH private key、X.509 certificate、PKCS#12 或 DER credential 的确定签名；路径使用 `.key`、`.pem`、`.crt`、`.cer`、`.der`、`.p12`、`.pfx`、`.jks`、`.keystore`、`.htpasswd` 或 `.passwd` 后缀；或者该路径被 `ssl_password_file`、`auth_basic_user_file` 以及名称以 `_certificate`、`_certificate_key`、`_trusted_certificate` 或 `_crl` 结尾的文件型 Nginx 指令引用。判断顺序是先元数据与指令引用、再对最多 2 MiB 的候选内容做有界签名检测；文件扩展名不是唯一判断依据。

Agent 只向 Web 返回 `sensitive_material` 等稳定原因码；不得把敏感内容、内容片段或逐文件内容摘要写入 workspace、SQLite、API、日志或审计。没有命中正向规则或不能安全判定的常规文件默认不可管理。正向规则、敏感指令集合和内容签名共同构成版本化安全策略，任何扩大都必须经过设计、安全测试和发布说明，不能由用户请求动态关闭。

遍历不跟随 symlink。link target 在进入日志、API 或 UI 前转换为安全分类；根外解析后的绝对路径不返回浏览器，配置正文中原本写明的 include 表达式仍可由已认证管理员在显式文件读取中看到。未来 v0.2.2 如何为校验候选重建安全的 symlink 语义需要独立设计，v0.2.1 不提前物化活动 link。

### 7.3 内容与容量限制

限制在服务端强制执行，前端提示不能代替后端校验：

| 限制 | 值 | 计数规则 |
| --- | --- | --- |
| 单个受管文件 | 2 MiB | UTF-8 原始字节数 |
| 生产根条目数 | 4096 | 常规文件、目录、symlink、特殊文件都计入 |
| 生产根受管文本总量 | 32 MiB | 可复制常规文本文件字节数 |
| 相对路径 | 1024 个 UTF-8 字节、64 层 | 每个路径分量最多 255 字节且不得超过运行文件系统的 `NAME_MAX` |
| 持久化工作区数量 | 8 | 所有状态都计入，直到显式删除完成 |
| 工作区数据总量 | 512 MiB | 全部工作区 `base`、`draft`、`control` 的逻辑字节数 |
| 逻辑组 | 128 个 | 配置根级总数 |
| 逻辑组成员 | 每组 1024、总计 4096 | 重复成员拒绝，不靠去重绕过上限 |
| 完整 diff 响应 | 4 MiB | JSON 编码后的响应上限 |
| 工作区搜索结果 | 500 个匹配 | 按路径、行号、列号稳定排序后的前 500 项 |
| 搜索词 | 256 个 UTF-8 字节 | 非空字面量，不支持正则 |

可管理常规文件必须是有效 UTF-8 且不含 NUL。单个常规文件超过 2 MiB、包含 NUL、不是 UTF-8 或被敏感策略命中时，以不可管理节点进入清单；读取或变更它会返回对应的 `CONFIG_LIMIT_EXCEEDED` 或 `CONFIG_ENTRY_NOT_MANAGED`。条目总数或可管理文本总量超过根级上限时，快照整体失败，不建立部分工作区。相对路径本身不是有效 UTF-8 时同样整体失败并返回 `CONFIG_PATH_INVALID`，避免在 JSON 与文件系统之间产生不一致身份。

编辑器不得自动格式化、改变编码、统一换行符或补删文件末尾换行；未改动文件不会触发保存。已有文件保存时沿用打开时检测到的换行策略，新建文件默认使用 LF。超出 diff 响应上限时只返回完整的逐文件状态摘要和 `complete: false`/`reason: response_limit`，不返回伪装成完整结果的截断 patch。搜索超过 500 项时返回前 500 项并明确 `complete: false`。

## 8. Manifest、摘要与并发标识

### 8.1 确定性 manifest

manifest 使用相对路径的原始 UTF-8 字节进行升序排序。每条记录至少包含：相对路径、entry 类型、受管/只读分类、常规文件模式、字节数、可管理常规文件的 SHA-256 内容摘要，以及 symlink、敏感材料或外部依赖的安全分类。敏感和不可管理常规文件只以类型、模式、大小和安全分类参与结构清单，不保存或公开逐文件内容摘要。摘要输入使用带版本号、长度前缀的规范二进制编码，不能依赖 map 顺序、JSON 空白、本地时区、inode、mtime、uid 或 gid。

manifest 格式具有显式 schema version。已发布 schema 不原地改义；未来升级必须读取旧版本或通过有验证的迁移生成新 manifest。

### 8.2 三类摘要

| 名称 | 来源 | 用途 |
| --- | --- | --- |
| `production_digest` | Agent 对固定 `/etc/nginx` 结构清单与可管理配置内容计算 | 检测快照竞态和工作区 stale；敏感材料正文变化不产生可被浏览器利用的摘要 oracle |
| `base_digest` | 工作区 `base` 与只读条目元数据 | 证明初始快照未被篡改 |
| `draft_digest` | 当前 `draft` 与只读条目元数据 | diff 身份、进程外篡改检测和 ETag |

快照在复制前后各计算一次生产摘要；两次不一致返回 `CONFIG_SNAPSHOT_CHANGED` 并删除 staged 内容。完成后 `base_digest` 必须与快照 manifest 的受管内容一致。打开工作区时，Agent 重新计算 `production_digest`；不同则把 `ready` 转为 `stale`。

### 8.3 强 ETag

工作区文件资源使用当前 `draft_digest` 形成强 ETag，格式为带双引号的版本化摘要，例如 `"draft-v1:<sha256>"`。所有会改变草稿的请求必须携带单个 `If-Match`；缺失、弱 ETag、多个候选或不匹配都不执行写入。不匹配返回 HTTP 409、`CONFIG_WORKSPACE_CONFLICT` 和安全的当前 ETag。

ETag 是工作区级而非单文件级，因此任一文件变更都会使所有已打开编辑会话的旧 ETag 失效。响应成功后在 header 和 DTO 中返回同一个新 ETag。浏览器发生冲突时保留内存中的未保存文本，获取服务器新版本后由用户复制或人工比对；客户端不能自动重放写入。

逻辑分组不改变 `draft`，因此使用独立的组集合强 ETag。分组写入同样要求 `If-Match`，冲突使用 `CONFIG_WORKSPACE_CONFLICT`，并返回当前组集合 ETag。

## 9. 生命周期与一致性流程

### 9.1 创建工作区

1. HTTP 边界验证登录、Origin、CSRF、名称和全局容量；服务端生成工作区 ID。
2. Web 在固定工作区根下建立 `control`，原子记录 `preparing`，并持有该工作区独占文件锁。
3. Web 向 Agent 发送仅含协议版本、request ID 和不透明工作区 ID 的 `config_snapshot` 请求。Agent 自行组合固定生产根和固定 snapshot staging 根。
4. Agent 用 `lstat` 做第一次有界清单与摘要，复制受管常规文件和安全元数据到 staged `base`，`fsync` 文件与目录，再做第二次生产摘要。
5. 两次生产摘要不同或任一步失败时，Agent 删除 staged 内容并返回分类错误；Web 不创建 SQLite `ready` 记录。
6. Agent 以原子 rename 完成 `base` 后，Web 逐文件复制为 `draft`，明确拒绝 hardlink，计算并复核 `base_digest`/`draft_digest`。
7. 一个 SQLite 事务写入工作区索引和创建审计事件；数据库失败时 Web 回退并删除未注册工作区。删除失败则保留 `preparing`，由启动对账继续处理。
8. 数据库提交成功后，Web 原子写入 control manifest 和 `ready` 状态并 `fsync` 父目录。若此步中断，启动对账根据已提交数据库记录和完整 manifest 安全完成，无法证明完整则置为 `needs_attention`。
9. API 仅在 `ready` 已落盘并复核后返回成功和初始 ETag。

系统不在快照过程中阻塞外部管理员直接修改 `/etc/nginx`；双摘要负责检测竞态。任何混合快照都不得作为工作区返回。

### 9.2 打开与 stale 检测

读取工作区前先验证 control schema、base manifest、draft manifest 和未完成 journal。对于 `ready`，再通过 Agent 读取当前生产摘要：

- 与记录一致：保持 `ready`，允许文件变更。
- 与记录不同：在 SQLite 与 control 中记录 `stale`，工作区保持可读、可搜索、可 diff，但拒绝后续文件写入。
- Agent 不可用：返回 `AGENT_UNAVAILABLE`，不擅自把工作区标为 stale 或 ready；已有页面可显示缓存的元数据，但不能进入可写状态。
- manifest 被进程外改变：进入 `needs_attention`，不把磁盘内容静默纳入新 ETag。

stale 工作区不自动 rebase、不做三方合并，也不能恢复为 ready。管理员创建新工作区后，可以在浏览器中人工参考旧 diff。v0.2.1 不提供服务器端跨工作区迁移变更。

### 9.3 草稿文件变更

创建、复制、重命名、替换内容和删除共用一条事务协议：

1. 验证认证、Origin、CSRF、DTO、`If-Match` 和请求体上限。
2. 获取工作区独占锁；重新读取状态、base manifest、draft manifest 和未完成 journal。
3. 要求状态为 `ready`，通过 Agent 重新读取当前生产摘要；不匹配立即转为 `stale`，Agent 不可用则拒绝写入。
4. 重新计算草稿摘要并与 control 记录及 `If-Match` 同时比较。
5. 校验源/目标相对路径、现有父目录、entry 类型、UTF-8/NUL、单文件和全局容量。每个路径分量都拒绝 symlink；目标不能逃离 `draft`。
6. 在 `control/journal` 原子写入 `prepared` 记录，包含操作类型、相对路径、旧/新摘要和恢复暂存引用，不包含配置正文；`fsync` journal。
7. 替换或创建使用同目录临时文件、受限权限、文件 `fsync`、原子 rename 和父目录 `fsync`。删除先原子移动到同工作区恢复暂存；重命名和复制都检查源、目标及覆盖规则，目标已存在时失败。
8. 重新计算完整 `draft_digest` 和容量，原子写入 staged control manifest。
9. SQLite 事务更新工作区摘要、更新时间和一条审计事件。事务失败时根据 journal 恢复文件系统旧状态并复核旧摘要。
10. 数据库提交后，原子发布 control manifest，把 journal 标记为 `committed`，`fsync` 后清理恢复暂存。
11. 返回新 ETag。任一阶段无法证明已回到旧摘要或已达到新摘要时，把工作区置为 `needs_attention`。

创建仅允许目标不存在；复制和重命名也不覆盖目标；内容保存使用 `PUT` 完整替换现有文件。include 引用不会随文件重命名自动修改，依赖图会把失效引用明确展示出来。diff 始终由 `base` 与 `draft` 现场派生，不读取 SQLite 操作历史；重命名在 v0.2.1 中确定性显示为一个删除和一个创建，不做启发式 rename 猜测。

### 9.4 启动重放与对账

Web 在对外绑定管理端口前扫描固定 workspaces 根，工作量受 8 个工作区和 512 MiB 上限约束：

- 无 SQLite 记录的完整 `preparing` 目录：按 control 状态继续清理；不会自动注册为 ready。
- 有 SQLite 记录但缺失目录、manifest 或 base：置为 `needs_attention`。
- `prepared` journal：比较旧摘要、新摘要和磁盘实际摘要；只在唯一可判定时完成提交或回退。
- `committed` 但未清理 journal：复核新摘要后幂等清理。
- 摘要既不是旧值也不是新值、恢复暂存缺失或 control 损坏：置为 `needs_attention`。
- 数据库和 control 状态不同：只有审计与摘要能够证明单一结果时修正较旧一侧，否则置为 `needs_attention`。

重放和对账必须幂等；在任何一步再次崩溃后，下次启动仍按同一证据得到同一结果。`needs_attention` 工作区只读，可显式删除，但不能编辑、复制变更到生产或通过普通请求清除状态。

### 9.5 状态机

```text
create ──> preparing ──complete──> ready
              │                    │
              │ unsafe/incomplete  ├──production digest changed──> stale
              ▼                    │
       needs_attention <───────────┤ manifest/journal ambiguous
                                   │
                                   └──delete──> removed

stale ──ambiguous──> needs_attention
stale ──delete─────> removed
needs_attention ──explicit delete──> removed
```

只有 `ready` 接受文件变更。`preparing` 只显示创建中或恢复中；`stale` 和 `needs_attention` 都只读。删除工作区只删除 `/var/lib/nginx-uix/workspaces/<id>` 及其 SQLite 元数据，不接触 `/etc/nginx`。删除同样要求最后一次记录的强 ETag、命名确认、journal 和审计；即使磁盘损坏导致无法重新计算 draft digest，API 仍返回 SQLite/control 中最后一次已知 ETag 供管理员确认删除。失败时保持可对账状态。

## 10. Include 依赖扫描

v0.2.1 实现窄化词法扫描器，而不是提前实现 Nginx AST：

- 识别注释、单引号、双引号、反斜杠转义、分号和 `include` 指令 token。
- 不把注释或字符串中的 `include` 当成指令。
- 使用镜像固定的 Nginx prefix `/etc/nginx` 解析相对 include；绝对路径必须先分类为根内或 external。
- glob 只在工作区 manifest 内匹配，按相对路径字节升序展开，不读取根外文件系统。
- 含变量或其他无法确定解析的 include 参数标为 `unresolved`，不尝试求值或访问文件系统。
- 记录源文件、源行列、原始安全显示值、解析分类、目标列表和是否缺失。
- 检测重复边、循环和最大深度；循环作为图状态展示，不递归到资源耗尽。
- external、缺失、越界、symlink 和特殊文件都只生成状态边，不读取正文。
- 扫描错误不伪装成 Nginx 语法错误；UI 明确称为“依赖扫描提示”。真正的配置有效性只由 v0.2.2 的完整 `nginx -t` 判定。

扫描器的单 token 上限为 64 KiB、单 include 指令上限为 256 KiB、图节点上限沿用 4096 个根条目、依赖边上限为 16384、递归深度上限为 64；超过任一限制返回 `CONFIG_LIMIT_EXCEEDED`。文件修改后重新生成受影响文件的边，并以完整 manifest 复核最终图，避免增量状态漂移。

## 11. SQLite 元数据与审计

v0.2.1 使用单调、不可回写的迁移增加以下概念；具体 SQL 按现有 store 模式拆分：

| 概念 | 持久化内容 |
| --- | --- |
| workspace index | ID、显示名称、状态、production/base/draft digest、manifest version、创建者、时间和安全原因码 |
| logical groups | ID、名称、稳定排序键、集合修订和创建/更新时间 |
| group members | group ID 与配置根相对路径；不保存文件内容 |
| operation metadata | 操作 ID、workspace ID、动作、旧/新摘要、结果、request ID 和时间 |
| audit event | actor、动作、相对路径集合或数量、摘要、结果、request ID 和时间 |

逻辑分组是配置根级元数据，不属于某一个工作区。成员使用相对路径，因此可在后续新工作区复用；当前工作区不存在的成员显示为 missing，不被自动删除。组名称规范化后唯一，排序稳定。分组变更不移动、创建或修改物理文件。

数据库不能保存配置正文、编辑器草稿、base/draft 副本、完整 unified diff、根外绝对路径或 journal 恢复内容。已发布迁移不原地修改；升级失败时应用不绑定管理端口，但不能破坏 v0.1 数据或生产 Nginx。

## 12. Agent 协议扩展

v0.2.1 在现有版本化 JSON/Unix Socket 协议上只增加两个只读能力：

| 操作 | 请求中的业务字段 | 成功结果 | 明确不接受 |
| --- | --- | --- | --- |
| `config_snapshot` | 不透明 workspace ID | production digest、manifest version、条目/字节统计、staged base 完成标识 | 根路径、目标路径、include 参数、命令参数 |
| `config_digest` | 无 | 当前 production digest、manifest version、条目/字节统计 | 任意路径或扫描选项 |

Agent 自身固定 `/etc/nginx`、入口和 `/var/lib/nginx-uix/workspaces` 根。workspace ID 通过严格格式校验后只作为单个路径分量；仍须在打开目录时做根内与 symlink 检查。Agent 以预先打开的根目录 descriptor 做逐分量 no-follow 解析，使用 Linux `openat2` 的 `RESOLVE_BENEATH`/`RESOLVE_NO_SYMLINKS` 或经测试的等强 descriptor-relative 实现；staging 与 `base` 必须不存在并以 exclusive create 建立，不能覆盖已有目录。读取文件后用同一 descriptor `fstat` 复核类型与身份，避免只做字符串 canonicalization 的 TOCTOU 窗口。请求拒绝未知字段、未知操作、重复字段、尾随 JSON、超限 body 和错误协议版本。

每个操作使用 `context.Context`、固定总超时、单文件/总输出限制和取消清理。`config_snapshot` 总期限为 60 秒，`config_digest` 为 15 秒；超时返回 `CONFIG_OPERATION_TIMEOUT`，不能延长为无界等待。Agent 不返回配置正文，只返回相对路径 manifest 或摘要所需的有界结构；错误响应只包含稳定 code 和 safe message。Agent 进程崩溃、Socket 不可用或协议异常统一映射为 `AGENT_UNAVAILABLE`，Web 不能回退为直接读取 `/etc/nginx`。

协议测试必须证明不存在任意 Shell、任意绝对路径、任意 Nginx 参数、生产写入、reload 或 restart 通道。

## 13. REST API 设计

### 13.1 通用约束

- 路径继续以 `/api/v1` 开头，JSON 字段使用 `snake_case`，时间使用带时区 RFC 3339。
- 使用现有 `{ "error": { "code", "message", "request_id", "details" } }` 错误 envelope。
- 所有响应包含 request ID；配置与差异响应使用 `Cache-Control: no-store`。
- 所有状态修改继续要求有效会话、可信 Origin 和 CSRF token。
- 文件相对路径只放在经过验证的 query 或 JSON 字段中，不作为通配 route segment，也不接受 URL 编码后的路径逃逸。
- 列表具有稳定排序；工作区最多 8 个，因此 v0.2.1 不引入分页。
- 请求 DTO 使用严格解码，拒绝未知字段、重复字段、尾随 JSON 和超限 body。
- 工作区显示名称在 trim 后为 1–80 个 Unicode code point，逻辑组名称为 1–64 个；两者拒绝控制字符和双向控制字符。工作区名称可重复，ID 才是资源身份；逻辑组名称按精确 UTF-8 字节唯一。
- 文件内容请求最多允许 2 MiB 正文加 64 KiB JSON envelope，其他配置 mutation 请求最多 256 KiB；服务端在 JSON 解码前先限制读取量。
- 创建工作区是受 60 秒总期限约束的同步请求，成功时才返回 HTTP 201；它不作为无界长任务运行。客户端断开会取消仍可取消的 I/O，但最终结果只以持久化状态为准：若提交已先完成，刷新列表会看到 ready 工作区；若未完成，清理或启动对账决定结果。

### 13.2 资源与方法

| 方法与路径 | 语义 | 并发条件 |
| --- | --- | --- |
| `GET /api/v1/config/workspaces` | 按 `updated_at DESC, id ASC` 列出工作区 | 无 |
| `POST /api/v1/config/workspaces` | 创建工作区，body 只含显示名称 | CSRF；容量预检 |
| `GET /api/v1/config/workspaces/{workspace_id}` | 读取状态、摘要、容量和依赖摘要 | 返回工作区 ETag |
| `DELETE /api/v1/config/workspaces/{workspace_id}` | 命名确认后删除持久化工作区 | `If-Match` + CSRF |
| `GET /api/v1/config/workspaces/{workspace_id}/files` | `path` 缺失时返回树；存在时返回受管文件正文与元数据 | 返回工作区 ETag |
| `POST /api/v1/config/workspaces/{workspace_id}/files` | 在已存在目录创建新常规文件 | `If-Match` + CSRF |
| `PUT /api/v1/config/workspaces/{workspace_id}/files?path=...` | 完整替换已有受管文件正文 | `If-Match` + CSRF |
| `PATCH /api/v1/config/workspaces/{workspace_id}/files?path=...` | 把已有受管文件重命名到 body 的 `destination_path` | `If-Match` + CSRF |
| `DELETE /api/v1/config/workspaces/{workspace_id}/files?path=...` | 命名确认后删除已有受管文件 | `If-Match` + CSRF |
| `POST /api/v1/config/workspaces/{workspace_id}/files/copies` | 从 `source_path` 复制到不存在的 `destination_path` | `If-Match` + CSRF |
| `GET /api/v1/config/workspaces/{workspace_id}/files/search` | 在 draft 做有界字面量搜索 | 无 |
| `GET /api/v1/config/workspaces/{workspace_id}/diff` | `path` 可选；返回单文件或全部 diff | 无 |
| `GET /api/v1/config/groups` | 列出逻辑组和成员；可用 `workspace_id` 标注 missing | 返回组集合 ETag |
| `POST /api/v1/config/groups` | 创建逻辑组 | 组集合 `If-Match` + CSRF |
| `PUT /api/v1/config/groups/{group_id}` | 替换名称、顺序和成员相对路径 | 组集合 `If-Match` + CSRF |
| `DELETE /api/v1/config/groups/{group_id}` | 命名确认后删除逻辑组，不删文件 | 组集合 `If-Match` + CSRF |

所有文件写入成功都返回新工作区 ETag。读取 stale 或 needs-attention 工作区允许返回内容和 diff；任何文件写入分别返回 `CONFIG_WORKSPACE_STALE` 或 `CONFIG_WORKSPACE_NEEDS_ATTENTION`。

### 13.3 主要 DTO

工作区 DTO 至少包含：

- `id`、`name`、`state`。
- `production_digest`、`base_digest`、`draft_etag`。
- `entry_count`、`managed_bytes`、`workspace_bytes`。
- `created_by`、`created_at`、`updated_at`。
- 可选的稳定 `state_reason_code`；不返回内部错误文本。

文件树节点至少包含：

- `path`、`name`、`entry_type`。
- `managed`、`read_only`、`status_reason_code`。
- 常规文件的 `size_bytes`、`content_digest` 和 `diff_status`。
- include 节点摘要：`dependency_status`、目标数量和循环标记。

文件正文只在显式 `path` 读取时返回。diff DTO 包含稳定排序的文件摘要、`complete`、可选 `reason` 和可选 unified patch。搜索 DTO 包含 path、1-based line/column 和受限单行片段；片段只作为显式配置读取响应返回，不能进入日志或审计。

### 13.4 稳定错误

| HTTP | code | 使用场景 |
| --- | --- | --- |
| 422 | `CONFIG_PATH_INVALID` | 非法、绝对、穿越、根外或 symlink 路径 |
| 422 | `CONFIG_ENTRY_NOT_MANAGED` | symlink、特殊文件、目录或 external 条目被请求变更 |
| 413 | `CONFIG_LIMIT_EXCEEDED` | 文件、条目、总量、工作区、搜索或请求上限 |
| 404 | `CONFIG_WORKSPACE_NOT_FOUND` | 工作区不存在或已删除 |
| 409 | `CONFIG_WORKSPACE_CONFLICT` | ETag 缺失/不匹配、目标已存在或并发变更 |
| 409 | `CONFIG_WORKSPACE_STALE` | 生产摘要已变化，旧工作区拒绝写入 |
| 409 | `CONFIG_WORKSPACE_NEEDS_ATTENTION` | 工作区一致性无法安全判定 |
| 409 | `CONFIG_SNAPSHOT_CHANGED` | 快照前后生产摘要不同 |
| 503 | `AGENT_UNAVAILABLE` | Agent、Socket、协议或只读摘要操作不可用 |
| 504 | `CONFIG_OPERATION_TIMEOUT` | 有界快照、摘要或工作区 I/O 超过固定期限 |

格式错误的 JSON、未知字段和普通字段校验继续使用现有 `invalid_request`。错误 details 白名单只允许与 code 对应的相对路径、当前 ETag、字段名、limit name、limit value 和实际计数；不能包含绝对路径、配置正文、diff、临时文件、命令行或底层错误。

## 14. 前端设计

### 14.1 信息架构

配置工作区采用已确认的 A 方案：桌面为连续审阅的三栏结构。

```text
┌───────────────┬──────────────────────────┬───────────────────┐
│ 文件与逻辑组  │ 编辑器                   │ 审阅              │
│ physical/group│ tabs + search + content  │ diff + dependencies│
└───────────────┴──────────────────────────┴───────────────────┘
```

- 左栏在物理树和逻辑组之间切换，条目类型、修改状态、external、missing 和只读原因同时使用文字/图标，不能只依赖颜色。
- 中栏显示文件标签、明确的未保存标记、显式“保存”按钮、查找和编辑区。v0.2.1 不自动保存。
- 右栏在“当前文件差异”“全部差异”“include 依赖”之间切换。unified diff 显示行号、`+`/`-`、文件状态和可访问标签。
- 页面顶部持续显示工作区名称、状态、生产摘要是否匹配和草稿变更数量；所有草稿明确标注“尚未执行 Nginx 校验”。页面没有发布、校验、reload 或 restart 按钮，依赖扫描提示也不能显示为配置有效。

### 14.2 响应式 A1 方案

| 视口宽度 | 布局 |
| --- | --- |
| `>= 1069px` | 文件树、编辑器、审阅三栏同时可见 |
| `834–1068px` | 文件树 + 编辑器；审阅使用右侧 drawer |
| `735–833px` | 收窄文件树 + 编辑器；审阅继续使用 drawer |

### 14.3 编辑器依赖

编辑器采用 CodeMirror 6 的模块化包，只启用基础文本编辑、行号、撤销/重做、搜索和官方 legacy Nginx stream mode：

- CodeMirror 6 guide：<https://codemirror.net/docs/guide/>
- `@codemirror/legacy-modes`：<https://code.haverbeke.berlin/codemirror/legacy-modes>
- `@codemirror/view`：<https://code.haverbeke.berlin/codemirror/view>

选择理由是官方维护、MIT 许可、Vue 可控集成和按模块静态打包。版本在实施时精确写入 `web/package.json` 与 `package-lock.json`，不使用浮动范围。替代方案是自建 textarea 高亮层或完整 IDE/LSP；前者难以可靠处理选择、撤销和可访问搜索，后者超出 v0.2.1 范围并显著增加体积与攻击面。

发布镜像只包含打包后的静态资源，不包含 npm cache、源码 map（除非现有生产策略明确允许）、测试 fixture 或 `node_modules`。依赖引入前记录许可证、维护状态、锁定版本和前端 bundle 体积差异。

### 14.4 保存、冲突和失败状态

- 保存只能由用户显式触发；按钮在无改动、请求进行中或工作区只读时禁用并解释原因。
- 浏览器只在内存中保存当前未提交文本。不得写入 `localStorage`、IndexedDB、Cache Storage、Service Worker cache 或 URL。
- 离开有未保存内容的文件、工作区、路由或页面前显示确认；浏览器关闭使用标准 beforeunload 提示。
- 409 conflict 显示持久 inline banner，保留本地文本，提供“复制本地内容”“读取服务器版本”“查看服务器差异”，不自动覆盖或重试。
- stale 显示生产配置已变化以及“创建新工作区”入口；旧工作区保持只读。
- needs-attention 显示一致性无法确认和工作区 ID，禁止普通保存；v0.2.1 只允许查看或命名删除。
- 会话过期时保留内存文本并允许复制，但禁止提交；重新登录后必须重新读取服务器 ETag，不能直接重放旧请求。
- 创建工作区期间显示可取消的进行中状态；用户取消或连接中断后先刷新工作区列表，再根据服务器持久化状态报告已创建、已清理或需要人工处理，不能把客户端取消直接当作服务器失败。
- toast 只用于非关键成功反馈。冲突、stale、needs-attention、容量失败和 Agent 不可用使用持续可见的 inline 状态。
- 文件删除、工作区删除和逻辑组删除使用具名确认 modal，明确对象名和“不影响生产配置”或“不删除文件”的真实后果。

### 14.5 DESIGN.md 扩展与可访问性

实现任何配置页面前，先在 `DESIGN.md` 补充与现有 token 相容的 tree、editor、diff、drawer、modal、toast、状态 badge 和冲突 banner 规范。不得在业务组件中散落硬编码颜色、装饰阴影或第二强调色。

交互必须满足：

- tree 使用语义化层级、方向键、Home/End、展开/折叠和可见焦点。
- tab、drawer、modal 和文件选择器具有明确 accessible name、键盘顺序和焦点恢复。
- 每个表单控件有 label；状态、diff 和文件类型不只依赖颜色。
- 触控目标至少 44×44px，对比度达到 WCAG 2.2 AA。
- 加载、空、成功、失败、冲突、stale、needs-attention 和 Agent unavailable 都有独立、可测试状态。

### 14.6 前端状态与动作边界

`WorkspaceStore` 是配置工作区页面状态的唯一所有者。组件和页面只表达用户意图并调用 store action；只有 store 可以调用类型化的 `WorkspaceClient`。client 只负责 URL、HTTP header、严格运行时响应解析和公开 API 错误，不拥有页面状态。store 从注入的 `SessionStore` 和当前服务器状态取得变更权限：CSRF token 只来自已认证会话，文件变更使用活动工作区的 `draft_etag`，分组变更使用当前分组集合 ETag，具名删除值由用户操作显式提供。action 不接受 actor、request ID、原始 URL 或任意 header。

页面状态保留有界投影：

- `active`、`tree`、`documents`、`banner`、`selectedPath` 和 `activeTask` 是工作区与编辑状态真源。
- `search` 和 `diff` 只保存最近一次显式读取结果；工作区身份变化时立即清除。
- `groups` 在服务器返回真实集合前保持 `null`，不得虚构空 ETag。
- `pendingAction` 是 `null` 或一个类型化的用户动作描述；变更操作必须 single-flight。

store 提供完整页面动作：创建和删除工作区；创建、复制、重命名、保存和删除文件；搜索、读取当前或全部差异；读取、创建、替换和删除逻辑分组。成功的文件变更必须用响应中的工作区摘要和 ETag 更新全部相关投影；删除或路径身份变化时重新读取文件树。工作区和分组变更使用服务器返回值刷新有界集合。

除显式 `saveFile` 外，任何 action 都不能发送本地 dirty 文本，也不能隐式保存、覆盖、重新加载或丢弃打开文档。重命名或删除会影响 dirty 文档时，store 必须在 client 调用前拒绝，页面先取得用户明确决定。干净文档可以在服务器变更成功后对账，dirty 文档不能被静默重写。

读取操作拥有可取消的 `AbortController`；工作区切换后忽略过期完成，同类重复读取会取消前一次 search、diff、tree、group 或 list。第二个并发变更在本地失败，不排队、不自动重试。会话过期、冲突、stale、needs-attention、Agent unavailable 和客户端断开都不能触发自动重试。

错误继续使用类型化 `APIRequestError`：conflict 保留本地文本并记录安全的当前 ETag；stale 与 needs-attention 禁止普通变更但保持读取；Agent unavailable 显示持续 banner。`pendingAction` 在成功、取消和失败时都必须通过 `finally` 清除。失败变更不修改现有服务器投影或本地文档，除非已经完整提交一份新的服务器响应。

前端测试必须覆盖 action 到 client 的 CSRF/ETag 参数映射、工作区/文件/搜索/diff/分组对账、变更 single-flight、读取取消和过期结果抑制、会话过期后不重试、冲突状态、dirty 文档保护、文本与换行符原样保留，以及浏览器持久化和 URL 中不存在配置内容。

## 15. 日志、审计与敏感信息

HTTP 访问日志沿用稳定字段，并为工作区操作增加 `workspace_id`、`action`、`result`、`duration_ms` 和 `request_id`。领域包不重复记录同一错误；由有处理责任的 API、Agent 或启动对账边界记录一次。

审计事件记录 actor、动作、相对路径集合或数量、旧/新摘要、结果、request ID 和时间。它不记录：

- 配置正文、搜索片段或完整 diff。
- 绝对生产路径、工作区内部临时路径或恢复暂存路径。
- Cookie、Authorization、CSRF token、请求 body 或 Agent 原始 body。
- 可能出现于 Nginx 配置中的私钥、密码、URI 凭据或 Header 值。

用户可见错误与内部诊断分离。内部底层错误只进入受保护日志并经过路径与内容脱敏；API 只返回第 13.4 节的稳定 code、可操作 message 和白名单 details。

## 16. Docker 构建缓存与验收编排

### 16.1 目标

Docker 验收必须避免让 smoke、故障注入、浏览器验收和恢复测试分别重复构建同一镜像，同时不能因缓存误命中而测试旧源码。缓存是性能优化，不得改变测试覆盖、镜像内容或失败语义。

### 16.2 Dockerfile 缓存

- 保留 Go 构建阶段现有 BuildKit module cache 和 build cache mount。
- 前端 `npm ci` 增加稳定 ID 的 BuildKit npm cache mount；`node_modules` 仍由 lockfile 与源码层决定，不能从宿主机复制。
- 先复制依赖清单并安装，再复制应用源码，保持依赖层可复用。
- 所有基础镜像继续固定到已验证 digest；缓存不能替代 digest 锁定或 `go mod verify`/`npm ci`。
- 最终镜像不包含 Go/npm/BuildKit cache、编译器、源码缓存或测试材料。

### 16.3 完整源码指纹

验收脚本计算版本化 `source_fingerprint`，覆盖 Docker build context 中未被 `.dockerignore` 排除且会被任一 `COPY`/`ADD` 使用的全部文件，并覆盖 Dockerfile、`.dockerignore`、平台无关构建参数、VERSION 和锁文件。指纹基于实际字节、相对路径、entry 类型和可执行位的确定性排序，不依赖 mtime 或当前时间。

平台相关的目标架构、解析后的基础镜像 digest 和架构构建参数与 `source_fingerprint` 组合为独立 `build_identity`。amd64 与 arm64 对同一源码共享 source fingerprint，但具有各自 build identity 和 image digest，不能互相误用缓存镜像。

测试必须证明：修改任一 Docker 输入会改变指纹；只修改 `.dockerignore` 明确排除的验收输出不会改变指纹。Dockerfile 新增或扩大 `COPY`/`ADD` 时必须同步更新指纹测试，不能维护一个容易漏文件的手写短名单。

测试镜像写入 OCI labels：应用版本、源码修订、source fingerprint、build identity 和可复现构建 epoch。相同 Git 提交使用提交时间或显式 `SOURCE_DATE_EPOCH`，禁止把当前墙钟时间写进会导致每次失效的构建参数。`.tmp`、`.superpowers` 等本地工具或验收产物必须进入 `.gitignore` 与 `.dockerignore`；它们不能参与版本提交、build context 或指纹。

### 16.4 单指纹只构建一次

- native-architecture 测试镜像以当前平台的 `build_identity` 作为身份，同时记录共享的 `source_fingerprint`。
- `tests/docker/smoke.sh` 的 `BUILD_IMAGE=auto` 检查本地镜像的 source fingerprint 与 build identity labels；两者都匹配才复用，不存在或任一不匹配才构建。
- 当前验收编排第一次使用 `BUILD_IMAGE=auto`，成功后把相同 `IMAGE` 传给 smoke 后续阶段、faults、browser、upgrade 和 recovery，并显式使用 `BUILD_IMAGE=0`。
- 测试脚本在 `BUILD_IMAGE=0` 时发现任一身份 label 不匹配必须失败，不能暗中重建或继续测试旧镜像。
- multiarch 仍构建 amd64/arm64 OCI 产物；native runtime 测试与 multiarch 产物使用相同源码指纹，但按平台记录独立 digest。

### 16.5 Buildx driver 与缓存能力

验收脚本在构建前读取当前 Buildx builder driver，并按已确认的能力分流。未知 driver 或 inspect 失败必须在执行构建前明确失败，不能静默猜测缓存支持。

- `docker` driver 用于原生 smoke、fault 和 workspace 验收时，不传入该环境不支持的 `type=local` `cache-from`/`cache-to`，不获取外部缓存锁，也不读取、修改或删除 `.tmp/buildx-cache` 或 `BUILDX_CACHE_SEED_DIR`；构建依赖 daemon 原生缓存，证据记录 `cache=daemon`。
- `docker-container` driver 保留可移植本地缓存语义。当前 worktree 的可写缓存固定为 `.tmp/buildx-cache`，可选 `BUILDX_CACHE_SEED_DIR` 只作为只读 `cache-from` 导入已验证缓存。

在 `docker-container` 路径下：

- seed 不复制、不轮换、不删除、不修改索引。
- 当前可写缓存和 seed 可以同时作为 cache-from；cache-to 只能指向当前 worktree 的临时导出目录。
- 导出成功后检查 `index.json` 与目录完整性，再在同一父目录原子轮换为 `.tmp/buildx-cache`。
- 导出或校验失败时保留旧可写缓存并删除失败临时目录，不得用空缓存覆盖旧缓存。
- 单个 worktree 同时只允许一个 cache writer，使用有界等待的进程锁；读者可以复用最后一个已完成缓存。
- 普通测试清理保留可写缓存。`.tmp`、缓存和锁全部排除于 Git、Docker build context 与最终镜像。

两条 driver 路径使用相同的 Dockerfile、platform、固定基础镜像 digest、确定性 build args、source fingerprint、build identity 和构建后身份校验。验收环境可以显式提供其他 worktree 的 seed，但仓库脚本和文档不能硬编码开发者绝对路径。

multiarch 验收继续创建运行级专用 `docker-container` builder，分别生成 `linux/amd64` 与 `linux/arm64` OCI 产物，并使用上述事务化本地缓存。当宿主代理仅监听 daemon 命名空间的 loopback 时，调用方可以把代理主机转换为 BuildKit 容器可解析的 `host.docker.internal`，通过既有 driver options 注入；日志和发布证据只记录代理是否配置，不能输出地址或凭据。原生验收不为外部缓存导出强制切换 builder，用户当前 builder 在验收前后保持不变。

### 16.6 缓存证据与冷构建

每次 Docker 验收记录：source fingerprint、image digest、目标平台、构建耗时、是否执行构建、当前 cache/seed 路径分类，以及 BuildKit 可获得的 cache hit/miss 摘要。日志不输出宿主机敏感路径；展示路径时只用参数名或仓库相对路径。

常规验收不使用 `--no-cache`。冷构建只用于明确安排的可复现性检查或缓存异常诊断，且与功能测试结果分开记录。缓存优化的完成证据包括连续两次相同指纹验收中第二次复用镜像、缓存导出失败不破坏旧缓存，以及输入变化后拒绝复用旧镜像。

## 17. 测试策略

所有新行为先写失败测试，确认失败原因正确后做最小实现。纯文档或机械更新使用差异、格式和一致性验证，不伪造 red-green 证据。

### 17.1 Go 单元测试

- 路径：空路径、绝对路径、`.`/`..`、分隔符、Unicode、编码逃逸、根前缀碰撞。
- 文件系统：根内/根外/broken/loop symlink、symlink 竞态、特殊文件、权限与模式。
- inventory：稳定排序、UTF-8/NUL、正向文件策略、敏感材料分类、条目和字节上限、manifest schema、确定性摘要。
- include：注释、引号、转义、glob、重复、缺失、external、循环、深度和上限。
- diff：创建、修改、删除、重命名表现、二进制拒绝、4 MiB fallback 和稳定顺序。
- workspace：ETag、状态转换、容量、目标已存在、stale、needs-attention 和删除。
- journal：每个持久化边界前后崩溃的完成、回退或 needs-attention 判定。
- API 错误映射和 details 白名单。

### 17.2 集成测试

- 使用 `t.TempDir()` 的真实文件系统快照、原子写入、只读目录、磁盘满等价故障和外部并发修改。
- SQLite 迁移、事务失败、审计写入失败、进程重启、orphan workspace 和对账幂等性。
- Agent Unix Socket 对端认证、严格 JSON、未知字段、body 上限、取消、超时和 staged 清理。
- 验证 Agent 不接受任意路径、命令、Nginx 参数或写生产操作。
- HTTP 登录、Origin、CSRF、DTO、ETag、409、413、422、503、no-store 与内容不进入日志。
- 真实 `/etc/nginx` fixture 的快照前后摘要变化检测；v0.2.1 测试不调用生产 reload。

### 17.3 前端与浏览器测试

- 文件打开、编辑、显式保存、创建、复制、重命名、删除、搜索、diff 和 include 视图。
- 冲突时本地文本保留；stale/needs-attention 只读；会话过期后可复制但不可提交。
- 离开确认、命名删除 modal、drawer 焦点、tree 键盘、task tab 状态保留。
- 断言 localStorage、IndexedDB、Cache Storage 和 Service Worker 中没有配置正文。
- 在 1068、833、734、640、480、320 CSS px 检查布局、溢出、焦点顺序和 44px 触控目标。
- WCAG 2.2 AA 自动检查加关键流程人工键盘检查；自动工具不能替代行为断言。

### 17.4 Docker、升级与故障验收

- 从 v0.1.0 数据卷启动 v0.2.1，迁移后登录、状态与只读生效配置仍工作。
- 创建工作区后重建容器并重新挂载卷，工作区、分组、摘要和状态可恢复。
- 创建/写入各持久化阶段杀死 UI 或 Agent，重启后不出现错误的 ready。
- Agent unavailable、只读数据目录、空间耗尽、源配置并发变化和取消都能清理或进入明确状态。
- 工作区 CRUD 前后记录 `/etc/nginx` 摘要、Nginx master PID 和 HTTP 服务结果，三者必须不变。
- 同一源码指纹只构建一次 native 测试镜像；后续 smoke/fault/browser/recovery 使用同一 image digest。
- 验证 `docker` driver 不生成外部缓存参数、不获取缓存锁且证据为 daemon cache；验证 `docker-container` 的 seed 只读、single-writer、失败导出保留旧缓存和指纹变化拒绝旧镜像。
- 在可用的原生 linux/amd64 与 linux/arm64 runner 上执行完整 runtime 验收；某一架构没有原生 runner 时构建并检查该平台 OCI 产物，同时在发布记录中保留未完成的原生运行限制，不把模拟结果表述为原生通过。

### 17.5 质量命令

v0.2.1 的实施与验收必须按变更范围实际记录至少以下命令：


`go mod tidy` 后必须确认没有非预期依赖变化；前端安装使用项目固定 Node/npm 和 `npm ci`。

## 19. 版本、文档与提交门禁

设计阶段保持 `VERSION`、`web/package.json` 和当前镜像元数据为 0.1.0。v0.2.1 开始实施时，在同一版本基线变更中同步：

- `VERSION` → `0.2.1`。
- `web/package.json` 与重新生成的 `package-lock.json` → `0.2.1`。
- Go 构建元数据、OCI image version label 和发布脚本 → `0.2.1`。
- `/api/v1` OpenAPI 契约与类型化前端 client。

完成版本号更新并实际读取 author 与 VERSION 后，新建代码文件使用真实 git author 和 `@since 0.2.1`。不得修改已有文件的 `@since 0.1.0`。Markdown、JSON、lockfile 和生成文件不添加代码文件头。

前端实现前先更新 `DESIGN.md`；API 行为变更同步更新 `api/v1` 契约；Docker cache 参数和升级方式同步到运维文档。最终创建 `docs/release/v0.2.1-verification.md`，记录实际命令、镜像 digest、架构限制和验收证据。未验证的项不勾选、不宣称完成。

## 20. 后续版本接口边界

v0.2.1 为后续版本保留的是稳定事实，而不是提前实现能力：

- `production_digest`、`base_digest` 和 `draft_digest` 可成为 v0.2.2 发布前置条件。
- base/draft/control 分离可让 v0.2.2 构造完整候选配置，但候选构造、symlink 物化和 `nginx -t` 仍需单独设计。
- journal 与 needs-attention 状态可被 v0.2.2 扩展为发布事务，但 v0.2.1 journal 只覆盖工作区自身。
- Agent 协议可增加新的版本化 typed operation，但 v0.2.1 二进制不能接受未来操作名。
- 逻辑分组与相对路径可供 v0.3 结构化编辑复用，但不能让 AST 反向成为工作区文件系统的真源。

任何后续扩展仍必须遵守生产配置是真源、完整校验、不可变备份、原子发布、失败恢复和无任意 Shell 的全局约束。
