## 1. 文档目的

本文是 v0.6.0 的唯一设计与测试规格。它把 `PLAN.md` 中“发布候选版”的七项交付物细化为可验证的安全审计、升级与灾难恢复、Nginx 兼容矩阵、跨模块浏览器回归、运维文档和契约一致性工作。

v0.6.0 不新增产品模块、业务页面、REST 资源、Agent 操作、数据库表或 Nginx 生产写入口。现有 v0.1.0–v0.5.0 能力只允许做缺陷修复、安全加固、兼容性修复和发布工程补齐。Docker 构建、容器运行、卷升级、容器故障注入和多架构验证仍全部属于 v0.7.0。

## 2. 用户结果与完成标准

发布候选完成后，管理员和维护者能够得到以下结果：

1. 认证、会话、CSRF、登录限流、Cookie、错误响应和日志脱敏具有可复现的安全测试证据。
2. Unix Socket 的类型、所有权、权限与 peer credential 均 fail closed；Agent 只接受版本化、类型化白名单操作。
3. 能按文档创建同时覆盖 Nginx 配置真源与 UIX 持久数据的离线一致性备份，并在空目标上完成灾难恢复演练。
4. 从 v0.5.0 数据布局启动 v0.6.0 时，不丢失管理员、会话、分组、工作区、历史、证书或任务；已发布 migration 校验和保持不变。
5. 代表性 Nginx 配置矩阵同时通过 lossless AST 回归和真实隔离 Nginx `-t`/`-T` 验证；镜像未包含模块的未知指令只做 lossless 回归，不伪称真实 Nginx 可用。
6. 同一浏览器会话完成登录、配置发布、路径实验和证书签发的主要旅程，且每个变更请求都保留 Cookie、Origin、CSRF、具名确认和持久任务证据。
7. 安装、升级、回滚、备份、恢复和故障排查文档与当前 0.6.0 接口一致；API 错误码、任务状态与 UI 终态用语不互相矛盾。

## 3. 明确范围

### 3.1 包含

- 现有认证与 HTTP 安全边界的审计、测试和必要加固。
- 登录用户名+来源限流之外的来源级喷洒保护；继续使用现有持久化 throttle 表，不新增 migration。
- Agent Socket 设置后的所有权二次验证、现有 peer UID 边界和固定路由白名单回归。
- 请求日志、API details、Agent 错误、证书/Cloudflare/Route Lab 敏感值的脱敏回归。
- `0001`–`0007` migration 的顺序、校验和、幂等、失败回滚和 v0.5.0 数据重开验证。
- 维护窗口内的冷备份导出与空目标恢复流程；备份同时包含 `/etc/nginx` 和 `/var/lib/nginx-uix`，并保留 owner、mode、symlink 与不可变备份正文。
- 配置兼容 fixture、lossless AST 回归和真实隔离 Nginx 回归。
- 一个跨模块 Playwright 发布候选旅程，以及既有分模块 E2E 的全量复验。
- 用户、管理员和故障恢复文档；README 只保留入口和关键安全边界，把详细流程链接到运维文档。
- 版本号、OpenAPI 版本、前端包版本和 Docker 默认构建参数同步为 `0.6.0`，但不构建或验证 Docker 镜像。

### 3.2 不包含

- 新的系统设置页面、通用审计模块、备份下载 API、在线热备份 API或任意文件下载器。
- 新的证书服务商、Nginx 功能、配置编辑能力、路径实验能力或 Agent 命令。
- 修改 `0001`–`0007` 已发布 migration；v0.6.0 没有 schema 变化，因此不创建空的 `0008` migration。
- 在运行中的进程旁直接复制 SQLite 主文件、WAL 或证书目录并把它称为一致性备份。
- 将浏览器 mock E2E 当成真实 Nginx、真实 ACME 或 Docker 验证证据。
- Docker、Buildx、镜像扫描、SBOM、volume upgrade、PID 1、capability 或 multiarch 验证；这些由 v0.7.0 统一执行。

## 4. 不可违反的安全与数据不变量

1. `/etc/nginx` 始终是配置真源；灾备不能从 SQLite 生成或覆盖一份推测的 Nginx 配置。
2. UI/API 不接受命令、可执行路径、Socket 路径、生产根、PID、signal、任意 URL 或未定义 Agent 参数。
3. Agent Socket 必须是固定路径的真实 Unix Socket，owner/group/mode 在设置后重新读取并精确验证；peer UID 不匹配或无法读取凭据时在 HTTP 解析前断开。
4. Agent 路由使用精确 path+method 白名单；未知路径、query、重复或未知 JSON 字段、超限 Body 和无效 ID 均不得调用运行时操作。
5. 密码、Cookie、CSRF、Authorization、Cloudflare Token、ACME key authorization/TXT、私钥、配置正文、diff 正文和请求 Body 不进入普通日志、审计 details 或 API 错误。
6. 登录限流必须同时约束单个规范化用户名+直接 peer IP 和同一直接 peer IP 的跨用户名喷洒；不信任 `X-Forwarded-For`。
7. 会话只持久化 token/CSRF digest，采用 8 小时 idle 与 24 小时 absolute lifetime；登出和过期删除服务端会话。
8. 所有业务 mutation 继续同时要求唯一 Session Cookie、可信 Origin 和当前 CSRF；GET 不改变业务状态。
9. 冷备份前必须停止会写入持久层的 UI/Agent 任务并等待退出；恢复目标必须为空或由管理员明确隔离，不能与现有数据树合并。
10. 恢复后先检查 owner/mode、SQLite integrity/migration、证书材料和完整 `nginx -t`，成功前不得 reload 或报告健康。
11. v0.6.0 不修改历史 migration 内容或伪造旧版本升级结果。
12. 浏览器 E2E 中的 mock 只证明前端交互与 HTTP 契约；真实 Nginx 与本地 ACME 分别由原生集成测试证明。

## 5. 安全审计与加固

### 5.1 认证、会话、CSRF 与限流

保留现有 Argon2id、missing-user dummy hash、通用凭据错误、digest-only session、derived CSRF、严格 Origin 和 `HttpOnly; SameSite=Strict` Cookie。HTTPS `NGINX_UIX_PUBLIC_URL` 继续强制 `Secure`；未配置公开 HTTPS origin 的本地 HTTP 模式不伪造 Secure Cookie。

登录失败同时记录两个持久化 key：

- `normalized_username + direct_peer_ip`：5 次/5 分钟后阻断 15 分钟。
- 固定不可由合法用户名产生的 source bucket + `direct_peer_ip`：20 次/5 分钟后阻断 15 分钟。

请求开始时先检查两个 key，任一阻断即返回同一个 `rate_limited` 和有界 `Retry-After`。失败时两个 key 都必须记录；成功认证后清除该用户名 key 与来源 bucket。任何持久化错误均 fail closed 为内部错误，不把密码或 key 回显。

### 5.2 HTTP 与敏感信息

安全回归必须证明：

- 登录、登出和全部业务 mutation 的 Origin/CSRF 边界不因未知路由或 Content-Type 变化而绕过。
- API 响应和 SSE 使用 `Cache-Control: no-store`；HTML history fallback 不吞掉 `/api`、`/health` 或未知路径。
- 请求日志只记录 method、模板外的安全 path、status、duration 与 request ID，不记录 query、Cookie、Authorization 或 Body。
- API details 只保留按错误码允许且经过语义校验的相对 path、opaque ID、limit 与 ETag。
- 证书和 Route Lab 的安全 DTO 不含秘密正文，未知服务错误统一返回可操作但脱敏的公共错误。

### 5.3 Unix Socket 与 Agent 白名单

Socket 启动顺序保持：检查旧路径类型 → 绑定 → `lstat` → `chown` → `chmod` → 再次 `lstat` → same-file、Socket type、owner、group 与 `0660` 全部精确验证。任何一步失败都只清理本进程刚绑定且 identity 未变化的 Socket。

白名单测试从代码中的固定路由表枚举当前操作，逐项验证 method、request ID、strict JSON、typed ID/path 和输出上限；额外覆盖 `/bin/sh`、`/exec`、路径穿越、query 注入、未知方法和未知字段，断言运行时调用计数为零。

## 6. 数据升级、备份导出与灾难恢复

### 6.1 v0.5.0 → v0.6.0

v0.6.0 不改变数据库 schema。升级测试创建完整 `0001`–`0007` 数据库，写入代表性的用户、会话、登录限流、分组、工作区、release/recovery/route history、证书账户/凭据元数据/证书/任务与审计行，关闭后用 v0.6.0 重新打开，再验证：

- migration 集合仍精确为 `1..7`，校验和未变化；
- 所有代表性行与外键仍存在；
- `PRAGMA integrity_check` 与 `foreign_key_check` 通过；
- 二次打开幂等，不改变业务数据。

### 6.2 冷备份导出

唯一受支持的 v0.6.0 导出是维护窗口内的冷备份：

1. 记录应用版本和待备份根。
2. 停止接收新任务，等待 UI、证书调度器、Route Lab、release/recovery task owner 和 Agent 退出；生产 Nginx 可按管理员停机窗口统一停止以获得最清晰的一致性边界。
3. 将 `/etc/nginx` 与 `/var/lib/nginx-uix` 作为同一个备份单元复制到新目录，保留 owner、group、mode、symlink 和时间元数据。
4. 生成不含文件正文的清单：相对路径、entry type、mode、size 与 SHA-256；私钥和 Token 密文只记录摘要。
5. 对备份中的 SQLite 运行只读 `integrity_check`，检查关键目录/文件权限，并对备份中的 Nginx 根运行隔离 `nginx -t`。
6. 备份失败或校验失败时删除/隔离不完整目标，不能把它标记为可恢复点。

不得仅复制 `nginx-uix.db` 而遗漏 WAL，也不得只导出数据库、只导出 `/etc/nginx` 或只导出证书目录。

### 6.3 灾难恢复

恢复只写入空的隔离目标：先恢复两个根及元数据，再检查 SQLite、migration、证书 `0600`、目录 `0700`、工作区/备份索引与正文一致性，随后在不 reload 生产的情况下执行完整 `nginx -t`。应用启动对账完成且健康证据明确后，才允许恢复对外服务。任何摘要、权限、数据库、证书或配置校验不确定都进入人工处理流程。

原生灾备演练在临时目录执行，不覆盖本机或容器真实路径。Docker volume 的备份/恢复和升级仍由 v0.7.0 验证。

## 7. Nginx 配置兼容矩阵

fixture 至少包含以下组：

| 组 | 覆盖 | 验证方式 |
| --- | --- | --- |
| include | 多文件、多层 glob、重复 include | inventory/include graph、AST、真实 `nginx -T` |
| server | 同端口 default、exact、wildcard、regex server_name | AST/Route Lab 静态分析、真实 `nginx -t` |
| location | exact、prefix、`^~`、`~`、`~*`、nested、named | AST/Route Lab 回归、真实 `nginx -t` |
| redirects | rewrite、try_files、index、error_page、内部跳转 | AST/Route Lab 回归、真实隔离 Nginx |
| proxy | proxy_pass 无 URI、带 URI、变量、upstream 引用 | lossless AST、真实 `nginx -t` |
| upstream | IPv4、IPv6、Unix Socket、weight/backup/down/max_fails/fail_timeout | lossless AST、真实 `nginx -t` |
| TLS | SNI、多 server、多证书引用、HTTP→HTTPS redirect | 生成本地证书的真实隔离 Nginx |
| syntax preservation | 注释、CRLF、混合空白、引号、未知指令 | byte-for-byte lossless parse/render/reparse |
| unavailable module | 当前本机/镜像未包含的模块指令 | lossless AST only；不声称 `nginx -t` 通过 |

兼容测试不能依赖生产端口、固定端口、生产 PID 或生产配置。真实 Nginx 使用随机回环端口、独立 prefix/PID/log/temp 并在成功、失败和取消后清理。

## 8. 浏览器发布候选旅程测试计划

### 8.1 主旅程

**Seed：** 现有 Vite preview、匿名 Session 和严格 API mock。

**文件：** `web/e2e/release_candidate.spec.ts`

**场景：** `login-publish-route-test-and-issue-certificate`

步骤：

1. 使用键盘从 Login 提交管理员凭据。
   - 期望：进入 Dashboard；登录请求带可信 Origin、不带 Cookie/CSRF；响应建立 HttpOnly 同源 Cookie；浏览器存储为空。
2. 打开已有 ready 工作区，审阅完整 diff，运行候选检查并具名确认发布。
   - 期望：mutation 带 Cookie、Origin、当前 CSRF 和 `If-Match`；终态明确为 published/healthy，并保留 backup/release ID。
3. 打开 Route Lab，运行 GET 的静态分析与隔离测试。
   - 期望：静态预测与运行证据分区；终态来自持久任务/SSE；页面明确生产 Nginx 未 reload。
4. 打开 Certificates，创建 production DNS-01 wildcard 计划并确认执行。
   - 期望：Cloudflare Token 不进入浏览器存储/URL/历史；风险短语精确匹配；终态显示证书与任务历史。
5. 退出登录。
   - 期望：DELETE 带 Cookie、Origin、CSRF；返回 Login；后续受保护页面恢复时需要重新认证。

每个模块 mock 在切换前解除，Cookie 和内存 Session 保持在同一浏览器 context。该测试不替代已有分模块响应式、键盘、失败和刷新测试。

### 8.2 回归集合

全量 Playwright 必须继续覆盖登录限流、Session 恢复/过期、发布 rollback/needs_attention、restore/restart/retention、Route Lab 取消/超时/SSE reconnect、证书 Token/导出/取消、320px reflow、200%/400% zoom、焦点 trap 和 axe。Docker 专用 spec 在 v0.6.0 原生运行中保持明确 skip。

## 9. API 错误、任务状态与 UI 用语

### 9.1 错误码

- `code` 是程序分支使用的稳定标识；UI 不展示未知后端 message、内部 path 或 stack。
- `message` 是安全公共摘要，但前端主要操作面使用与页面语言一致的动作级文案，并附 request ID 作为排障关联值。
- 认证使用小写公共码；配置、Route Lab、证书和 Agent 使用现有稳定大写领域码。v0.6.0 不重命名既有码。
- OpenAPI `ConfigErrorCode`、Go 映射、TypeScript `APIErrorCode` 与客户端 allowlist 必须覆盖相同的公开集合；新增码必须同时更新四处并有测试。

### 9.2 任务状态

| 语义 | Release/Restore | Route Lab | Certificate | UI 终态用语 |
| --- | --- | --- | --- | --- |
| 排队/执行 | `queued`/`running` | `queued`/`running` | `queued`/`running`/`cancelling` | queued/running/cancelling，不推测成功 |
| 成功 | `succeeded` | `succeeded` | `succeeded` | 明确真实证据与生产健康边界 |
| 安全回滚 | `rolled_back` | 不适用 | 不适用 | 原状态已恢复且健康已确认 |
| 普通失败 | `failed` | `failed`/`timed_out` | `failed` | 明确生产是否未变或旧证书仍在用 |
| 取消 | `cancelled` | `cancelled` | `cancelled` | 只有服务端持久终态才称取消完成 |
| 不可判定 | `needs_attention` | cleanup failure 用阻断错误 | `needs_attention` | 需要人工处理，绝不显示成功 |

UI 不把 `failed`、`rolled_back`、`needs_attention` 合并为同一个“error”。所有终态同时使用可见文字与非颜色图形；技术 `last_error_code` 只作为安全排障证据，不替代用户可执行说明。
