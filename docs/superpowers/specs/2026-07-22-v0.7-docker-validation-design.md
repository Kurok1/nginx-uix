# Nginx UIX v0.7.0 Docker 一体化统一验证设计

> 文档状态：已完成；v0.7.0 唯一设计真源

> 版本类型：功能冻结后的部署验证版

> 源码基线：v0.6.0 完整产品能力

> 关联文档：`AGENTS.md`、`PLAN.md`、`DESIGN.md`、`docs/release/v0.6.0-verification.md`、`docs/release/v0.7.0-verification.md`

## 1. 目标与非目标

v0.7.0 不增加产品模块、REST 资源、Agent 操作或数据库 migration。它把 v0.6.0 已交付的完整能力放入最终一体化镜像，重新验证构建、启动、进程监督、持久化、安全、浏览器、故障恢复、供应链和多架构边界。

本版本不发布镜像、不创建远端 tag，也不把模拟运行写成原生运行。正式发布不可变镜像属于 v1.0.0；v0.7.0 只生成本地候选产物和可复现证据。

## 2. 候选镜像与版本身份

- `VERSION`、前端包版本、OpenAPI 和 Docker 默认构建版本统一为 `0.7.0`。
- Node.js `24.17.0`、npm `11.13.0`、Go `1.26.5`、Nginx `1.30.3-alpine-slim` 与 s6-overlay `3.2.3.0` 固定到版本和已验证 digest/checksum。
- source fingerprint 覆盖实际 Docker build context；platform、基础镜像 digest 和确定性构建参数组成 build identity。
- 同一源码、同一平台只构建一个 native 验收镜像。后续 smoke、fault、upgrade、recovery、browser 和 security 套件必须复用同一 image ID。
- 常规验收复用 BuildKit 缓存，不使用 `--no-cache`。第二次相同身份检查必须证明直接复用镜像。

## 3. 架构证据等级

本次执行主机为 Darwin/arm64，Docker daemon 为 Linux/arm64。证据严格分为：

| 等级 | arm64 | amd64 |
| --- | --- | --- |
| OCI 构建与静态检查 | 必须通过 | 必须通过 |
| 最小启动、登录、状态、停止 | 原生必须通过 | 仅真实 amd64 runner 可标记原生通过 |
| 完整 smoke/fault/workspace/browser | 原生必须通过 | 当前主机记录为未运行，不能用 Rosetta/QEMU 冒充原生通过 |

若 amd64 进程在当前 arm64 主机上失败，只有同时满足“arm64 原生通过、amd64 OCI 静态检查通过、诊断明确指向 Rosetta/QEMU/跨架构 `/proc` 或模拟器限制”时，才记录为已确认的架构限制并忽略该次模拟运行失败。无法确认原因时仍按失败处理。

## 4. 原生容器验收

### 4.1 安装、身份与持久化

- 一条 `docker run` 使用两个空 volume 启动，初始化完整默认 Nginx 树，管理员通过只读 Secret 文件登录。
- UI 只映射宿主回环随机端口；Nginx 暴露接口保持 `80/443`，Agent 只使用 `/run/nginx-uix/agent.sock`。
- 非空 `/etc/nginx` 的普通文件、隐藏文件、目录和 symlink 在启动、停止和重建后字节与元数据不变。
- 管理员、session、throttle、工作区、分组、release、backup、restore、restart、Route Lab、证书元数据、任务和审计随 `/var/lib/nginx-uix` 持久化。

### 4.2 进程、信号与健康

- PID 1 必须是 s6 init；UI 以 `10001:10001` 运行，Agent 以 root 运行并只接受固定 Unix Socket 协议，Nginx master/worker 与 API 报告的真实 `/proc` 身份一致。
- liveness 只检查 UI；readiness 和 Docker health 同时检查 SQLite、Agent 与真实 Nginx。
- `SIGTERM`/`docker stop` 在有界时间内转发并以零状态退出；重建后 SQLite integrity、foreign key 和 Nginx 配置保持一致。
- UI、Agent、Nginx 单进程崩溃分别验证监督恢复或明确永久失败；不能以仍存在 PID 1 冒充健康。

### 4.3 完整产品闭环

同一最终镜像至少覆盖：登录与 session、Dashboard/生效配置、工作区 CRUD 与 ETag 冲突、结构化 upstream/location 变更、发布与 reload、备份与人工恢复、固定 restart、Route Lab 静态分析与隔离运行、证书目录/账户/任务边界，以及安全审计查询。

真实证书网络测试只允许本地 ACME 测试服务或 Let's Encrypt staging，禁止消耗 production 配额。若最终镜像的固定外部网络策略无法在不改变生产安全边界的情况下接入本地服务，则必须保留既有本地 ACME 集成证据，并把“最终容器真实签发”明确标为未通过，不能用 mock UI 结果替代。

## 5. 升级、重建与灾难恢复矩阵

官方直接升级路径是 v0.6.0 → v0.7.0；v0.7.0 不新增 migration，数据库集合仍为 `1..7`。同时保留 v0.1.0 数据直接打开的长链兼容测试，证明单调 migration，而不把它宣传为跳过中间发布文档的推荐运维路径。

| 来源 | 目标 | 必须保留 |
| --- | --- | --- |
| 空 volume | v0.7.0 | 默认配置、管理员、migration `1..7` |
| v0.1.0 fixture | v0.7.0 | 用户、session、配置字节并完成 migration `1..7` |
| v0.6.0 release commit | v0.7.0 | 两个持久根、全部领域数据、权限与开放状态 |
| v0.7.0 冷备副本 | 新空 volume | 摘要、owner/mode/symlink、SQLite、配置、证书与历史 |
| v0.7.0 已有 volume | 重建同镜像 | session、任务、历史和 Nginx 真源 |

备份与恢复必须同时处理 `/etc/nginx` 和 `/var/lib/nginx-uix`。只复制 SQLite 主文件、把非空目标合并恢复或从 SQLite 反向生成配置均判定失败。

## 6. 故障注入

至少覆盖无效/缺失 Nginx 配置、只读数据卷、4 KiB 空间等价、管理端口冲突、Agent 下线、UI 崩溃、Nginx 重复崩溃、reload/restart 失败、取消与超时。每个场景都断言生产配置摘要、Nginx 真实状态、持久任务终态和清理结果；无法安全判断时必须进入 `needs_attention`。

主机文件系统无法可靠制造真实块设备磁盘满时，4 KiB tmpfs 与确定性写入故障只作为等价证据，并在发布记录中注明，不把它写成真实磁盘满。

## 7. 权限与容器安全边界

- 候选不使用 `--privileged`、host PID/network、Docker Socket 或额外设备。
- 先以 `--cap-drop ALL` 运行，再逐项加入镜像实际启动所需 capability；每项都记录对应的 s6、Nginx 或 owner/mode 操作，未证明需要的 capability 不保留。
- Agent Socket 必须为真实 socket、owner `0:10002`、mode `0660`；非组用户连接失败。
- `/var/lib/nginx-uix`、工作区、备份、证书 vault、私钥、Token 和 SQLite 权限按根规范验证。
- 最终文件系统不含 Go/Node/npm/npx、浏览器、`node_modules`、源码、测试 fixture、构建缓存、包管理缓存、临时 Secret 或归档。

## 8. 浏览器与网络边界

Playwright 在独立的固定浏览器镜像中运行，通过运行级 Docker network 访问 UI 容器。发布镜像本身不得包含浏览器层。

- 真实容器流程覆盖登录、工作区持久编辑、ETag 冲突和清理。
- 当前所有前端浏览器测试在固定浏览器镜像中通过，Docker 专项按环境条件执行而不是伪造 base URL。
- 在 `1068/833/734/640/480/320` CSS px 检查页面级溢出、44px 触控目标和响应式切换；键盘验证包括焦点可见、树/标签方向键、Modal Escape/焦点恢复和注销。
- UI 端口只映射到 `127.0.0.1`；容器网络中仅浏览器测试容器可访问管理端。Agent Socket、SQLite 和宿主 Docker API 均不通过 TCP 暴露。

## 9. 多架构、SBOM 与漏洞门禁

- 分别构建 `linux/amd64`、`linux/arm64` OCI layout，校验 descriptor digest/size、平台字段、config labels、healthcheck、entrypoint、volume 和 source identity，再合并为本地多平台 layout。
- BuildKit 为候选生成 SPDX SBOM attestation；验收校验 attestation 与对应平台 manifest 关联且可解析。
- 漏洞扫描器镜像必须固定版本与 digest，扫描数据库更新时间和扫描时间写入证据；扫描结果不得包含 CRITICAL/HIGH 未处置漏洞。若数据库不可用或扫描器失败，门禁为未通过而不是跳过。
- 扫描发现来自固定基础镜像的漏洞时，先确认是否存在同系列已修复 digest；升级基础镜像属于安全维护，不得通过 ignore 文件静默放行。确属无修复且不可达的例外必须逐项记录 CVE、组件、理由和到期时间。

## 10. 完成与证据

实施时先运行静态脚本测试并构建一次 native 镜像。主矩阵先校验该镜像身份并构建双架构 OCI/SBOM，再按顺序复用 exact native image 完成 minimal boot、smoke、fault、workspace/release/recovery、upgrade、security、ACME 和 browser；最后扫描并重新计算 source fingerprint，证明验收期间输入没有变化。

只有实际通过的项目才能在 `PLAN.md` 勾选。`docs/release/v0.7.0-verification.md` 必须记录主机/daemon 架构、完整命令、exit code、image ID、source/build identity、manifest digest、缓存分类、扫描数据库时间、原生/静态/未运行边界和脱敏后的失败诊断。

最终执行结果、digest、命令和已知边界见 [v0.7.0 验收证据](../../release/v0.7.0-verification.md)。
