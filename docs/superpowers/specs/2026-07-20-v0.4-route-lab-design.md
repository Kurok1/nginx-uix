## 1. 文档目的

本文把 `PLAN.md` 中 v0.4.0“路径实验室版”细化为可实施、可测试和可恢复的唯一版本规格。管理员可以选择一个尚未发布的 `ready` 工作区，以 Host + URI 等请求语义在第二个隔离 Nginx master 中执行真实请求，并同时获得静态候选解释与运行时最终命中证据。

路径实验室不是发布流程、通用 HTTP 客户端或任意 Nginx 启动器。配置仍以生产 `/etc/nginx` 和工作区 draft 为事实来源；SQLite 只保存测试任务、阶段、受限请求摘要、静态分析和运行结果。测试成功不改变工作区、不发布配置、不 reload/restart 生产 Nginx。

本规格的 Nginx 语义基线是官方的 [request processing](https://nginx.org/en/docs/http/request_processing.html)、[server names](https://nginx.org/en/docs/http/server_names.html)、[`location`](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)、[rewrite](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html) 和 [access log](https://nginx.org/en/docs/http/ngx_http_log_module.html) 文档。静态解释只报告能够证明的候选和排除事实；真实沙箱记录是最终命中的权威证据。

## 2. 用户结果与完成标准

管理员能够：

1. 对当前 workspace ETag 下的 scheme、port、Host、SNI 和 URI 生成静态 server/location 候选解释。
2. 看见 exact、wildcard、regex、default server 以及 exact、最长 prefix、`^~`、regex、nested location 的优先级和排除原因。
3. 以 HTTP/HTTPS、Method、Query、Headers 和可选 Body 在随机回环端口执行一次真实请求。
4. 看见最终 server Route ID、location Route ID、最终 URI、upstream、状态码、受限响应头/正文、耗时和断言结果。
5. 取消 queued/running 测试；超时、取消、请求失败和 Agent/UI 退出后不会留下沙箱 master、worker、PID、Socket、日志或临时文件。
6. 查看按服务端稳定顺序保存的历史，并复制未被脱敏的安全参数重新构造测试。

后端交付只有同时满足以下条件才完成：

- 静态分析绑定 workspace ID、revision、draft digest 和强 ETag，输入或 draft 改变后不能复用旧结论。
- Agent 只接受类型化 route-test 请求；连接目标和 Nginx/stage/workspace/production 路径全部为固定可信路径。
- 沙箱复制完整候选、隔离绝对 include、重写全部 listen/PID/log/temp 路径并在启动前执行 `nginx -t`。
- 每个可到达 HTTP server/location 都有稳定 Route ID；最终证据来自处理结束位置的专用 access log，而非响应头猜测。
- HTTP/HTTPS、取消、超时、输出上限、启动失败和 UI 断连均有清理证据。
- exact、最长 prefix、`^~`、regex 顺序、nested、rewrite、try_files 和 error_page 由真实 Nginx 集成测试覆盖。
- API、SQLite、SSE、审计和应用生命周期测试通过，且生产 master PID、监听端口和配置摘要不变。

完整 v0.4.0 的前端页面、响应式、键盘与浏览器验收已于 2026-07-21 通过；完成证据统一记录在 `docs/release/v0.4.0-verification.md`。

## 3. 范围

### 3.1 包含

- 基于 v0.3 `DraftSnapshot` 和 `nginxast.Project` 的 ETag 绑定静态分析。
- 常用 TCP `listen` 端口、`default_server`、`ssl` 和 server_name exact/wildcard/regex/default 分析。
- exact、prefix、`^~`、`~`、`~*`、nested 和 named-internal 位置候选解释。
- URI percent-decoding、dot segment 和 `merge_slashes` 能够静态确定时的规范化说明。
- 完整候选树复制、workspace draft overlay 和绝对 include 隔离。
- 全部沙箱 listener 到随机 `127.0.0.1` 高位端口的映射。
- 独立 prefix、PID、error/access log、client/proxy/FastCGI/uWSGI/SCGI temp 目录。
- 沙箱专用稳定 server/location Route ID 和最终 access-log 证据。
- HTTP/HTTPS、Host、SNI、Method、URI、Query、受控 Headers 和可选 Body。
- 期望状态码、包含文本和禁止文本断言。
- queued/running/terminal 任务、阶段事件、用户取消、全局超时和并发上限。
- SQLite 历史、稳定 cursor 分页、普通审计摘要、REST 与 SSE。
- 基于 `DESIGN.md` 的 Route Lab 页面、静态/运行证据分离、任务取消、SSE 重连、历史安全复制和响应式/可访问性验收。
- 原生真实 Nginx 集成测试；Docker 统一留到 v0.7.0。

### 3.2 不包含

- 发布、reload、restart、restore、工作区写入或任何生产配置修改。
- 任意目标 URL、任意目标 IP、开放代理、端口扫描或绕过沙箱回环连接。
- TCP/UDP `stream`、QUIC/HTTP3、mail、PROXY protocol、Unix listen socket 或动态 listen 参数。
- WebSocket/CONNECT 隧道、流式响应、无限下载、客户端证书或任意 TLS 校验设置。
- 证明 rewrite、try_files、index、error_page、X-Accel-Redirect 或模块子请求的完整内部跳转链。
- 将 Go RE2 对 PCRE 的近似判断伪装成 Nginx 正则事实；无法证明时明确为 `indeterminate`。
- 在 SQLite、日志或审计中保存请求 Body、Authorization/Cookie 类 Header 值、完整响应正文或完整 Agent 诊断。
- Docker 构建、容器运行、卷、容器升级、多架构与最终镜像复验；统一属于 v0.7.0。

## 4. 不可违反的安全与数据不变量

1. 请求的网络连接地址始终由 Agent 固定为本次沙箱的 `127.0.0.1:<random_port>`；Host 和 SNI 只改变 HTTP/TLS 语义，不能改变连接目标。
2. Agent 不接收 executable、命令参数、生产路径、workspace 路径、stage 路径、PID 路径、日志路径或目标 URL。
3. workspace 必须为 `ready`，且 queue 时的 workspace ID、revision、production digest、draft digest 和强 `If-Match` 全部一致。
4. Agent 在根权限边界内重新验证 production/workspace digest，不能信任 UI 进程提交的“已验证”标志、Route ID 映射或配置正文。
5. 沙箱只复制候选并修改临时副本；不写生产 `/etc/nginx`、workspace base/draft/control、备份或证书。
6. 沙箱 master 使用独立 process group、prefix 和 PID；成功、失败、超时、取消、客户端断连和 Agent shutdown 都先 TERM、等待，再 KILL 整个拥有的 process group 并回收。
7. Agent 启动先对固定 Route Lab 根执行有界对账；只处理具有合法 owner marker、PID 身份和根内 canonical path 的遗留目录，无法证明所有权时 fail closed 并报告错误。
8. 单次请求、Body、Header 数量/总量、响应 Header、响应片段、日志、诊断、阶段和历史页全部有固定上限。
9. `CONNECT`、`TRACE`、包含控制字符的 method/header/URI、用户提交的 `Host`/`Content-Length`/hop-by-hop Header 和保留的内部测试 Header 均拒绝。
10. 非 GET/HEAD/OPTIONS 方法或任何非空 Body 必须提交精确确认值 `RUN SIDE-EFFECTING REQUEST`；确认值不持久化、不记录日志。
11. 请求 Body 和敏感 Header 值只在当前 UI→Agent 调用内存中存在；历史只保存 size/digest、Header 名和 redacted 标志。
12. 响应不返回 `Set-Cookie`、`WWW-Authenticate`、`Proxy-Authenticate`、认证 token 或 Agent 注入的内部 Header；正文片段只按有界 UTF-8 文本返回。
13. 静态预测与运行证据使用不同字段和状态；不一致时保留双方证据，不自动把预测改写成“命中”。
14. Route Lab 不持有生产变更 lease，也不能与 release/restore/restart 共享或调用其写接口。

## 5. 总体架构

```text
Browser
  │ POST analysis / queue / cancel; GET result/history/SSE
  ▼
nginx-uix HTTP boundary
  └── routelab.Service
      ├── verified WorkspaceStore.DraftSnapshot
      ├── static Analyzer (server + location candidates)
      ├── RouteLabRepository (SQLite task/stages/history)
      └── typed RouteLabAgent
              │ Unix Socket, fixed action + bounded DTO
              ▼
        nginx-uix-agent / runtime.Service
          1. reverify production + workspace identities
          2. copy production and overlay draft in fixed Route Lab root
          3. rewrite include/listen/PID/log/temp and inject Route IDs
          4. nginx -t
          5. start second nginx master in owned process group
          6. request fixed loopback target with Host/SNI semantics
          7. collect response + final access-log evidence
          8. TERM/KILL/reap and remove stage

Production /etc/nginx + production master: read-only and never signalled
Workspace draft: read-only and never changed
```

组件边界：

| 单元 | 负责 | 不负责 |
| --- | --- | --- |
| `routelab` analyzer | 请求规范化、server/location 候选、理由、稳定 Route ID | 文件复制、启动进程、HTTP、SQLite |
| `routelab.Service` | ETag 绑定、任务状态机、持久化、Agent 编排、取消结果 | Nginx 命令、绝对路径、前端状态 |
| `runtime` Route Lab | 固定根物化、临时重写、真实 Nginx/HTTP、进程组清理 | 用户认证、历史分页、发布 |
| `store` | run/stage 原子状态、稳定历史和审计 | 配置正文、请求 secret、进程控制 |
| `httpapi` | auth/Origin/CSRF/If-Match、严格 DTO、REST/SSE | 静态语义或 Agent 命令 |
| `app` task owner | request-independent goroutine、per-run cancel、bounded shutdown | 领域状态推断 |

`routelab` 在消费方定义 `WorkspaceStore`、`Repository`、`Agent` 和 `Clock` 小接口。`config.Service`、`store.DB` 和 `runtime.AgentClient` 提供具体实现；`config` 不依赖 Route Lab。

## 6. 请求模型与限制

### 6.1 输入

```text
workspace_id + strong If-Match
scheme: http | https
host: ASCII hostname / bracketed IPv6 / IP; no scheme, userinfo, path or control characters
port: 1..65535; absent -> 80/443
sni: HTTPS optional DNS name; absent -> DNS-shaped host; HTTP must be empty
method: GET/HEAD/OPTIONS/POST/PUT/PATCH/DELETE from fixed set
uri: origin-form absolute path beginning with /
query: raw query without leading ?, fragment or control bytes
headers: ordered unique case-insensitive names, at most 32, combined name/value <= 16 KiB
body: at most 64 KiB
timeout_ms: 100..30000, default 5000; whole task hard limit 45 seconds
assertions: optional status; optional contains/forbidden UTF-8 text, each <= 1024 bytes
confirmation: exact side-effect phrase when required
```

Header 名必须符合 HTTP token。拒绝 `Host`、`Content-Length`、`Transfer-Encoding`、`Connection`、`Upgrade`、`Proxy-*`、`Trailer`、`TE`、内部 `X-Nginx-UIX-*` 和任何换行。`Authorization`、`Cookie` 和名称包含 `token`、`secret`、`key` 的 Header 可以用于当前请求，但值永不进入 SQLite、API terminal history、日志或审计，并使历史参数标记 `replayable:false`。

### 6.2 输出上限

- HTTP response header 最多 64 个、规范化后总计 32 KiB；只公开安全 allowlist 与不敏感的 `X-*`，始终排除认证和 Cookie Header。
- 响应 Body 最多读取 64 KiB，历史/API 只保存/返回前 16 KiB 的有效 UTF-8 文本片段；二进制或未知 content type 返回 size/digest/`snippet_omitted:true`。
- Agent stdout/stderr 合计 1 MiB；Nginx error/access log 各 1 MiB；超限终止测试并返回稳定错误。
- 单 workspace 静态候选最多 1000 server、5000 location、10000 candidate fact；达到上限不返回伪完整结果。
- 同一 Agent 最多并发 2 个沙箱；UI 最多保留 8 个 active run，超过返回 429/`ROUTE_LAB_BUSY`。

## 7. 静态 server 选择分析

### 7.1 listener

Analyzer 从 `http` 直接子 server 的 direct `listen` 读取端口、地址、`default_server`、`ssl` 和已知参数。没有 listen 时按 Nginx 默认端口形成显式 derived listener fact。动态参数、Unix socket、`quic`、`proxy_protocol`、无法解析的地址或同端口多个具体地址组会标为 blocking/indeterminate，不能创建宣称等价的沙箱。

请求只提供 port，不提供生产目的 IP。常见 wildcard/单地址 listener 可唯一成组；同一 port 同时存在多个具体地址且无法由语义唯一选择时返回 `ROUTE_LISTENER_AMBIGUOUS`，而不是任意合并 server 集合。

每个 server candidate 包含：

- stable server Route ID、相对 source range。
- listen facts、是否进入请求 listener group、排除 reason。
- 是否是 group default、默认来源是显式 `default_server` 还是 source-order fallback。
- `ssl` 与 scheme 是否一致。

### 7.2 server_name

在唯一 listener group 内按官方优先级分析：

1. exact name；
2. 最长的 leading wildcard（`*.example.org`/`.example.org`）；
3. 最长的 trailing wildcard（`mail.*`）；
4. source order 中第一个可证明匹配的 PCRE-style regex；
5. listener default server。

Host 比较去掉合法端口和单个末尾点并做 ASCII lower-case；IDN 只接受调用方提供的 ASCII punycode，不在服务端猜测转换。Go regexp 无法表达的合法 PCRE、`$hostname` 或变量型名称保持 `indeterminate`。如果一个更高优先级候选无法证明不匹配，静态 winner 为空但候选列表完整保留；运行沙箱仍可给最终 server。

HTTPS 同时展示 SNI server candidate 与 HTTP Host final candidate。二者不同时不报错；结果明确区分 TLS selection 和 request selection，且最终 Route ID 由运行日志确认。

## 8. 静态 location 候选分析

静态输入使用 path 的 Nginx-normalized projection；如果 `merge_slashes`、percent decoding 或字符语义不能唯一证明，则保留原 URI，并把 prediction 标为 `indeterminate`。

每一层 location 搜索输出有序 candidate facts：

1. exact literal 相等时立即选中，其他 sibling 标为 `exact_selected` 排除。
2. 所有匹配 prefix 按 byte length 排序，记住最长；较短项标为 `shorter_prefix`。
3. 最长 prefix 是 `^~` 时跳过当前层 regex，并记录 `prefix_priority_stops_regex`。
4. 否则按 source order 检查 `~`/`~*`；首个可证明匹配项选中，后续项标为 `earlier_regex_selected`。
5. 没有 regex 命中时回到最长普通 prefix；没有 prefix 时使用 server context Route ID。
6. 进入 literal prefix 后递归分析 direct nested location；named location 不参与外部 URI 的初次匹配，只作为可能的 internal redirect candidate。

PCRE/RE2 差异、变量、无法证明的 nested 上下文、ambiguous include 或 v0.3 project incomplete 都不能生成“确定 winner”。静态分析可以带 `complete:false` 返回解释，但 route run 只有在 Agent 能够对全部可达 server/location 注入 Route ID 时才启动；否则 fail closed。

静态结果只预测首次 URI location。rewrite、try_files、index、error_page 和 X-Accel-Redirect 可能改变最终 URI/location；这些 directive 只产生 `runtime_may_redirect` fact，最终链条不做猜测。

## 9. Route ID 与沙箱配置变换

### 9.1 稳定身份

Route ID 使用 `route-v1`、relative path、node source span、node kind 和 header identity 的长度前缀 SHA-256，公开前 128 bit lowercase hex：

```text
server route:   srv_<32 hex>
location route: loc_<32 hex>
server fallback location: srv_<32 hex>
```

同一 draft 内容与 source placement 下稳定；source/header 改变后自然变化。API 通过映射返回 matcher、parent Route ID 和相对 source range，不公开 byte offset 或临时绝对路径。

### 9.2 临时变换

Agent 复用 v0.2 candidate materialization 的安全复制与 overlay，但变换仅发生在 owner-only Route Lab stage：

1. 重新验证 production digest、workspace state/control/manifest 和 draft digest。
2. 复制完整 production tree、overlay draft、计算 candidate digest、隔离指向 `/etc/nginx` 的绝对 include。
3. 为每个支持的原 listener group 预留随机 `127.0.0.1:0` 端口并在写入配置前关闭 reservation；端口只在本次 stage 内使用。
4. 重写每个 `listen` 到对应 loopback port；保留 `default_server`、`ssl` 和兼容的 HTTP 参数，删除 socket-tuning 参数；不支持的协议参数 fail closed。
5. 删除临时副本内原有 `access_log`，在 http 级注入唯一 JSON access log；替换/注入独立 `pid`、`error_log`、`daemon off`、`master_process on` 和所有 temp path。
6. 在每个 server/location block 的第一条 rewrite 指令之前插入随机变量名的 `set`，值为稳定 Route ID；随机变量名防止与用户变量冲突。
7. access log 使用 `escape=json` 记录 test token、server Route ID、location Route ID、`$uri`、`$status`、`$upstream_addr`、`$upstream_status` 和 `$request_time`。
8. 对变换后的完整配置重新 parse，并执行真实 `nginx -t`；任何 source edit 重叠、Route ID 缺失或 Nginx 拒绝都不启动。

专用 access log 在请求处理结束的 location 上下文写入，能够反映可靠的最终 location；它不尝试记录未被 Nginx 可靠暴露的完整 redirect chain。

## 10. 沙箱进程与真实请求

Agent 使用 `exec.CommandContext` 的固定 Nginx executable 和独立参数启动 foreground master。启动进程拥有新的 process group；stage owner marker 持久化 run ID、随机 nonce、candidate digest 和 master PID identity。启动成功必须同时满足：

- `nginx -t` 已通过；
- master 仍存活，PID 文件与启动 PID/identity 一致；
- 目标 loopback port 在超时内 accept；
- production master PID 和 production listener snapshot 与启动前一致。

HTTP client 禁止代理、redirect、cookie jar、keep-alive 和环境代理。DialContext 忽略 URL host，固定连接目标 loopback mapping；HTTPS 的 `tls.Config.ServerName` 仅来自已验证 SNI，证书链不作为 Route Lab 路由断言，且此受控跳过验证只用于固定回环沙箱。

每次只发一个请求，内部随机 Header 关联唯一 access-log row。响应完成或达到片段上限后关闭连接，等待 bounded access-log flush，要求恰好一个主请求证据。没有证据、多个冲突证据或未知 Route ID 返回 `ROUTE_EVIDENCE_INCOMPLETE`，不得从静态预测填补。

最终清理顺序：关闭 client transport → TERM process group → 等待 master/workers → KILL remaining group → wait/reap parent → 验证 PID/port 不再存在 → 删除 stage。清理失败覆盖普通业务失败并返回 `ROUTE_CLEANUP_FAILED`；不能报告成功。

## 11. 任务状态、取消与重启对账

### 11.1 状态机

```text
queued
  -> running/preparing
  -> running/validating
  -> running/starting
  -> running/requesting
  -> running/collecting
  -> succeeded/completed
  -> failed/failed
  -> cancelled/cancelled
  -> timed_out/timed_out
```

每次 transition 与 immutable stage event 在一个 SQLite transaction 内完成。Terminal 状态不可重新运行。断言不通过仍是技术执行 `succeeded`，但 `assertions_passed:false`；启动、请求或证据失败才是 task `failed`。

### 11.2 用户取消

`POST .../cancellations` 只设置 durable `cancel_requested_at` 并通知 app task owner 的 per-run cancel function。queued task 可直接 terminal；running task 由 Agent context cancellation 执行清理后 terminal。HTTP 客户端断开 queue/cancel 请求不等于取消，SSE 断开也不改变任务。

### 11.3 UI/Agent 生命周期

- app task owner 使用 `context.WithoutCancel` 持有 request-independent run，维护有界 `runID -> cancel` map。
- UI graceful shutdown 先停止接收新任务，再取消所有 route runs，并等待 Agent 清理；超时返回明确 shutdown error。
- UI 启动把遗留 queued/running/cancel-requested DB task 终结为 `failed/ui_interrupted`，不盲目重跑可能有副作用的 HTTP 请求。
- Agent 启动在监听 Unix Socket 前对账固定 Route Lab 根并清理可证明属于 Route Lab 的遗留进程；任何不可证明目录使 Agent readiness 失败。

## 12. SQLite 与历史

新增单调 migration：

- `route_lab_runs`：ID、workspace/revision/digests、state/stage、safe request JSON、secret/body metadata、static analysis JSON、terminal result JSON、error code、actor/request ID 和时间。
- `route_lab_stages`：run ID、monotonic sequence、stage、result、stable code、bounded public details 和 occurred time。

`safe_request_json` 只包含 scheme/host/port/SNI/method/URI/query、非敏感 Header、敏感 Header 名、body size/digest、timeout 和非敏感 assertion。Body、confirmation 和敏感 Header 值永不持久化。`terminal_result_json` 只包含有界响应、Route evidence 和 assertion outcome。

历史按 `(created_at DESC, id DESC)` 排序，cursor 使用服务端签名/编码的最后一项键；默认 20、最大 100。过滤只支持 exact workspace ID 和 terminal/nonterminal state，不接受任意 SQL sort。删除 workspace 不删除历史，也不能被历史 FK 阻止。

任务创建和取消写普通 audit：action、run/workspace ID、method/scheme、side-effecting bool、result 和 request ID；不写 URI query、Header 值、Body、assertion 文本、response snippet 或 upstream 地址。

## 13. REST API 与 SSE

| 方法与路径 | 语义 |
| --- | --- |
| `POST /api/v1/config/workspaces/{id}/route-analyses` | 对当前 ETag 纯计算静态解释 |
| `POST /api/v1/config/workspaces/{id}/route-tests` | 复核输入/ETag、持久化 queued task 并返回 202 |
| `GET /api/v1/route-tests` | 稳定分页历史 |
| `GET /api/v1/route-tests/{run_id}` | 完整持久化 task/stages/result |
| `GET /api/v1/route-tests/{run_id}/events` | snapshot + stage + terminal SSE，支持 `Last-Event-ID` |
| `POST /api/v1/route-tests/{run_id}/cancellations` | 请求取消 queued/running task |

analysis 和 queue 需要认证、同源 Origin、CSRF 和单个强 `If-Match`；取消需要认证、Origin/CSRF。GET/SSE 需要认证。全部响应 `Cache-Control: no-store`；SSE 设置 `X-Accel-Buffering: no`、5 秒写 deadline、2 秒 heartbeat，terminal 后关闭。

所有请求使用 strict JSON、拒绝 unknown/duplicate key 和宽松类型转换。queue 响应含 Location；请求 Body/mutation 最大 128 KiB。DTO list 非 null、时间为 UTC RFC3339、duration 字段显式 `_ms`。

稳定错误至少包括：

| HTTP | code | 场景 |
| --- | --- | --- |
| 409 | `ROUTE_WORKSPACE_CONFLICT` | ETag/revision/digest 改变 |
| 422 | `ROUTE_PROJECT_INCOMPLETE` | include/AST/Route ID 注入不能证明完整 |
| 422 | `ROUTE_LISTENER_AMBIGUOUS` | port 对应多个无法唯一选择的地址组 |
| 422 | `ROUTE_REQUEST_INVALID` | Host/SNI/method/URI/header/body/assertion 非法 |
| 409 | `ROUTE_CONFIRMATION_REQUIRED` | 非幂等或 Body 请求缺少精确确认 |
| 429 | `ROUTE_LAB_BUSY` | active/concurrency 上限 |
| 422 | `ROUTE_CANDIDATE_INVALID` | 变换后的真实 `nginx -t` 失败 |
| 503 | `ROUTE_SANDBOX_START_FAILED` | master/port 未就绪 |
| 504 | `ROUTE_REQUEST_TIMEOUT` | 请求或全局 deadline |
| 409 | `ROUTE_EVIDENCE_INCOMPLETE` | access-log final evidence 缺失/冲突 |
| 500 | `ROUTE_CLEANUP_FAILED` | process/port/stage 清理无法证明 |
| 409 | `ROUTE_ALREADY_TERMINAL` | 对 terminal run 取消 |
| 404 | `ROUTE_TEST_NOT_FOUND` | run 不存在 |

details 白名单只允许 run/workspace/Route ID、relative source、current ETag、limit 名和值、diagnostic code 和 stage；不返回绝对路径、命令、raw log 或请求 secret。

## 14. Agent 协议

新增固定 action `route_test_execute`。Agent request 只含：run ID、workspace ID、production/draft digest、validated typed request、stable timeout 和 request ID。Agent 自己重建 project/Route map；UI 不发送配置正文、edit、绝对路径、端口 mapping 或 executable。

Agent response 只含 candidate digest、Route evidence、HTTP result、bounded diagnostics、timings 和 cleanup evidence。协议 request/response 都有独立大小上限和 strict JSON；Agent error classifier 映射 route-specific code，不泄漏 stage 路径或 Nginx raw stderr。

Unix peer credential 规则不变，只接受固定 UI UID。Agent handler 的 request context 是 sandbox 的所有者；连接取消必须传播到 process group cleanup。

## 15. 日志、审计与敏感信息

HTTP 边界只记录 request ID、run/workspace ID、state/stage、method、scheme、side-effecting、result 和 duration。Agent 记录 run ID、candidate digest abbreviation、stage、process cleanup result 和 duration。

禁止日志/审计包含：

- URI query、request/response Body 或 snippet。
- Header 值、Cookie、Authorization、CSRF、SNI certificate 内容。
- assertion text、confirmation phrase、upstream URL/address。
- production/workspace/stage 绝对路径、命令行、PID file content 或 raw Nginx output。

运行结果可以向已认证管理员返回最终 upstream 的受限地址摘要，但普通日志和 audit 不记录。内部 Route/Test token 不进入公开 DTO。

## 16. 测试策略

所有新行为先有失败测试，再做最小实现。

### 16.1 analyzer 与领域服务

- listener 默认/显式端口、ssl/default、wildcard/单地址/多地址歧义和 unsupported 参数。
- exact、leading/trailing wildcard、regex order、default server、Host trailing dot/case 和 SNI/Host 分离。
- exact、longest prefix、`^~`、regex source order、nested/named 与 no-location fallback。
- PCRE-only、merge_slashes、percent/dot normalization 和 rewrite/try_files/error_page indeterminate facts。
- stable Route ID、ETag binding、input validation、confirmation、limits、assertion pass/fail。
- queue/run/cancel/timeout/Agent error/cleanup error/reconcile 状态机与 race。

### 16.2 Agent、文件系统与真实 Nginx

- candidate copy/overlay/include isolation 不改变 production/workspace byte。
- listen/PID/log/temp rewrite 和 Route injection render/reparse；existing access_log/return/rewrite 不绕过 marker。
- port reservation、startup failure、request failure、timeout、caller cancel、output overflow 和 process-group cleanup。
- HTTP Host、HTTPS SNI、Header/Body、no redirect、fixed loopback dial 和 response redaction。
- 真实 Nginx fixture 覆盖 exact、prefix、`^~`、regex order、nested、rewrite、try_files、error_page 和 upstream evidence。
- 每个真实用例前后 production master PID、worker、listener 和 config digest 一致；stage root 为空且随机端口不可连接。

### 16.3 Store、API 与应用生命周期

- migration fresh/upgrade/checksum、约束、terminal invariant、stage sequence、stable cursor 和 page limit。
- request secret 永不落库；history redaction/replayable 标志；audit safe summary。
- auth/Origin/CSRF/If-Match、strict DTO、no-store、error details whitelist 和 response bounds。
- SSE snapshot/reconnect/heartbeat/terminal；cancel race；UI shutdown 与 restart reconciliation。
- `go test ./...`、`go test -race ./...`、`go vet ./...`、`golangci-lint run`、`go mod tidy/verify` 全部通过。

### 16.4 前端与浏览器

先扩展 `DESIGN.md` 的 Route Lab token/components，再实现输入、静态解释、运行结果、历史、复制参数、取消和断点布局。浏览器验收明确区分 static/runtime，覆盖非幂等确认、SSE reconnect、键盘、焦点、320px/zoom/reflow 和浏览器持久化无 secret；上述验收均已通过。
