> 文档状态：已确认，可实施
>
> 制定日期：2026-07-14
>
> 目标版本：0.1.0
>
> 关联文档：`AGENTS.md`、`PLAN.md`、`DESIGN.md`

## 1. 文档目的

本文把 `PLAN.md` 中 v0.1.0“基础可观测版”细化为可执行的产品和技术设计。v0.1.0 要交付的是一套安全、只读、可诊断的一体化 Nginx 运行环境，而不是配置管理器的缩小版。

本设计只解释 v0.1.0 的实现边界。根级 `AGENTS.md` 继续约束全部工程、安全和质量活动，`DESIGN.md` 继续作为前端视觉和交互的权威基线。实现中发现三者冲突时必须停止相关工作并请求确认。

## 2. 目标与完成标准

v0.1.0 的用户结果是：管理员通过一条 Docker 命令启动包含 Nginx UIX、特权 Agent、进程监督器和 Nginx 的单个容器，然后从受保护的 Web UI 查看真实运行状态与实际生效配置。

版本必须同时满足以下目标：

1. 一体化镜像能够在 `linux/amd64` 和 `linux/arm64` 上启动。
2. `/etc/nginx` 为空时写入最小默认配置；只要目录非空就绝不覆盖其中任何内容。
3. UI、Agent、Nginx 分进程运行，单个进程故障不会被伪装成整个系统健康。
4. 管理界面从首次启动起即要求认证、登录限速、安全会话和 CSRF 防护。
5. Dashboard 展示经过 `/proc` 验证的 Nginx master、worker、启动时间、版本、编译参数和启动校验结果。
6. 配置页只展示固定命令 `nginx -T` 输出中实际加载的文件和内容，不扫描未生效文件。
7. Nginx 配置错误或进程停止时，管理界面仍可用于诊断，同时容器 readiness 明确失败。
8. 所有命令、输出、路径、权限、超时和错误都受固定边界约束。

## 3. v0.1.0 范围

### 3.1 包含

- Go Web/API 服务 `nginx-uix`。
- Go 本地特权服务 `nginx-uix-agent`。
- Vue 3 + TypeScript 管理界面。
- npm、项目级 `web/node_modules` 和 `package-lock.json`。
- SQLite 用户、会话、登录限速和迁移元数据。
- s6-overlay PID 1 和服务监督。
- Nginx stable Debian 运行时。
- 单管理员首次引导、登录、当前会话和登出。
- UI、Agent、Nginx 的组件健康状态。
- Nginx 运行状态、构建信息、进程信息和最近启动校验。
- 基于 `nginx -T` 的生效配置只读浏览。
- liveness、readiness 和 Docker healthcheck。
- 本地真实 Nginx 集成测试与 Linux Docker 验收。

### 3.2 不包含

- 配置创建、编辑、删除、分组、diff、备份、发布或恢复。
- 手动 start、stop、reload 或 restart API 和 UI 控件。
- upstream、server 或 location 的结构化管理。
- location 路径匹配测试；`nginx -t` 和 `nginx -T` 都不能冒充路径匹配测试。
- Let's Encrypt、ACME、证书签发或续期。
- 未生效配置文件、任意目录或任意宿主机文件浏览。
- 任意 Shell、任意可执行文件、任意命令参数或透传路径。
- UI 内管理员初始化向导、注册、找回密码或密码重置。
- 多用户、角色权限、集群、Kubernetes、Nginx Plus 或 Docker Socket。
- UI 与 Nginx 分离容器的官方部署方式。
- 管理界面自身的 TLS 终止；v0.1.0 官方示例只映射宿主机回环地址。
- 原生 Linux 安装包；本地 Nginx 只用于开发测试。

## 4. 已确认的关键决策

| 主题 | 决策 |

| 官方部署 | 单个一体化 Docker 镜像 |

## 5. 容器与进程架构

```text
s6-overlay / PID 1
├── nginx-uix
│   ├── 非 root 用户 nginx-uix
│   ├── HTTP :9000
│   ├── REST API + 嵌入式 SPA
│   └── SQLite /var/lib/nginx-uix/nginx-uix.db
├── nginx-uix-agent
│   ├── root
│   ├── Unix Socket /run/nginx-uix/agent.sock
│   └── 固定的 status、build-info、startup-validation、effective-config 操作
└── nginx
    ├── root master
    ├── 非特权 worker
    └── 前台运行，监听 80/443
```

### 5.1 s6 职责

s6-overlay 负责：

- 作为 PID 1 转发停止信号并回收孤儿进程。
- 在 long-running 服务启动前执行目录、用户、权限和配置卷初始化。
- 分别监督 UI、Agent 和 Nginx，不使用一个后台 Shell 同时托管三个进程。
- UI 崩溃后单独恢复 UI，不主动停止健康的 Nginx。
- Nginx 异常退出后使用 s6 death tally 和 `s6-permafailon` 执行有上限的自动恢复策略。
- 收到容器停止信号后，先停止接收管理请求，再终止 Agent 和 Nginx，并在总停止期限内等待子进程退出。

UI 和 Agent 不以“必须先有健康 Nginx”为启动前提。Nginx 配置无效时，UI 与 Agent 仍应可用，以便展示诊断信息。

### 5.2 权限边界

- PID 1 和 Nginx master 以容器内 root 身份运行，这是绑定 80/443、切换 worker 用户和执行初始化所需的最小容器内权限。
- UI 使用固定的非 root UID/GID，只有数据目录和 Agent Socket 组权限。
- Agent 以 root 运行，但不监听 TCP，不接受 Shell 文本、可执行文件路径、配置路径或命令参数。
- Agent Socket 所属为 `root:nginx-uix-agent`，权限为 `0660`；只有 UI 用户加入该专用组。
- Agent 在 Linux 上校验 Unix Socket 对端凭据，拒绝非预期 UI UID。
- Nginx worker 不加入 Agent Socket 组。
- 容器不要求 `--privileged`、Docker Socket 或额外 Linux capability。

### 5.3 故障隔离

- UI 失败：Nginx 和 Agent 继续运行；s6 恢复 UI；readiness 在 UI 恢复前失败。
- Agent 失败：UI 继续提供登录与页面外壳，Dashboard 显示 Agent 不可用和 Nginx 状态未知。
- Nginx 配置无效：启动脚本返回专用永久失败状态，不启动 Nginx；UI/Agent 可用；readiness 返回 503。
- Nginx 运行后崩溃：s6 保证两次快速拉起之间至少间隔 1 秒；5 分钟滚动窗口内死亡 5 次时，`s6-permafailon` 让 `finish` 以 125 退出并停止继续拉起，直到容器重启。
- SQLite 或 UI 数据目录失败：UI 不绑定 9000，日志给出脱敏原因；Nginx 生命周期保持独立；readiness 返回 503。

“自动恢复耗尽”不会被报告为健康，也不会无限快速重启。能够稳定运行超过 5 分钟的 Nginx 不受旧死亡窗口影响；进入永久失败后，v0.1.0 没有远程按钮用于清除 death tally，管理员修复外部原因后重启容器。

## 6. 构建和镜像设计

### 6.1 多阶段构建

镜像采用四个逻辑阶段：

1. 前端构建阶段使用 Node 官方 Debian 镜像，在 `web/` 中执行 `npm ci` 和 `npm run build`。
2. Go 构建阶段使用 Go 官方 Debian 镜像，编译静态的 UI 与 Agent 二进制；前端产物通过 `go:embed` 进入 UI 二进制。
3. 浏览器测试使用独立 Playwright 镜像，不把浏览器带入发布镜像。
4. 最终阶段以 Nginx stable Debian 镜像为基础，只加入 s6-overlay、两个 Go 二进制、服务定义和最小默认配置。

最终镜像不得包含 Go/Node 编译器、`node_modules`、npm 缓存、源码、浏览器、测试 fixture 或测试密钥。

### 6.2 初始工具链和镜像基线

以下是 2026-07-14 确认的初始实现基线：

| 用途 | 固定版本标签 | 发布镜像中保留 |
| --- | --- | --- |
| Go 构建 | `golang:1.26.4-trixie` | 否 |
| 前端构建 | `node:24.17.0-trixie-slim` | 否 |
| Nginx 运行时 | `nginx:1.30.3-trixie` | 是 |
| 浏览器测试 | `mcr.microsoft.com/playwright:v1.61.0-noble` | 否 |
| 进程监督 | s6-overlay `v3.2.3.0` 架构归档 | 是 |

实现 Dockerfile 时必须把基础镜像固定到多架构 manifest digest，并校验 s6-overlay 架构归档的 SHA-256。不得使用 `latest`、`stable`、`lts` 等浮动标签代替表中的精确版本。升级任何基线都作为独立依赖更新，重新运行 amd64/arm64 构建和启动测试。

SQLite 驱动选用 `modernc.org/sqlite`，初始固定版本为 `v1.53.0`。它通过 `database/sql` 提供 CGo-free SQLite，采用 BSD-3-Clause 许可证，并明确支持本项目需要的 darwin/linux amd64/arm64。`go.mod` 必须同时使用该版本上游 `go.mod` 对应的 `modernc.org/libc` 版本，避免上游已记录的不兼容组合。选择它是为了维持纯 Go、多架构静态构建；若未来替换驱动，只能修改 Store 适配层并重新执行迁移、并发、race 和多架构测试。

Node 镜像内置的 npm 版本必须在创建 `package-lock.json` 前记录到 `web/package.json` 的 `packageManager` 字段，并在本地文档、CI 和构建镜像中保持一致。Playwright npm 依赖必须与测试镜像的 `v1.61.0` 完全一致。

### 6.3 架构支持

- 正式构建目标为 `linux/amd64`、`linux/arm64`。
- Docker 构建使用 `TARGETARCH` 选择 s6-overlay 的 `x86_64` 或 `aarch64` 归档。
- amd64 至少执行完整 Docker smoke test。
- arm64 至少完成镜像构建和启动检查；具备原生 arm64 runner 时执行同一套完整 smoke test。

## 7. 端口、目录和配置

### 7.1 端口与官方暴露方式

容器内固定提供：

- `80/tcp`：Nginx HTTP。
- `443/tcp`：Nginx HTTPS。
- `9000/tcp`：Nginx UIX 管理界面。

官方 v0.1.0 示例只把管理端映射到宿主机回环地址：

```text
127.0.0.1:9000:9000
```

用户通过服务器本地浏览器、SSH 隧道或自己维护的 HTTPS 反向代理访问。v0.1.0 不自动生成管理端证书，也不默认把 9000 暴露到所有宿主机网卡。

### 7.2 持久化和运行时目录

| 路径 | 类型 | 用途 |
| --- | --- | --- |
| `/etc/nginx` | 持久化 | Nginx 配置真源 |
| `/var/lib/nginx-uix` | 持久化 | SQLite 和未来版本的持久化元数据 |
| `/run/nginx-uix` | 临时 | Agent Socket、启动校验和监督状态 |

数据目录由 root 初始化为 UI 专用所有者，目录权限不得高于 `0700`，SQLite 文件权限不得高于 `0600`。运行时目录在每次容器启动时重建，不进入持久化卷。

### 7.3 Nginx 配置卷初始化

初始化逻辑按以下顺序执行：

1. 枚举 `/etc/nginx` 的全部直接条目，包括隐藏文件。
2. 完全没有条目时，复制镜像内置的最小配置和静态欢迎页。
3. 存在任何条目时，不复制、不合并、不修复、不改权限、不重命名任何用户内容。
4. 明确使用 `/etc/nginx/nginx.conf` 作为容器内 Nginx 入口。
5. 入口缺失、不可读或配置无效时，记录启动校验失败并保持 Nginx 停止；UI/Agent 继续启动。

最小默认配置必须前台运行、使用 `/run` 下的 PID、把访问日志和错误日志输出到标准输出/错误，并包含一个可验证的 HTTP 监听。用户挂载的非空配置不受这些默认值覆盖。

### 7.4 应用环境变量

| 变量 | 规则 |
| --- | --- |
| `NGINX_UIX_LISTEN_ADDR` | 可选，默认 `0.0.0.0:9000` |
| `NGINX_UIX_PUBLIC_URL` | 可选；配置为可信 `https://` URL 时启用 Secure 会话 Cookie |
| `NGINX_UIX_ADMIN_USERNAME` | 用户表为空时必填；已有管理员时忽略 |
| `NGINX_UIX_ADMIN_PASSWORD_FILE` | 用户表为空时首选密码来源 |
| `NGINX_UIX_ADMIN_PASSWORD` | 仅作为开发和兼容回退；密码文件存在时忽略 |

环境变量不会把任意 Nginx 路径、命令或 Agent 参数暴露给用户。Nginx 二进制和入口配置在镜像中固定。

## 8. 启动与管理员引导

### 8.1 启动顺序

1. s6 初始化用户、组、持久化目录和运行时目录。
2. 按空目录规则初始化 `/etc/nginx`。
3. UI 打开 SQLite，检查目录/文件权限并执行单调迁移。
4. 用户表为空时执行管理员引导。
5. Agent 创建 Unix Socket 并开始提供只读操作。
6. Nginx 服务先运行固定的 `nginx -t -c /etc/nginx/nginx.conf`，原子写入启动校验结果，再决定是否启动 master。
7. UI 在自身数据库和认证初始化成功后绑定 9000；它不等待 Nginx 健康。

### 8.2 首次管理员规则

- 只有用户表为空时才读取引导变量。
- 用户名和至少一种密码来源必须存在；缺失时 UI fail closed，不开放管理端口。
- `NGINX_UIX_ADMIN_PASSWORD_FILE` 优先于明文环境变量。
- 密码文件最多读取 4 KiB，只移除一个末尾换行，拒绝空值和 NUL 字节。
- 用户名规范化后必须唯一，只允许 3–64 个可打印 ASCII 字符。
- 初始密码必须为 12–128 个 Unicode 字符。
- 密码使用 Argon2id 和每个用户独立随机 salt；最低参数为 19 MiB 内存、2 次迭代、并行度 1。
- 用户创建和迁移在数据库事务中完成；任一步失败都不得留下半初始化用户。
- 已存在管理员时完全忽略引导用户名和密码，防止容器环境变化静默重置凭据。

v0.1.0 不提供注册、初始化页面、密码修改、密码找回或管理员重置。忘记密码的恢复流程必须在后续版本单独设计，不能通过重新设置环境变量绕过。

### 8.3 SQLite 最小数据模型

v0.1.0 只建立以下持久化概念：

- `schema_migrations`：已应用迁移版本和校验信息。
- `users`：规范化用户名、密码哈希、创建时间和禁用标记。
- `sessions`：会话 token 摘要、CSRF token 摘要、创建时间、最近活动和过期时间。
- `login_throttles`：用户名与来源地址组合的失败窗口和封禁截止时间。

数据库不保存 Nginx 配置正文、`nginx -T` 输出、进程快照或密码明文。迁移只向前执行，已发布迁移不可原地修改。

## 9. 认证、会话和 Web 安全

### 9.1 登录流程

1. 浏览器向 `POST /api/v1/auth/session` 提交 JSON 用户名和密码。
2. API 校验同源 `Origin`、内容类型、请求大小和登录限速。
3. 不论用户名不存在、密码错误还是账户禁用，外部都返回同一条通用认证失败消息。
4. 验证成功后生成 32 字节密码学随机 token，只把 SHA-256 摘要写入 SQLite。
5. 原始 token 只通过会话 Cookie 返回；CSRF token 通过 `no-store` JSON 响应返回并仅保存在前端内存。
6. 登录成功后清理当前“用户名 + 来源地址”组合的失败计数。

登录限速以规范化用户名和来源地址组合为键：5 分钟内允许 5 次失败，第 5 次后封禁 15 分钟并返回 429 与 `Retry-After`。限速状态存入 SQLite，容器内 UI 重启不会清空封禁。v0.1.0 不信任转发来源地址 Header；未直接访问 UI 时，限速来源就是与 UI 建立连接的反向代理地址。

### 9.2 会话规则

- 会话采用 8 小时空闲超时和 24 小时绝对超时。
- 最近活动时间最多每 5 分钟落库一次，避免每个轮询请求都写 SQLite。
- Cookie 名固定为 `nginx_uix_session`，设置 `HttpOnly`、`SameSite=Strict`、`Path=/`，不设置持久化 `Expires` 或 `Max-Age`。
- 仅当 `NGINX_UIX_PUBLIC_URL` 是经过解析的 `https://` URL 时设置 `Secure`。
- v0.1.0 不信任任意 `X-Forwarded-Proto` 来决定 Cookie 安全属性。
- `GET /api/v1/auth/session` 可恢复当前用户信息和 CSRF token；响应禁止缓存。
- `DELETE /api/v1/auth/session` 删除服务端会话并清除 Cookie。
- 会话 token、CSRF token、密码和请求 Body 不进入日志、API 错误、localStorage 或 sessionStorage。

### 9.3 CSRF 与请求边界

- 登录请求没有既有 CSRF token，但必须通过同源 `Origin` 检查。配置 `NGINX_UIX_PUBLIC_URL` 时以该 URL 为可信源，否则要求 `Origin` 与本次请求的 scheme、Host 一致；缺失或不匹配都拒绝。
- 所有已认证的非安全方法同时要求会话 Cookie、同源检查和 `X-CSRF-Token`。
- API 只接受声明的 JSON 字段，拒绝未知字段、超限 Body 和错误内容类型。
- 每个请求生成或验证受限格式的 request ID，并在响应和结构化日志中关联。
- 认证相关、运行状态和配置响应都设置 `Cache-Control: no-store`。

## 10. Agent 协议与命令边界

### 10.1 传输

UI 与 Agent 使用 Unix Socket 上的 HTTP/1.1 + JSON。Socket 路径固定为 `/run/nginx-uix/agent.sock`，不提供 TCP 监听和远程配置。

内部 Agent API 固定为：

| 方法与路径 | 作用 |
| --- | --- |
| `GET /v1/health` | Agent 自身可用性 |
| `GET /v1/status` | Nginx master/worker 运行状态 |
| `GET /v1/build-info` | Nginx 版本和编译参数 |
| `GET /v1/startup-validation` | 最近启动校验和自动恢复状态 |
| `GET /v1/effective-config` | 执行固定 `nginx -T` 并返回实际加载配置 |

Agent 不接受请求 Body、查询参数、文件路径、命令参数或可执行文件选择。未知路径和方法一律拒绝。

### 10.2 固定命令执行

Agent 只允许通过 `exec.CommandContext` 调用镜像内固定 Nginx 二进制：

- 构建信息：`nginx -V`。
- 生效配置：`nginx -T -c /etc/nginx/nginx.conf`。

启动监督流程额外允许固定的 `nginx -t -c /etc/nginx/nginx.conf`。任何调用都禁止 `sh -c`、字符串拼接和用户参数透传。

命令边界固定为：

- `nginx -V` 超时 3 秒，成功结果在 Agent 进程生命周期内缓存。
- `nginx -T` 超时 10 秒，stdout 与 stderr 总量上限 16 MiB。
- 启动 `nginx -t` 超时 10 秒，诊断输出上限 256 KiB。
- 超时后必须取消并回收子进程；输出超限时立即停止读取、终止命令并返回稳定错误。
- 同时到达的生效配置请求共享同一个进行中的 `nginx -T`，不并发启动多个配置转储进程；完成后不在服务端持久缓存正文。

### 10.3 Agent 响应安全

- 只返回类型化 DTO，不把原始 `exec.Cmd`、环境变量或内部堆栈暴露给 UI。
- `nginx -T` 的配置正文只返回给已认证的管理员 API，不写日志或 SQLite。
- stderr 诊断在返回浏览器前限制长度并去除不可打印控制字符。
- Agent 错误在 UI API 边界映射为稳定错误码。
- Unix Socket 权限和对端凭据是双重本地授权；它们不替代 Web 层认证。

## 11. Nginx 状态模型

### 11.1 信息来源

Agent 使用以下来源交叉验证：

1. `nginx -V` 报告的编译期 PID 路径中的 PID 文件候选。
2. s6 监督的 Nginx 子进程 PID 候选。
3. `/proc/<pid>/exe`、`cmdline`、`stat` 和父子关系。
4. `nginx -V` 的固定构建信息。
5. 启动监督流程写入 `/run/nginx-uix` 的原子状态文件。

PID 文件或监督器 PID 只提供候选，不能单独证明 Nginx 正在运行。挂载配置显式覆盖 PID 路径时，编译期 PID 文件候选可以不存在，s6 候选仍可用于发现 master。Agent 必须确认进程可执行文件和命令行符合镜像内 Nginx，并拒绝复用后的陈旧 PID。

### 11.2 状态定义

| 状态 | 判定 |
| --- | --- |
| `running` | master 经 `/proc` 验证，且至少存在一个属于该 master 的 worker |
| `degraded` | master 经验证，但 worker 为零、部分进程信息不可读或最近自动恢复尚未稳定 |
| `stopped` | 完成全部受限检查后确认不存在有效 master |
| `unknown` | Agent 超时、权限不足、来源互相矛盾或无法完成可靠判定 |

超时和读取失败不得被映射为 `stopped`。Dashboard 必须区分“确认停止”和“无法判断”。

### 11.3 状态字段

状态 DTO 至少包含：

- 采样时间。
- `running`、`degraded`、`stopped` 或 `unknown`。
- master PID 和启动时间；不存在或未知时为 `null`。
- 按 PID 升序排列的 worker PID、进程角色和启动时间。
- Nginx 版本。
- configure arguments 原始数组。
- 最近启动校验的时间、结果、退出码和脱敏诊断。
- s6 death tally 当前窗口内的自动恢复次数、最近一次结果和是否已进入永久失败。

构建信息在 Agent 生命周期内缓存；进程状态每次请求都重新读取。Dashboard 默认每 5 秒轮询，不使用 SSE，因为 v0.1.0 没有长任务。

## 12. 生效配置设计

### 12.1 数据来源

配置页只调用 `nginx -T -c /etc/nginx/nginx.conf`。它不执行目录遍历，不接收文件路径，也不读取用户点击路径对应的文件。

成功输出按 Nginx 的 `# configuration file <path>:` 标记拆分。每次标记出现都形成一个按输出顺序编号的条目，因此同一文件被多次加载时保留多次出现，而不是错误去重。入口前的非配置诊断不作为文件正文。

返回结构至少包含：

- 本次生成时间。
- Nginx 版本。
- 入口配置路径。
- 文件出现次数。
- 每个条目的稳定本次响应 ID、加载序号、Nginx 报告的路径和只读正文。

文件顺序严格等于本次 `nginx -T` 输出顺序。v0.1.0 不推断一个无法由输出可靠证明的 include 图，也不显示未被本次命令加载的文件。

### 12.2 错误与旧数据显示

- `nginx -T` 非零退出时返回 `NGINX_CONFIG_INVALID`，不把不完整输出包装为成功配置。
- 超时返回 `NGINX_COMMAND_TIMEOUT`。
- 超过 16 MiB 返回 `NGINX_OUTPUT_TOO_LARGE`。
- Agent 不可用返回 `AGENT_UNAVAILABLE`。
- Nginx master 停止但配置有效时，`nginx -T` 仍可成功并展示配置；页面同时保留运行状态提示。
- 前端刷新失败时可以在内存中保留上一份成功结果，但必须显著标记为“旧数据”和上次成功时间；页面刷新后不持久保存旧正文。

所有配置响应设置 `Cache-Control: no-store`，不进入 Service Worker、浏览器持久缓存或 SQLite。

## 13. 对外 REST API

所有业务 API 使用 `/api/v1`，JSON 字段使用 `snake_case`，时间使用带时区的 RFC 3339。

| 方法与路径 | 认证 | 作用 |
| --- | --- | --- |
| `POST /api/v1/auth/session` | 否 | 登录并创建单一浏览器会话 |
| `GET /api/v1/auth/session` | 是 | 获取当前管理员和 CSRF token |
| `DELETE /api/v1/auth/session` | 是 + CSRF | 登出并撤销当前会话 |
| `GET /api/v1/system/status` | 是 | 获取 UI、Agent、Nginx 聚合状态 |
| `GET /api/v1/nginx/effective-config` | 是 | 获取本次 `nginx -T` 生效配置 |

`GET /api/v1/system/status` 即使 Agent 或 Nginx 异常也返回可渲染的聚合状态：UI 状态为健康，Agent 状态标记为不可用，Nginx 状态为 `unknown`，并在 `issues` 中携带稳定错误码。这样 Dashboard 不会因下游故障只显示一个通用错误页。

### 13.1 错误结构

请求整体失败时统一返回：

```json
{
  "error": {
    "code": "NGINX_CONFIG_INVALID",
    "message": "Nginx 配置无法通过检查。",
    "request_id": "01J...",
    "details": {}
  }
}
```

v0.1.0 稳定错误码至少包括：

- `AUTH_INVALID_CREDENTIALS`
- `AUTH_RATE_LIMITED`
- `AUTH_SESSION_EXPIRED`
- `CSRF_INVALID`
- `AGENT_UNAVAILABLE`
- `NGINX_NOT_RUNNING`
- `NGINX_CONFIG_INVALID`
- `NGINX_COMMAND_TIMEOUT`
- `NGINX_OUTPUT_TOO_LARGE`
- `INTERNAL_ERROR`

错误消息面向管理员且脱敏。`details` 只允许每个错误码预先声明的非敏感字段，不接受底层错误对象直接序列化。内部路径、命令环境、堆栈、Cookie、密码和配置正文不得出现在错误对象中。

## 14. 健康检查

### 14.1 HTTP 健康端点

- `GET /health/live`：只证明 UI HTTP 进程能够响应；不检查数据库、Agent 或 Nginx，不返回内部细节。
- `GET /health/ready`：检查 SQLite、Agent Socket 和真实 Nginx 状态；任何一项失败都返回 503，成功返回 200；响应只包含通用状态。

两个端点不要求登录，但不得泄露版本、PID、路径、错误诊断或组件明细。

### 14.2 Docker healthcheck

Docker healthcheck 使用同一个 Go 二进制的受限 healthcheck 模式请求容器回环地址，不依赖发布镜像中的 curl 或 wget。初始参数为：

- interval：10 秒。
- timeout：3 秒。
- start period：20 秒。
- retries：3。

Docker 使用 readiness 而不是 liveness，因此 Nginx 停止或 Agent 故障时容器显示 unhealthy。即使如此，只要 UI 自身可用，宿主机映射的 9000 仍可打开诊断页面。

## 17. 日志与可观测性

- UI、Agent 和启动监督流程输出结构化日志到 stdout/stderr。
- 稳定字段至少包括 `component`、`action`、`result`、`duration_ms`、`request_id` 或启动事件 ID。
- 领域错误只在具有处理责任的边界记录一次，避免逐层重复。
- 登录失败日志不区分“用户不存在”和“密码错误”，也不记录密码或请求 Body。
- `nginx -T` 配置正文永不写日志；只记录执行结果、耗时、退出分类和输出字节数。
- Cookie、Authorization、CSRF token、密码、Secret 文件内容和 SQLite 会话摘要不得记录。
- 用户可见诊断与内部日志分离；API 只返回稳定错误码和脱敏说明。

## 18. 错误和恢复策略

| 故障 | 用户可见行为 | 运行时行为 |
| --- | --- | --- |
| 首次管理员变量缺失 | 9000 不监听；日志提示缺少引导输入 | UI 反复受控启动失败；Nginx 独立处理 |
| SQLite 迁移或权限失败 | 9000 不监听 | 不跳过迁移，不新建不完整数据库 |
| `/etc/nginx` 非空但入口缺失 | Dashboard 启动校验失败 | 不修改目录；Nginx 保持停止 |
| `nginx -t` 失败 | 显示配置无效和脱敏诊断 | 不启动 Nginx；readiness 503 |
| Agent Socket 不可用 | Dashboard 显示 Agent 不可用、Nginx 未知 | UI 保持可登录；readiness 503 |
| 状态读取超时 | 显示 `unknown`，不是 `stopped` | 请求取消并回收资源 |
| `nginx -T` 超时或过大 | 配置页显示稳定错误，可保留内存旧数据 | 命令被终止；不写缓存或数据库 |
| Nginx 崩溃 | 显示当前死亡窗口和最终停止 | 5 分钟内死亡 5 次后进入永久失败 |
| UI 崩溃 | 短暂无法访问 | s6 恢复 UI，Nginx 不受影响 |
| 容器停止 | 页面连接终止 | 信号转发、优雅退出、回收全部子进程 |

任何无法可靠判定的状态都显示 `unknown` 或“需要人工检查”，不得猜测成功。

### 19.2 真实 Nginx 集成测试

集成测试使用临时 prefix、独立 PID、随机回环端口和仓库固定 fixture，不触碰开发者当前运行的 Nginx：

- 有效配置启动并产生可验证的 master/worker 状态。

- 命令取消、超时、输出过大和部分输出处理。
- 测试成功、失败和取消后的进程与临时文件清理。

macOS 本地 Nginx 可覆盖命令和配置解析集成测试，但 `/proc`、Linux Unix Socket 对端凭据、s6 和容器信号必须在 Linux Docker 中验收。

- 空库迁移和管理员事务。

- 过期会话清理和并发读取。

- 登录成功、通用失败、限速、后端不可用和会话过期。
- Dashboard 的 healthy、degraded、stopped、unknown、Agent unavailable 状态。
- 生效配置加载、文件切换、重复路径条目和严格只读行为。
- loading、empty、error 和 stale 状态。

- 不使用大型脆弱快照代替行为断言。

### 19.5 Docker smoke 与故障注入

- Debian 一体化镜像正常启动。
- 空 `/etc/nginx` 初始化默认配置。
- 非空 `/etc/nginx` 字节级保持不变。
- Secret 文件引导管理员，明文回退只在未提供文件时生效。

- 数据卷重挂载后管理员和会话规则保持。
- amd64 完整运行；arm64 构建和启动，具备 runner 时执行完整运行。

```text
real Nginx integration + Docker fault tests + multi-arch
```

v0.1.0 只需要创建与上述能力直接相关的 `cmd/nginx-uix`、`cmd/nginx-uix-agent`、`internal/app`、`internal/runtime`、`internal/store`、`internal/httpapi`、`web`、`deploy/docker` 和测试 fixture。`upstream`、`location`、`routelab`、`certificate` 等后续包在对应版本开始前不创建空壳。

## 23. 版本之后的边界

v0.2.0 才引入工作副本、diff、完整校验、备份、原子发布、手动 reload/restart 和回滚。v0.3.0 才引入 upstream 与 location 结构化管理。v0.4.0 才以隔离 Nginx 实例实现真实路径匹配测试。v0.5.0 才处理 Let's Encrypt。

这些后续能力必须复用 v0.1.0 建立的认证、Agent 类型化边界、真实状态模型和一体化容器，但不得通过扩展 v0.1.0 范围提前实现。
