## 1. 文档目的

本文把 `PLAN.md` 中 v1.0.0 的六项交付物细化为可验证的兼容性冻结、发布阻断项清零、安装/升级/恢复证据汇总、正式多架构镜像发布、手册发布和后续安全响应流程。

v1.0.0 不新增产品模块、业务页面、REST 资源、Agent 操作、数据库表或 Nginx 配置能力。v0.7.0 已经完成完整产品在最终一体化镜像中的原生 arm64 运行验证、amd64/arm64 OCI 与 SBOM 静态验证；v1.0.0 只允许兼容性修复、安全修复、数据完整性修复、回滚修复和正式发布工程。

开始本版本时，本地 `main` 的 v0.7.0 基线为 `e46d34d`。远端仓库可访问但为空；本规格建立和冻结守护阶段不 push、不创建 tag、不发布镜像。

## 2. 用户结果与完成标准

稳定版完成后，管理员和维护者必须得到以下结果：

1. `/api/v1`、持久化配置格式和已发布 migration 具有明确、可执行的兼容性承诺。
2. 没有已知的阻断发布安全问题、数据损坏问题或失败后无法恢复的发布/回滚路径。
3. 全新安装、v0.7.0 直接升级、同版本重建和双持久根冷备恢复都有当前 1.0.0 候选的实际证据。
4. linux/amd64 与 linux/arm64 使用同一源码身份生成正式一体化镜像、SBOM、漏洞扫描结果和不可变 digest。
5. 用户、管理员和故障恢复流程不要求进入容器执行日常管理 Shell。
6. 补丁版本兼容性、安全报告、修复、披露和支持窗口具有公开流程。

## 3. 明确范围

### 3.1 包含

- 冻结 OpenAPI v1 当前路径、方法、参数、请求/响应 schema、错误码、SSE 事件和安全要求。
- 冻结工作区 manifest、control state、mutation journal 的 v1 持久化编码和解释规则。
- 冻结 SQLite `0001`–`0007` migration 的文件名、顺序和内容校验和。
- 仅为安全、数据完整性、回滚可靠性或发布阻断问题实施最小修复。
- 在最终候选上复验 Go、前端、浏览器、真实 Nginx、本地 ACME、Docker、升级、恢复、故障和供应链门禁。
- 在真实 linux/amd64 runner 补齐 v0.7.0 明确未运行的原生最小启动、持久化升级和恢复证据。
- 发布用户手册、管理员手册、故障恢复手册、`SECURITY.md` 和补丁支持策略。
- 将源码推送到已配置的 GitHub 远端，并在全部门禁通过后发布签名或 digest 可验证的版本 tag 与多架构镜像。

### 3.2 不包含

- 新增或重新设计任何 v1.0 产品功能。
- 新增 REST 资源、Agent 命令、数据库业务表或配置持久化格式。
- 把内部 Go 类型、Nginx AST 节点或 SQLite repository 类型承诺为仓库外公共 API。
- Cloudflare 之外的 DNS 服务商、插件系统、集群、Kubernetes、WAF、Nginx Plus 或 `stream` 路径实验。
- 修改历史 migration、从 SQLite 反向生成 Nginx 配置，或用破坏性数据重建掩盖升级失败。
- 在缺少真实 runner、扫描数据库、registry digest 或恢复证据时用模拟结果替代。

## 4. v1 兼容性冻结

### 4.1 REST API v1

`api/v1/openapi.yaml` 是公开 REST 契约真源。冻结范围包括：

- `/api/v1` 下的 path、HTTP method 和 `operationId`；
- path/query/header 参数及其 required、类型、格式、约束和重复值语义；
- request body、response status、media type、schema、枚举和稳定错误码；
- Session Cookie、Origin、CSRF、`If-Match`、SSE reconnect 和 `Cache-Control` 要求；
- JSON `snake_case` 字段、RFC 3339 时间和显式时长单位。

v1 中禁止删除 path/operation/status/字段、把可选字段改为必填、收窄已接受输入、改变字段含义、重用错误码表达不同语义或弱化安全要求。新增可选响应字段或新增独立资源也必须先证明旧客户端可继续工作、更新 OpenAPI/Go/TypeScript/浏览器契约并经过显式兼容性评审；稳定版发布前默认不接受此类扩展。

`TestOpenAPIV1FrozenContractFingerprint` 对规范化后的完整 OpenAPI 文档计算结构指纹。它只把 `info.version` 归一为 API major，因此应用补丁版本本身不会改变 v1 指纹；其他任何契约或文案变化都会要求显式审阅并更新基线。现有 `TestOpenAPIContract` 继续验证 OpenAPI 与真实 handler 的方法、路由、DTO、错误和安全边界一致。

### 4.2 配置模型

v1 对外承诺的是行为与持久数据可读性，不承诺内部 Go 类型布局：

- `/etc/nginx` 始终是配置真源；SQLite 不保存可反向覆盖文件的配置副本。
- `ManifestSchemaVersion=1`、policy version `1`、`ControlSchemaVersion=1` 和 `JournalSchemaVersion=1` 的既有记录必须保持可读且保持原语义。
- manifest 的 canonical ordering、entry/dependency 分类、mode/size/content digest 和安全 symlink 表达不能被静默重新解释。
- control state 与 journal 的 strict JSON、UTC 时间、opaque ID、revision、phase 和 digest 含义不能被静默改变。
- Nginx AST 是内部实现；其兼容性通过 lossless parse/render/reparse、golden fixture 和真实隔离 Nginx 回归保证，不形成仓库外 Go API。

`TestV1DurableConfigModelFingerprint` 使用实际生产编码函数固化 manifest、control state 和 journal 的代表性持久化字节。未来确需新格式时必须增加 schema/policy version、同时读取旧格式、提供失败恢复与升级测试，并保留旧记录 fixture；不得直接改写 v1 解释后更新指纹。

### 4.3 数据库 migration

v1.0.0 的已发布 migration 集合精确为 `0001`–`0007`。规则如下：

1. 已发布 SQL 文件名和内容永久不可修改、重排、删除或复用版本号。
2. 没有 schema 变化时不创建空 migration。
3. 未来 schema 变化只能新增下一连续编号；v1.0.0 之后首个编号只能是 `0008_*`。
4. 每个新 migration 必须事务化、单调、失败回滚、重复打开幂等，并从当前最旧受支持数据 fixture 验证数据和外键保留。
5. 应用启动继续校验已应用 checksum；不允许手工改写 `schema_migrations` 绕过失败。
6. 文件系统配置与 SQLite 更新继续按明确恢复顺序处理，不能假设二者共享事务。

`TestV1PublishedMigrationsAreImmutable` 固化 `0001`–`0007` 的精确文件集合和 SHA-256。既有 migration checksum、升级 fixture、`integrity_check`、`foreign_key_check`、失败回滚和灾备测试继续作为行为证据。

## 5. 发布阻断项

以下任一条件存在时不得创建正式 tag 或发布镜像：

- 未处置的 Critical/High 漏洞，或没有明确到期日和不可达证据的安全例外；
- 认证、Session、CSRF、Origin、限流、Agent Socket/peer credential、路径约束或秘密脱敏回归；
- 会导致生产 Nginx 配置、SQLite、备份、证书或任务状态损坏的已知问题；
- validate、发布、reload、健康确认、自动回滚、人工恢复或 restart 存在已知不可恢复失败；
- v1 OpenAPI、配置格式或历史 migration 冻结门禁失败；
- linux/amd64 或 linux/arm64 正式产物未构建，或对应证据被模拟运行冒充；
- v0.7.0 已知的真实 amd64 runner 缺口尚未补齐；
- 全新安装、v0.7.0 升级、同卷重建或双根冷备恢复没有当前候选证据；
- SBOM、漏洞数据库、本地 image ID、正式 manifest digest、source fingerprint 或 build identity 缺失；
- 用户必须进入容器 Shell 才能完成正常管理或受支持恢复流程；
- 发布所需 GitHub/GHCR 权限、不可变 tag 策略或回滚目标未验证。

发现阻断项时先写失败测试或复现步骤，再实施最小修复。修复不得降低断言、跳过测试、吞掉错误、扩大超时或把 `needs_attention` 伪装为成功。

## 6. 稳定性与恢复验收

最终候选必须在同一 source fingerprint 和 exact platform image ID 上完成；发布后再以回读的 registry manifest digest 固化产物：

1. 全部 Go、前端、浏览器、真实 Nginx 和本地 ACME 回归。
2. 原生 linux/arm64 完整 Docker 矩阵复验。
3. 真实 linux/amd64 最小启动、登录、状态、优雅停止、v0.7.0 数据升级、同卷重建和双根冷备恢复；若提供完整 runner，执行与 arm64 同级矩阵。
4. 连续稳定运行期间反复检查 UI、Agent、Nginx、SQLite、调度器和持久任务 owner，无泄漏 goroutine、残留沙箱、失联任务或错误健康状态。
5. 重复执行工作区创建、候选校验、发布、reload、健康确认、备份和人工恢复；每轮校验生产摘要、master PID、SQLite integrity、备份索引和审计终态。
6. 注入只读卷、容量不足、端口冲突、Agent/UI/Nginx 崩溃、reload/restart 失败、超时和取消；无法安全判断时必须进入 `needs_attention`。

稳定运行时长和重复发布轮数在执行前写入验收记录，必须足以覆盖证书调度、任务恢复和资源回收观察窗口；不得在失败后缩短门槛。

- 用户手册：登录、Dashboard、配置工作区、结构化编辑、发布/恢复、Route Lab 和证书管理。
- 管理员手册：安装、持久卷、Secret、权限、升级、监控、备份、审计和证书运维。
- 故障恢复手册：UI/Agent/Nginx/SQLite/配置/证书故障、`needs_attention`、冷备恢复和回滚决策树。
- `SECURITY.md`：受支持版本、私密报告渠道、响应目标、披露流程和不会接受的公开秘密材料。
- v1.0.0 验收记录：环境、命令、exit code、runner 架构、local image ID、registry manifest digest、SBOM、扫描数据库时间、source/build identity、通过/失败/未运行边界。

文档命令使用明确占位符，不包含真实密码、Token、域名、私钥或 production ACME 操作。日常流程不得依赖容器内 Shell；仅灾难取证可以在停机、只读和明确目标边界下使用受控命令。

## 8. 版本与发布规则

- 正式候选前同步 `VERSION`、OpenAPI `info.version`、`web/package.json`、lockfile、Docker 默认版本和镜像标签为 `1.0.0`。
- 候选 tag 使用可识别的预发布版本；正式 tag 精确为 `v1.0.0`，不能移动或覆盖。
- 多架构 manifest 至少包含 `linux/amd64` 与 `linux/arm64`，两者来自同一 source fingerprint。
- 正式镜像必须同时记录版本 tag 与不可变 digest；文档优先展示 digest pin。
- `latest` 如需提供，只能在 `v1.0.0` 不可变 tag 和 digest 已验证后作为可移动便利别名，不能作为升级或回滚真源。
- 发布失败时不覆盖既有 tag；修复后使用新的预发布或补丁版本。
- push、tag、GitHub Release 和 registry 发布属于外部不可逆发布步骤，只在本规格全部门禁通过且用户明确确认发布时执行。

默认镜像 registry 可使用与源码仓库同属一个组织的 GHCR；正式名称、权限和包可见性必须在发布前通过只读检查确认，不从仓库 URL 静默推断为已授权发布目标。

## 9. 补丁版本与安全响应

- `1.0.x` 只接受兼容的安全、数据完整性、回滚、可靠性和文档修复，不增加产品范围。
- REST API 保持 v1 兼容；数据库只允许向前 migration；旧配置持久格式保持可读。
- 每个补丁从失败测试开始，重新运行受影响门禁、全仓质量门禁和正式镜像最小回归。
- 安全报告优先通过 GitHub 私密漏洞报告或 `SECURITY.md` 指定的私密渠道，不要求在公开 issue 中披露漏洞细节。
- Critical/High 修复需要明确影响范围、临时缓解、修复版本、升级/回滚步骤和披露时间；不得在修复可用前公开密钥、利用细节或用户数据。
- 受支持版本和响应目标以 `SECURITY.md` 为准；无法满足时必须公开更新状态，不静默失联。

## 10. 实施与验收顺序

1. 建立本规格，将 `PLAN.md` v1.0.0 状态改为“进行中”，不提前勾选未验证项目。
2. 固化 OpenAPI v1、配置持久化模型和 `0001`–`0007` migration 指纹，并先取得 RED、再取得 GREEN。
3. 同步应用版本为 `1.0.0`；创建任何新代码文件前重新读取 git author 与更新后的 `VERSION`。
4. 建立阻断问题清单，复验安全、数据完整性和所有发布/回滚失败路径。
5. 补齐真实 amd64 runner、连续稳定运行和重复发布/恢复测试。
6. 汇总安装、升级、重建和恢复证据，完成三类手册与安全响应文档。
7. 构建 exact release candidate，完成双架构 OCI、SBOM、漏洞和内容门禁。
8. 生成 v1.0.0 验收记录；只有全部交付物有证据后才勾选 `PLAN.md` 并改为“已完成”。
9. 取得用户明确发布确认后，依次 push 源码、创建不可变 tag、发布多架构镜像与 GitHub Release，并回读远端 digest/tag 验证结果。
