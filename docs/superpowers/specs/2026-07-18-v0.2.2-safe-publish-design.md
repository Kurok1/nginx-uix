## 1. 文档目的

本文把 `PLAN.md` 中 v0.2.2“安全发布闭环版”细化为可直接实施和验收的产品与技术设计。v0.2.2 只在 v0.2.1 已持久化的工作区之上增加候选配置校验、不可变备份、可恢复的多文件发布、reload、运行确认和自动回滚，不提前交付 v0.2.3 的人工恢复、restart、备份保留策略或完整历史中心。

本版本首次获得生产写入和 Nginx 控制权限，因此所有成功结论都必须来自持久化阶段证据。一次命令返回成功、一次 `nginx -t` 通过或客户端收到 2xx 都不足以单独证明发布成功。

## 2. 用户结果与完成标准

管理员能够在一个 `ready` 工作区中执行发布检查，阅读完整差异和候选校验证据，具名确认后启动发布任务，并持续看到以下阶段的真实结果：

```text
锁定工作区与摘要
  -> 重新核验生产和草稿
  -> 创建并验证不可变备份
  -> 再次校验完整候选配置
  -> 持久化发布意图
  -> 原子替换各生产文件
  -> 对生产路径执行 nginx -t
  -> reload
  -> 确认 master、worker 与固定回环 HTTP 健康
  -> 成功提交，或恢复备份并确认回滚
```

版本只有同时满足以下条件才完成：

1. 错误候选配置不会创建可用发布记录、修改生产文件或触发 reload。
2. 发布检查与最终发布都绑定精确的 `production_digest`、`draft_digest`、工作区修订和校验策略版本。
3. 生产摘要或草稿摘要发生变化时，发布在任何生产写入前失败。
4. 备份覆盖发布前完整生产树，完整性验证通过后才允许写生产文件。
5. 每个文件替换是同目录临时文件、文件 `fsync`、原子 rename 和父目录 `fsync`；事务阶段可以在崩溃后判定并恢复。
6. 发布后的真实生产路径再次通过完整 `nginx -t` 后才允许 reload。
7. reload 后确认 master PID 未变化、worker 已形成可用集合，并通过固定回环 HTTP 探针。
8. 可安全判定的失败自动回滚；无法证明已成功或已恢复时进入 `needs_attention`，绝不报告成功。
9. 浏览器断开不改变任务事实；任务、阶段、备份索引和结果在应用与 Agent 进程重启后仍可查询。
10. UI 在桌面、平板和手机上都能完成检查、确认和结果审阅，并满足 WCAG 2.2 AA。

## 3. 范围

### 3.1 包含

- 对完整候选树执行隔离、有界、无 Shell 的 `nginx -t`。
- 对安全可公开的 Nginx 诊断提取相对文件、行号、阶段和稳定原因码。
- 发布检查资源及其短期有效的摘要绑定证据。
- 发布前工作区状态、生产摘要、base 摘要、draft 摘要和工作区修订复核。
- root Agent 创建、验证和保护的完整生产备份。
- 新建、修改和删除受管文件的可恢复多文件发布协议。
- 发布后生产配置校验。
- 固定的 reload 操作，不接受浏览器提供的命令、参数、PID 或路径。
- master PID、worker 集合和固定回环 HTTP 健康确认。
- 可判定失败的自动回滚和回滚后重新校验、reload、健康确认。
- 发布任务、阶段事件、备份索引、工作区结果与审计的 SQLite 持久化。
- 发布任务状态查询和 SSE 事件流。
- 发布检查、具名确认、进度、成功、失败、已回滚和 `needs_attention` UI。
- v0.2.1 → v0.2.2 数据升级、进程重启、崩溃重放和原生故障注入验收。

### 3.2 不包含

- 人工选择备份恢复；属于 v0.2.3。
- 删除备份、保留策略、配额回收和手工导出；属于 v0.2.3。
- restart、停止或启动 Nginx；属于 v0.2.3。
- 修改生产文件权限、所有者或目录结构的通用文件管理器。
- 对敏感材料正文、私钥或证书的浏览、编辑或 diff。
- Nginx AST、结构化语义编辑、自动格式化或 include 自动修复。
- 在生产 Nginx 上执行路径匹配实验；属于 v0.4。
- 接受任意健康 URL、目标主机、Shell、可执行文件、Nginx 参数或绝对路径。
- 把“每个文件原子替换”包装成“整个任意 `/etc/nginx` 目录可单次 rename”。
- Docker 构建、容器运行、卷、容器升级、Docker 浏览器流程、镜像内容和多架构验证；全部统一移交 v0.7.0。

## 4. 不可违反的安全不变量

1. `/etc/nginx` 继续是配置真源；SQLite 只保存状态、索引、摘要和审计，不保存可反向覆盖生产的配置正文。
2. Web/API 进程不能直接读取或写入 `/etc/nginx`、备份正文或 Agent 发布暂存，也不能执行 Nginx 命令。
3. 只有 root Agent 可以创建完整候选、备份、生产临时文件并执行 validate/reload/rollback。
4. Agent 请求只含协议版本、request ID、不透明工作区/检查/发布 ID 和精确摘要；不接受根路径、目标路径、健康 URL、命令或透传参数。
5. 发布检查不授予发布权。最终发布必须重新读取工作区和生产事实，不能只信任旧检查结果。
6. `stale`、`preparing`、`published`、`needs_attention` 或有未完成工作区 journal 的工作区都不能开始发布。
7. 同一时刻最多有一个生产发布或自动回滚事务；候选检查可并行但具有全局上限。
8. 备份未完成、未同步或未通过完整性复核时，禁止任何生产写入。
9. 发布期间不 reload 半完成文件集合；只有全部目标文件已 durable 且生产 `nginx -t` 通过后才 reload。
10. 回滚以已验证备份为唯一自动恢复来源，不从 SQLite、工作区 base 或浏览器重建旧生产配置。
11. master PID 变化、进程状态不确定、备份损坏、摘要不唯一或回滚健康确认失败都进入 `needs_attention`。
12. API、日志、SSE 和审计不包含配置正文、完整 diff、敏感路径、绝对路径、命令行、Cookie、CSRF、凭据或原始 Nginx stderr。

## 5. 总体架构

```text
Browser
  │ session + Origin + CSRF + If-Match
  │ POST check / POST publish / GET task / GET SSE
  ▼
nginx-uix Web/API (non-root)
  ├── config release service
  │   ├── workspace lock + digest/revision checks
  │   ├── persistent task state + stage events
  │   └── startup reconciliation
  ├── store ── SQLite
  └── typed Agent client
          │ Unix Socket + peer credentials
          ▼
nginx-uix-agent (root)
  ├── candidate materializer + isolated validator
  ├── immutable backup writer + integrity verifier
  ├── durable release journal + production applier
  ├── fixed nginx validate/reload adapter
  └── status + loopback HTTP health verifier
          │
          ├── /etc/nginx
          └── /var/lib/nginx-uix/backups + releases
```

### 5.1 组件边界

| 单元 | 负责 | 不负责 |
| --- | --- | --- |
| `config` release service | 检查/发布授权、任务状态机、Agent 阶段编排、工作区最终状态、启动对账 | 直接写生产或解释原始 stderr |
| `runtime` candidate | 固定根候选物化、include 路径隔离、`nginx -t`、诊断脱敏 | SQLite、HTTP DTO、用户确认 |
| `runtime` release | 生产锁、备份、journal、文件替换、reload、健康确认、自动回滚 | 任意 restore/restart/retention |
| `store` | 检查、发布、阶段、备份索引、任务和审计元数据 | 候选/备份/生产正文 |
| `httpapi` | 认证、CSRF、ETag、DTO、SSE、稳定错误 | 直接调用文件系统或命令 |
| Vue workspace | 检查、确认、进度和结果投影 | 推断后台成功、自动重试变更 |

不创建通用 `task manager`、`utils` 或插件层。发布任务只服务当前配置发布领域；未来证书任务在其版本中通过明确接口复用必要的小原语。

## 6. 持久化布局与权限

```text
/var/lib/nginx-uix/
├── nginx-uix.db
├── workspaces/<workspace-id>/
├── releases/<release-id>/
│   └── control/
│       ├── state.json
│       └── events.ndjson
└── backups/<backup-id>/
    ├── tree/                 # 完整生产树，包含受保护材料
    └── control/
        ├── manifest.bin      # Agent 私有完整性 manifest
        └── complete.json
```

- `release-id`、`backup-id` 都是服务端生成的 128-bit lowercase hex，不复用工作区 ID。
- `releases` 与 `backups` 由 Agent 建立并验证根身份；备份目录和文件不高于 `0700`/`0600`，Web 不读取正文。
- 备份完成后切换为应用级不可变：文件只读、目录不可写，`complete.json` 最后原子写入并 `fsync` 全链路。任何后续写入请求都被 Agent 拒绝。
- 备份正文不会通过 Unix Socket 返回；Web 只得到 ID、创建时间、内部完整性状态、条目数和总字节数。
- v0.2.2 不删除已完成备份。容量不足在生产写入前失败；保留策略留到 v0.2.3。

## 7. 候选配置物化与隔离校验

### 7.1 完整候选树

候选不是只包含被编辑文件的稀疏目录。Agent 按以下顺序创建完整候选：

1. 用 descriptor-relative、no-follow 遍历读取当前固定生产根。
2. 复制目录、常规文件和经分类允许的内部 symlink 到 root-only 暂存；特殊文件、断裂/越界 symlink 或无法确定的条目 fail closed。
3. 从工作区 `control/manifest.bin` 读取受管路径集合，并重新验证 `draft` 的摘要、类型、模式、UTF-8、NUL 和上限。
4. 用 `draft` 的受管文件覆盖对应候选文件；base 中存在而 draft 删除的受管文件从候选删除；新文件使用固定安全模式。
5. 重新生成候选 manifest 和摘要，确认它精确绑定请求中的 draft 摘要。

候选暂存不使用 hardlink，避免验证或清理改变生产、base、draft 或备份。错误、取消和超时都清理暂存；清理失败只记录相对对象 ID，并阻止同一 ID 复用。

### 7.2 include 与固定命令

候选使用固定 Nginx 二进制和固定参数，不使用 `sh -c`。相对 include 在候选 prefix 下解析；词法扫描明确识别的、指向固定生产根内的绝对 include 会在仅用于校验的副本中等长或有界重写到候选根。原工作区和最终发布内容不被改写。

以下情况拒绝候选，而不是猜测：

- include 参数含变量且可能指向生产根内受管文件。
- include token 无法无歧义定位或超过词法上限。
- 绝对 include 越出允许根且无法证明为只读外部依赖。
- 候选与生产的固定 Nginx build/prefix 不一致。

命令总期限 60 秒，stdout+stderr 总计最多 1 MiB，只允许预定义退出码。诊断解析只公开：稳定 code、候选相对路径、1-based 行号和脱敏摘要。原始命令、绝对路径和完整 stderr 仅在受保护 Agent 日志中按内容规则进一步脱敏后记录。

### 7.3 发布检查证据

成功检查记录：

- `check_id`、`workspace_id`、工作区 revision。
- `production_digest`、`base_digest`、`draft_digest`、candidate digest。
- manifest/policy/validator schema version。
- Nginx build identity。
- 检查开始、结束和过期时间。
- 阶段结果与安全诊断列表。

检查默认 10 分钟过期。它用于用户审阅，不替代发布事务中的重新校验。

## 8. 备份模型

### 8.1 完整性范围

备份覆盖发布前固定生产根的完整受支持树，而不只覆盖 diff 文件。manifest 以版本化长度前缀编码包含：相对路径、entry 类型、mode、symlink 安全目标、常规文件字节数和 SHA-256。敏感文件摘要只存在 Agent 私有 manifest，不进入 SQLite、API、日志或审计。

备份采用双清单：复制前清单必须匹配期望生产摘要；复制后重新读取生产并计算清单。前后不一致时删除未完成备份并返回生产并发变化，绝不发布。

### 8.2 可用备份条件

只有同时满足以下条件才插入 `complete` 备份索引：

- 所有 entry 已复制且类型、大小、mode 和内容摘要一致。
- 所有文件和目录已 `fsync`。
- 私有 manifest 已原子写入并复读校验。
- `complete.json` 已最后写入并同步父目录。
- 生产二次清单仍等于发布期望摘要。

不完整目录不出现在普通备份列表中。启动对账会清理从未进入生产写阶段的不完整备份；若关联事务可能已写生产，则保留证据并进入恢复判定。

## 9. 多文件发布协议

任意已有 `/etc/nginx` 目录无法在不改变部署布局的前提下用一次 rename 整体切换。v0.2.2 的“原子发布”准确语义是：每个文件原子替换，事务全程持久化、可恢复，且运行中的 Nginx 在完整生产校验前不 reload。

### 9.1 目标集合

Agent 从已验证备份与候选 manifest 计算稳定排序的操作：

1. 创建所需同级临时文件。
2. 修改现有常规文件。
3. 创建新常规文件。
4. 删除 draft 已删除的受管常规文件。

目录 CRUD、symlink CRUD、特殊文件、敏感材料和不受管文件不进入目标集合。已有文件保持发布前 mode 与 owner；新受管文件使用 `0640` 和固定 root/nginx owner。任何目标路径或父目录在执行时身份变化都视为并发冲突。

### 9.2 Agent release journal

Agent journal 不含正文，至少包含：schema、release/backup/workspace ID、期望摘要、candidate 摘要、操作清单摘要、master PID 基线、当前阶段、已 durable 的操作序号、时间和安全结果码。

阶段单调推进：

```text
prepared
  -> files_applying
  -> files_applied
  -> production_validated
  -> reload_requested
  -> runtime_confirmed
  -> committed

任一可恢复失败
  -> rollback_applying
  -> rollback_files_restored
  -> rollback_validated
  -> rollback_reload_requested
  -> rolled_back

任一证据不唯一
  -> needs_attention
```

每次阶段或操作序号推进都先原子写 journal 并同步。生产替换使用同目录随机临时文件、`O_EXCL|O_NOFOLLOW`、正确 owner/mode、文件 `fsync`、rename 和父目录 `fsync`。删除先由 journal 和备份证明可恢复，再 unlink 并同步父目录。

### 9.3 发布前置复核

获取全局发布锁和工作区独占锁后依次要求：

- 工作区状态为 `ready`，无工作区 mutation journal。
- `If-Match` 精确匹配当前 draft ETag。
- 工作区 revision、base、draft 现场复核通过。
- 当前 production digest 等于工作区记录和检查记录。
- 检查记录未过期且绑定相同 build/schema；随后仍重新物化和校验候选。
- 当前 Nginx 状态为 `running`，具有唯一 master 和至少一个有效 worker。
- 固定回环健康探针在发布前取得可比较基线。

任何一项失败都不创建生产写 journal；工作区按事实保持 `ready`、转 `stale` 或转 `needs_attention`。

## 10. reload 与健康确认

### 10.1 固定 reload

reload 只调用 Agent 内部固定 Nginx 可执行文件和固定 reload 参数。浏览器和 Web 不能提供二进制、PID、signal、prefix 或额外参数。命令总期限 15 秒、输出上限 1 MiB。

### 10.2 确认窗口

reload 前记录唯一 master PID 和 worker PID 集合。reload 后在最多 30 秒内有界轮询：

- master PID 存在且与基线相同。
- 状态不为 stopped/unknown，最终达到 running。
- 至少一个有效 worker，且 worker 证据采样稳定。
- 对真实生产路径的最后一次 `nginx -t` 仍有效。
- 固定连接目标为 loopback；默认 `127.0.0.1:80`，仅允许受信任启动配置改变 loopback 端口、Host 和 path，API 不能覆盖。
- HTTP 探针完成连接、写入、header/body 上限和总超时限制；任何完整 HTTP 响应都证明基础服务可达，状态码仍作为证据展示。

健康探针不用于路径匹配结论，不跟随重定向，不连接非 loopback，不允许用户 Header 或 Body。发布前基线不可用时拒绝发布，并给出稳定的健康前置失败；不以关闭检查绕过。

## 11. 自动回滚与判定

### 11.1 自动回滚触发

以下发生在已创建完整备份之后时触发自动回滚：

- 文件应用失败或应用后摘要不等于候选。
- 生产 `nginx -t` 失败。
- reload 明确失败。
- master PID、worker 或固定回环健康在窗口内未确认。
- Web/Agent 启动对账发现事务停在可唯一判定的未提交阶段。

### 11.2 回滚成功条件

回滚从完整备份恢复整个受支持生产树，使用与发布相同的逐文件 durable 协议。只有同时满足以下条件才报告 `rolled_back`：

- 生产完整性摘要等于备份摘要。
- 恢复后的真实生产路径 `nginx -t` 通过。
- 若发布 reload 已请求或无法证明未请求，则对恢复配置执行固定 reload。
- master PID、worker 和固定回环 HTTP 探针通过确认。

若可以证明生产文件已恢复但 Nginx 运行事实无法确认，结果仍是 `needs_attention`，不能降级为“回滚成功”。此时工作区进入 `needs_attention`，普通编辑和发布被阻止；v0.2.3 才提供人工处置入口。

## 12. 崩溃恢复与生命周期

Web 在绑定管理端口前：

1. 对账 SQLite 中非终态发布和 Agent release journal。
2. 对只停留在校验/备份前的任务安全标记失败或取消。
3. 对 `prepared` 到 `files_applied` 的事务，比较生产、候选和备份摘要，只在结果唯一时继续回滚。
4. 对 `production_validated` 到 `reload_requested` 的事务默认恢复备份，避免在无人确认的启动路径继续授予新配置运行成功。
5. 对 `reload_requested` 后的事务重新采样 master/runtime/health；不能完整证明成功时回滚。
6. 对已 `committed`/`rolled_back` 但 SQLite 落后的一侧幂等补记阶段与审计。
7. 摘要既不是候选也不是备份、journal 缺失、备份损坏或阶段倒退时标记 `needs_attention`。

重放可反复执行，在任意恢复步骤再次崩溃后得到相同判定。Agent 停止接收新发布后才进入服务关闭；已在生产写阶段的事务获得有界清理窗口，超时则保留 durable journal 由下次启动继续。

## 13. 领域状态与 SQLite

### 13.1 工作区状态扩展

新增 `published` 终态。发布成功后原工作区保持可读、可 diff，但不可再编辑或再次发布；它记录 `last_release_id`。这避免修改 v0.2.1 不可变 base 或把已发布草稿静默 rebase 为新工作区。管理员从新生产状态创建新的工作区继续编辑。

检查失败、发布前失败或已确认自动回滚后，工作区在生产摘要仍等于其 base 时保持 `ready`。证据不唯一时进入 `needs_attention`。其他旧工作区在下一次读取时按现有规则转 `stale`。

### 13.2 新持久化概念

单调迁移新增：

| 概念 | 持久化内容 |
| --- | --- |
| publish checks | ID、workspace/revision、摘要绑定、schema/build、状态、诊断计数、时间 |
| releases | ID、workspace/check/backup、actor、状态、当前阶段、摘要、request ID、时间 |
| release stages | release ID、单调 sequence、阶段、结果、安全 code、时间、公开 details JSON |
| backups | ID、release ID、状态、条目数、总字节数、创建/验证时间 |

终态 release 状态固定为：`succeeded`、`failed`、`rolled_back`、`needs_attention`、`cancelled`。运行态使用 `queued`、`running`、`rolling_back`。阶段按 `(release_id, sequence)` 稳定排序，并有严格上限；重复恢复按幂等 operation ID 去重。

## 14. REST API 与 SSE

### 14.1 资源

| 方法与路径 | 语义 |
| --- | --- |
| `POST /api/v1/config/workspaces/{id}/publish-checks` | 绑定当前 ETag 执行发布检查 |
| `GET /api/v1/config/publish-checks/{check_id}` | 查询检查证据 |
| `POST /api/v1/config/workspaces/{id}/releases` | 具名确认并创建发布任务 |
| `GET /api/v1/config/releases/{release_id}` | 查询任务、阶段和最终结果 |
| `GET /api/v1/config/releases/{release_id}/events` | 从 `Last-Event-ID` 恢复的 SSE 阶段流 |

检查 POST 要求认证、Origin、CSRF 和 `If-Match`；body 为空对象。发布 POST 还要求 `check_id` 和精确 `confirm_name`。不能用查询参数触发变更。

### 14.2 响应约束

- 所有检查、发布和事件响应使用 `Cache-Control: no-store`。
- 发布创建返回 202、release DTO 和 `Location`；任务成功与否通过任务资源判断，不把 202 当成功。
- SSE `id` 是单调 stage sequence，`event` 只使用 `snapshot`、`stage`、`terminal`、`heartbeat`。
- 首次连接先发送持久化 snapshot；断线重连从 `Last-Event-ID` 继续，不丢失终态。
- 心跳不写数据库、不进入 aria-live；无权限、任务不存在或 session 过期时关闭流并返回正常 HTTP 错误。
- 客户端取消连接不取消发布。v0.2.2 不提供用户取消生产写阶段的 API。

### 14.3 稳定错误

新增公开错误：

| HTTP | code | 场景 |
| --- | --- | --- |
| 422 | `CONFIG_CANDIDATE_INVALID` | 候选完整校验失败 |
| 409 | `CONFIG_PUBLISH_CHECK_EXPIRED` | 检查过期或摘要绑定变化 |
| 409 | `CONFIG_PUBLISH_IN_PROGRESS` | 已有全局发布/回滚事务 |
| 409 | `CONFIG_PRODUCTION_CHANGED` | 发布前生产摘要变化 |
| 409 | `CONFIG_BACKUP_INVALID` | 备份未完成或完整性失败 |
| 503 | `NGINX_HEALTH_UNAVAILABLE` | 发布前或确认阶段回环健康不可用 |
| 500 | `CONFIG_RELEASE_NEEDS_ATTENTION` | 无法安全判定发布或回滚事实 |

底层错误继续映射到现有 timeout、Agent unavailable、path/limit 和 workspace 状态错误。details 白名单只允许相对路径、行号、阶段、limit、HTTP 状态和当前 ETag。

## 15. 前端交互

### 15.1 发布入口

发布入口位于现有工作区审阅区域，不创建脱离工作区的新配置真源。只有以下条件全部满足时“检查发布”可用：

- 工作区 `ready`。
- 没有浏览器内 dirty 文档。
- diff 完整且至少有一个变化。
- 当前没有 mutation 或发布任务。
- session 已认证。

dirty、stale、published、needs-attention、diff incomplete 和 Agent unavailable 都显示持久 inline 原因，不通过 disabled 外观或 toast 单独表达。

### 15.2 检查与确认

检查面板展示：差异文件/行数、生产与草稿身份、候选校验结果、诊断位置、Nginx build、检查时间和过期时间。成功后仍明确提示“尚未修改生产配置”。

发布使用具名 modal：

> 发布工作区“`<name>`”并 reload Nginx？
>
> 系统将重新检查生产和草稿，创建完整备份，更新生产配置并 reload。失败时会在可安全判定时自动回滚；无法确认时将进入需要人工处理。

确认输入必须精确等于工作区名称。modal trap focus、Escape 关闭、背景 inert、关闭后恢复触发焦点。任务一旦进入生产写阶段，关闭 modal 或页面不取消任务。

### 15.3 进度与结果

进度使用有序 stage timeline。每一项同时包含图标、阶段名称、状态词和时间；颜色不是唯一信号。当前阶段使用最小 `aria-live=polite`，历史阶段和心跳不重复播报。

结果区分：

- 成功：已发布、reload 与健康确认通过，显示 release/backup ID 和阶段证据。
- 失败且未写生产：明确“生产配置和 Nginx 未改变”。
- 已回滚：明确“发布失败，已恢复最后一个有效版本并确认运行健康”。
- needs-attention：阻断性 inline alert，明确生产或运行状态无法确认，只允许查看证据；不提供 v0.2.3 的人工恢复按钮。

页面刷新后从 release GET 和 SSE 恢复，不凭内存推断。toast 只用于“检查完成”等非关键成功；发布终态始终留在页面内。

## 16. DESIGN.md 扩展与可访问性

实现发布 UI 前先在 `DESIGN.md` 增加 `publish-check-panel`、`release-confirmation-modal` 和 `release-stage-timeline`，复用现有 neutral surface、status pair、Action Blue、modal、drawer 和 44px 规则。

- timeline 使用语义有序列表，连接线为中性 hairline，不使用渐变或装饰阴影。
- running/success/warning/error/unknown 都有可见文字和既定形状图标。
- 诊断使用只读、可选择、内部滚动的 code viewer 语法，不使用编辑器角色。
- 320 CSS px 只允许 timeline/diagnostic 自身滚动，页面无横向溢出。
- 1068/833/734/640/480/320 px 均验证确认 modal、进度、终态和焦点恢复。
- 自动 axe/contrast 不能替代键盘、200% zoom、400% reflow 和 SSE 状态播报检查。

## 17. 日志、审计与脱敏

每个检查和发布阶段记录 `request_id`、`workspace_id`、`check_id`/`release_id`、`stage`、`result` 和 `duration_ms`。只有 Agent 边界记录命令执行细节，领域层不重复日志。

审计至少记录：检查开始/结果、备份完成、发布开始、生产文件应用、生产校验、reload 请求/结果、健康确认、回滚开始/结果和 needs-attention。details 只保存计数、公开摘要身份、相对路径数量和稳定 code。

严禁记录：配置正文、diff patch、完整 stderr、绝对路径、临时路径、命令行、敏感摘要、Cookie、Authorization、CSRF、健康 Host 的秘密值或请求 body。

## 18. 测试策略

所有新行为先写失败测试，再实现最小修改。

### 18.1 Go 单元与组件测试

- candidate：完整树 overlay、创建/修改/删除、绝对/相对 include、变量拒绝、symlink/特殊文件、模式、上限和清理。
- validation：固定命令、超时、取消、输出上限、诊断相对化和敏感信息脱敏。
- backup：双清单、敏感文件不泄露、fsync 顺序、完整标记、损坏拒绝和容量失败。
- release：每个 durable 阶段前后故障、操作稳定排序、并发生产变化、摘要不匹配和 global lock。
- reload/health：master 保持、worker 变化/稳定、loopback 限制、超时、非 2xx 响应证据和不跟随重定向。
- rollback：应用失败、生产校验失败、reload 失败、健康失败、回滚 reload 失败和 needs-attention。
- store：迁移、CAS、幂等阶段、顺序、终态和审计一致性。
- HTTP/SSE：认证、Origin、CSRF、If-Match、strict JSON、202/Location、Last-Event-ID、断线恢复和 no-store。

### 18.2 真实 Nginx 与文件系统集成

- 用固定 fixture 对候选完整 `nginx -t` 验证多层 include、绝对 include、错误位置和敏感依赖。
- 在隔离 Nginx 实例上验证 reload 保持 master、替换 worker 和 HTTP 可达。
- 发布期间在每个文件操作点杀进程，重启后只得到旧生产、新生产已确认或 needs-attention。
- 外部进程在检查后、备份中、应用中和 reload 前修改生产，分别验证拒绝、回滚或 needs-attention。
- 注入只读目录、磁盘满、rename/fsync 失败、PID 不可读、worker 缺失、端口超时和 Agent 崩溃。

### 18.3 前端与浏览器

- dirty/diff incomplete/stale/published/needs-attention 的入口阻断。
- 检查 loading/invalid/success/expired。
- 具名确认、焦点 trap/Escape/restore 和重复提交 single-flight。
- SSE snapshot、阶段追加、重连、刷新恢复、终态和 session 过期。
- 成功、未写生产失败、rolled_back 和 needs-attention 的准确文案。
- 1068/833/734/640/480/320 响应式、无页面横向溢出、44px target 和键盘流程。

### 18.4 原生升级、进程重启与持久化

- v0.2.1 SQLite 数据升级后旧工作区、认证、状态和配置浏览保持可用。
- 发布成功后重启应用与 Agent 进程并重新打开相同持久化目录，生产配置、备份索引、published 工作区和 release 结果保持一致。
- 发布各阶段终止 UI 或 Agent 进程，重新启动后恢复判定正确。
- reload 失败、只读配置目录、持久化目录空间耗尽和健康端口不可用均不报告成功。
- 本版本不运行 Docker 脚本、不构建验收镜像、不验证 volume/container lifecycle，也不执行 multiarch；这些门禁全部属于 v0.7.0。

## 20. 版本、文档与提交门禁

开始实施时在同一基线同步：

- `VERSION`、`web/package.json`、lockfile、Go/OCI metadata → `0.2.2`。
- 新建代码文件使用实际读取的 git author 和 `@since 0.2.2`。
- 新迁移只新增 `0003_*.sql`，不修改已发布迁移。
- API 行为同步 `api/v1/openapi.yaml` 和前端严格类型/解析器。
- 前端实现前先更新 `DESIGN.md`。

质量门禁沿用根 `AGENTS.md` 的 Go、前端和原生真实 Nginx 命令。按 `PLAN.md` 当前确认的版本边界，v0.2.2 不执行任何 Docker 或 multiarch 验证；这些命令只在 v0.7.0 运行。未运行或用户停止的测试不声称通过，未取得证据的 `PLAN.md` 项不勾选。

## 21. v0.2.3 接口边界

v0.2.2 留给后续版本的是只读事实和受保护恢复点：

- backup ID、完整性状态和关联 release 可供 v0.2.3 人工恢复，但本版本没有 restore API。
- needs-attention 保留证据并阻止普通变更，v0.2.3 才能记录人工处置。
- release/backup 阶段可进入历史页面，v0.2.2 UI 只围绕当前工作区和最近任务。
- retention 只能删除未受保护且不被事务引用的备份；v0.2.2 不提前实现删除。
- restart 必须是新的 Agent typed operation；不能把 reload 接口扩展为任意 signal。
