# Nginx UIX v0.7.0 升级与回滚

## 适用范围

本流程覆盖官方直接支持的 v0.6.0 到 v0.7.0 Docker 持久数据升级。v0.7.0 不新增数据库 migration，已发布集合仍精确为 `0001`–`0007`。原生 arm64 验收已经完成停止旧容器、原卷直升、双卷冷备复制到空 volume、同镜像重建和持久数据对账；真实 amd64 runtime 仍等待对应 runner。

升级不是只替换 UI 文件：`/etc/nginx` 和 `/var/lib/nginx-uix` 必须作为同一个恢复单元管理。不得只复制 SQLite 主文件、只备份 Nginx 配置或让旧版本与新版本同时写同一数据根。

v0.7.0 只提供本地验收候选，没有远端发布 tag。实际升级必须使用来源和 digest 明确的镜像；不要把本文中的本地候选标签误写成公共 pull 地址。

## 升级前

1. 阅读目标版本的 `PLAN.md`、设计规格和验收记录，确认没有未接受的平台限制。
2. 记录当前应用版本、提交/构建身份、Nginx `-V`、持久根和服务身份。
3. 在 UI 中确认没有执行中的 release、restore、restart、Route Lab 或 certificate task；未完成任务必须等待持久终态或按产品流程取消。
4. 记录所有开放 `needs_attention` case。升级不会自动把不确定状态变成成功。
5. 优雅停止旧一体化容器并确认 exit code；不要在 UI、Agent、Nginx 或 SQLite 写连接仍活动时复制 volume。
6. 按[冷备与灾难恢复](backup-and-disaster-recovery.md)创建、验证一个覆盖两个持久根的恢复点。
7. 在备份副本上检查 SQLite integrity、migration `1..7`、owner/mode、证书材料和隔离 `nginx -t`。

任何检查失败都停止升级。不要通过删除 WAL、修改 migration 表、跳过损坏文件或从 SQLite 重建 Nginx 配置继续。

## 前向升级

1. 保持旧容器停止，部署版本、image ID、source fingerprint 和 build identity 明确的 v0.7.0 镜像。
2. 保持 `/etc/nginx`、`/var/lib/nginx-uix`、管理员 Secret 和 public URL 不变。
3. 将原来的两个 volume 挂载到相同目标，启动 v0.7.0 一体化容器；启动对账完成前不接收生产变更。
4. 检查 liveness 与 readiness，登录后复核 Dashboard 的 UI、Agent、Nginx 和启动校验证据。
5. 验证管理员、工作区、分组、release/recovery 历史、Route Lab 历史、证书账户/证书/任务和备份索引仍存在。
6. 只执行无副作用读取和隔离测试作为 smoke；不要用生产 reload 验证升级。
7. 保留升级前恢复点，直到观察窗口结束并完成一次恢复演练。

v0.7.0 打开数据库时会幂等复核 migration 校验和。任何历史 SQL 与记录校验和不一致都会拒绝启动，不能手工改写 `schema_migrations` 绕过。

## 回滚决策

先判断数据兼容性，再决定是否只回滚程序：

| 情况 | 允许动作 |
| --- | --- |
| v0.7.0 尚未启动 | 可恢复 v0.6.0 容器；持久数据未被新程序打开 |
| v0.7.0 已启动，但 schema 仍为 `1..7` 且未产生待执行任务 | v0.6.0 与 schema 兼容；仍应先停机并保存 v0.7.0 快照 |
| 存在执行中或 `needs_attention` 任务 | 不做盲目二进制回滚；先保留证据并完成/处置任务 |
| 未来版本新增 migration | 不允许把新数据目录直接交给旧版本；恢复匹配旧版本的完整冷备 |
| integrity、摘要或权限无法确认 | 隔离当前数据，进入灾难恢复；不得报告回滚成功 |

v0.7.0 不新增 schema 或产品持久状态，但这不替代停机快照、任务终态和完整双卷兼容性检查。

## 程序回滚

1. 优雅停止 v0.7.0 一体化容器，等待所有文件描述符与任务 owner 退出。
2. 为当前 v0.7.0 状态再创建一个只读故障证据快照。
3. 确认数据库 migration 仍为 `1..7`，且没有只能由新版本解释的进行中状态。
4. 部署先前经过验证的 v0.6.0 镜像，保持两个 volume 和全部启动输入不变。
5. 启动并检查 health、登录、只读历史和 Nginx 状态；不要把“进程能启动”当成生产健康已确认。

如果任一步不确定，停止旧程序并恢复升级前的完整冷备，而不是把目录合并回去。

## 数据恢复式回滚

数据恢复会丢弃升级后产生的操作记录，因此必须是明确的管理员决策，并保留故障状态副本：

1. 停止所有 UIX/Nginx 配置写入者。
2. 将当前两个持久根重命名或移到隔离位置；不要删除唯一故障证据。
3. 创建空目标，按原 owner/group/mode 恢复升级前冷备的两个根。
4. 在隔离状态检查 manifest、SQLite、migration、证书文件和完整 `nginx -t`。
5. 启动匹配备份版本的 Agent/UI，完成对账后再恢复流量。

恢复目标不得与现有树逐文件合并。无法证明恢复摘要、权限、数据库和 Nginx 校验全部一致时，终态是“需要人工处理”，不是成功。
